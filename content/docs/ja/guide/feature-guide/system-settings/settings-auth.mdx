## 認証設定の概要

認証設定は 5 つのセクションに分かれています。左側のナビゲーションで「認証」配下のセクションを切り替えます。既定では「基本認証」が開きます。

**各セクションの概要**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| セクション | 用途 | セクション内のタブ |
| --- | --- | --- |
| [基本認証](#基本認証) | パスワードでのログインと登録、メールアドレスの確認、ドメイン制限を設定します。 | — |
| [OAuth 連携](#oauth-連携) | 組み込みのサードパーティログインプロバイダーの認証情報を設定し、有効化または無効化します。 | 「GitHub」「Discord」「OIDC」「Telegram」「LinuxDO」「微信」 |
| [パスキー認証](#パスキー認証) | WebAuthn パスキーの有効化、ドメイン、検証要件を設定します。 | — |
| [ボット対策](#ボット対策) | Cloudflare Turnstile による人間かどうかの確認を設定します。 | — |
| [カスタム OAuth](#カスタム-oauth) | カスタム OAuth プロバイダーを追加、管理します。 | — |

</div>

<Callout type="info" title="ヒント">

- ログイン方式を有効にできない、OAuth コールバックでエラーが発生する、新しいドメインでパスキーを使用できない、またはログイン後の検証に失敗する場合は、[よくある質問](#よくある質問)を参照してください。
</Callout>

## 設定セクション

この章では、左側のナビゲーションに表示される順に 5 つのセクションを説明します。各セクションの保存ボタンと設定が反映されるタイミングについては、[保存と反映](#保存と反映)を参照してください。

### 基本認証

- 認証-基本認証

![認証-基本認証ページ](/assets/guide/feature-guide/system-settings-authentication-basic-authentication.png)

**操作手順**

1. 必要に応じて「パスワードログイン」「登録を有効にする」「パスワード登録」「メールアドレスの確認」をオンまたはオフにします。
2. メールアドレスのドメインを制限する場合は、先に「メールドメインの許可リスト」に 1 行につき 1 つのドメインを入力して保存してから、「メールドメイン制限」をオンにします。
3. ページ上部の「変更を保存」をクリックします。

<Callout type="warn" title="注意">

- メールアドレスの確認を有効にする前に、メール送信設定（SMTP または Resend）を使ってサーバーから正常にメールを送信できることを確認してください。
- 認証オプションを保存しても、メール送信設定のテストは実行されません。メールが届かない場合、ユーザーは登録時の確認やパスワードの再設定を完了できないことがあります。
</Callout>

**設定項目**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap [&_td_code]:wrap-anywhere">

| 設定項目 | 説明 | 入力要件と制限 | デフォルト値 |
| --- | --- | --- | --- |
| パスワードログイン | ユーザー名とパスワードでのログインを許可します。 | オン・オフを切り替えます。 | オン |
| 登録を有効にする | 新規ユーザーの登録を許可します。 | オン・オフを切り替えます。オフにすると、OAuth や微信で初めてログインした場合も新規アカウントは作成されません。 | オン |
| パスワード登録 | パスワードを使用した登録を許可します。 | オン・オフを切り替えます。「登録を有効にする」もオンである必要があります。 | オン |
| メールアドレスの確認 | パスワードで登録した新規アカウントにメールアドレスの確認を求めます。 | オン・オフを切り替えます。有効にする前に、<a href="/ja/docs/guide/feature-guide/system-settings/settings-operations#メールと通知" target="_blank" rel="noopener noreferrer">運用設定</a>の「メールと通知」でメール送信設定を完了してください。 | オフ |
| メールドメイン制限 | 「メールドメインの許可リスト」に含まれるドメインのメールアドレスのみを受け付けます。 | オン・オフを切り替えます。許可リストが未保存の場合は有効にできません。表示されるメッセージは[よくある質問](#よくある質問)を参照してください。 | オフ |
| メールエイリアスの制限 | メールエイリアス（例 `user+alias@domain.com`）の使用を拒否します。 | オン・オフを切り替えます。有効にすると、`first.last@example.com` のように、`@` より前に `+` または `.` を含むメールアドレスが拒否されます。 | オフ |
| メールドメインの許可リスト | 許可するメールアドレスのドメインです。ドメイン制限が有効な場合に使用されます。 | 1 行につき 1 つのドメインを正確に入力します。完全なメールアドレスやワイルドカードは入力できません。 | `gmail.com`、`163.com`、`126.com`、`qq.com`、`outlook.com`、`hotmail.com`、`icloud.com`、`yahoo.com`、`foxmail.com` |

</div>

<Callout type="info" title="ヒント">

- ユーザー名は最大 20 文字、メールアドレスは最大 50 文字、パスワードは 8～128 文字です。
- 新規登録したユーザーは一般ユーザーとして作成されます。管理者ロールの作成や変更は、権限を持つ管理者が<a href="/ja/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">ユーザー管理</a>で行います。
- パスワード登録用の確認コードを送信するときと、ログイン済みのユーザーがメールアドレスを紐付けるときに、ドメインの許可リストとメールエイリアスのルールがチェックされます。
</Callout>

### OAuth 連携

組み込みのサードパーティログインプロバイダーにこのサイトを登録したら、対応するタブに認証情報を入力して有効にします。

このセクションには「GitHub」「Discord」「OIDC」「Telegram」「LinuxDO」「微信」の 6 つのタブがあります。ページ上部には「リセット」と「変更を保存」があり、「変更を保存」をクリックすると各タブの変更がまとめて保存されます。微信以外の各タブの上部には「設定ガイド」があり、「ログインを有効にする前に、プロバイダー側のアプリケーションで以下の値を設定してください。」という案内と、コピーできるコールバック URL が表示されます。未保存の変更がある場合は、見出しの横に「未保存の変更」と表示されます。

**操作手順**

1. プロバイダーの管理画面でアプリケーションを作成し、アプリケーション名、ホームページ、プロバイダーが指定するコールバック URL を登録します。
2. 対応するタブに認証情報とエンドポイントを入力し、ページ上部の「変更を保存」をクリックします。
3. プロバイダーのスイッチをオンにし、ページ上部の「変更を保存」をもう一度クリックします。

<Callout type="info" title="ヒント">

- 「設定ガイド」のコールバック URL は「サーバーアドレス」を基に生成され、形式は `/oauth/{provider}` です。OIDC では「リダイレクト URL」、その他のプロバイダーでは「認可コールバック URL」と表示されます。GitHub、Discord、OIDC では「ホームページ URL」も表示されます。
- サーバーアドレスが未設定の場合、これらの URL はプレースホルダー「サイトのアドレス」で始まるため、そのままでは使えません。先に<a href="/ja/docs/guide/feature-guide/system-settings/settings-site#システム情報" target="_blank" rel="noopener noreferrer">サイトとブランドの設定</a>でサーバーアドレスを入力してください。
- Discord と OIDC のトークン交換では、サーバーアドレスから生成された対応するコールバック URL が送信されます。現在、GitHub のトークン交換では `redirect_uri` は送信されません。
- LinuxDO は、受信したリクエストのプロトコルとホストに `/api/oauth/linuxdo` を付加してコールバック URL を生成します。画面に表示される URL と異なる場合があります。
- コールバック URL、ブラウザーからアクセスする公開 URL、サーバー側で認識するプロトコルは整合している必要があります。画面でこのサイト用に生成された URL をコピーし、プロバイダーの要件とリバースプロキシが実際に転送するパスに合わせてください。
- 管理者は<a href="/ja/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">ユーザー管理</a>でユーザーの連携情報を管理できます。
</Callout>

#### OIDC

- 認証-OAuth 連携 OIDC

<Callout type="info" title="ヒント">

- 「設定ガイド」には「プロバイダーが対応している場合、OIDC Discovery でエンドポイントのフィールドを自動入力できます。」という案内も表示されます。

### パスキー認証

- 認証-パスキー認証

![認証-パスキー認証ページ](/assets/guide/feature-guide/system-settings-authentication-passkey-authentication.png)

パスキーは WebAuthn を使用します。有効にすると、ユーザーはパスキーを登録し、そのパスキーでログインできます。「メインドメイン」と「互換パスキードメイン」は「パスキードメイン」グループにあります。グループ内の「設定が必要な理由」をクリックすると、「パスキードメインの設定方法」が開きます。

**操作手順**

1. 必要に応じて「Passkey を有効にする」をオンにし、表示名、ユーザー検証、デバイスタイプの優先設定を指定します。
2. 「パスキードメイン」グループの「メインドメイン」を入力し、旧ドメインは「互換パスキードメイン」に残します。ポートを含む完全なアドレスは「パスキーの使用を許可するサイト」に入力します。
3. ページ上部の「変更を保存」をクリックします。
4. 確認ダイアログが表示されたら、「現在のドメイン」と「新しいドメイン」を確認します。互換ドメインを削除する場合は、影響を受けるパスキーも確認し、「ドメインを変更」または「ドメインを削除」をクリックします。

<Callout type="warn" title="注意">

- 「パスキードメインの設定方法」には、現在のサイトとシステムで現在使用されているドメインが表示されます。ダイアログ内のボタンは、ドメインが未設定の場合は「現在のサイトを入力」、設定済みの場合は「既存のドメインを保持」と表示されます。
- このボタンは、HTTPS または `http://localhost` でアクセスしており、ホストが IP アドレスでない場合にのみ使用できます。条件を満たさない場合は「HTTPS のドメインで Passkey を設定してください。ローカル開発では localhost を使用できます。」と表示されます。
- メインドメインが現在のサイトと一致しないか未設定の場合、グループ内の案内が黄色の警告に変わります。「パスキーの使用を許可するサイト」に現在のサイトが含まれていない場合は、「現在のサイトはまだリストにありません。ユーザーがこのサイトでログインする場合は、… を追加してください。」と表示されます。
- 削除したドメインのパスキーは使用できなくなります。確定する前に、影響を受けるユーザーが別の方法でログインできることを確認してください。
- 「Passkey を有効にする」をオフにすると、パスキーを登録済みで 2FA を有効にしていないユーザーはログインできなくなります。一次認証に成功した後もパスキーでの検証が要求され、「この認証方式は現在利用できません。」と表示されます。
- ログインできる状態に戻すには、「Passkey を有効にする」を再度オンにするか、<a href="/ja/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">ユーザー管理</a>で該当ユーザーに対して「Passkey をリセット」を実行します。リセットすると、ユーザーのパスキー認証情報が削除され、既存のログインセッションが無効になります。
</Callout>

### カスタム OAuth

ログインページでユーザーが利用できるカスタム OAuth プロバイダーを追加・管理します。

セクション上部の「コールバック URL の形式」には、コピーできる「OAuth コールバック URL」が表示されます。URL はサーバーアドレスに `/oauth/{slug}` を付けた形式です。サーバーアドレスが未設定の場合は「サイトアドレス」が使われます。その下にプロバイダーの一覧があり、右側に「プロバイダーを追加」があります。このセクションにはページヘッダーの保存ボタンがなく、プロバイダーごとにダイアログで保存します。

#### プロバイダー一覧

- 認証 - カスタム OAuth

![認証 - カスタム OAuth ページ](/assets/guide/feature-guide/system-settings-authentication-custom-oauth.png)

一覧には「ユーザー認証に使用するカスタム OAuth プロバイダーを管理します」と表示されます。プロバイダーがない場合は「カスタム OAuth プロバイダーはまだ設定されていません。」と表示されます。

**削除手順**

1. 対象のプロバイダーにユーザーの紐付けが残っていないことを確認します。下記の「ログイン・紐付け・削除のルール」を参照してください。
2. 対象行の ⋯ メニューから「削除」を選択します。
3. 確認ダイアログ「プロバイダーを削除」で削除を確定します。削除が完了すると「プロバイダーを削除しました」と表示されます。

<Callout type="warn" title="注意">

- 削除後は、そのプロバイダーを使っていたユーザーが、そのプロバイダー経由でログインできなくなります。
- ユーザーの紐付けが残っている場合、削除は拒否され、「この OAuth プロバイダーにはまだユーザーが紐付けられているため、削除できません。先にすべてのユーザーの紐付けを解除してください。」と表示されます。

</Callout>

**一覧の各列**

| 列 | 説明 |
| --- | --- |
| アイコン、名前 | プロバイダーのアイコンと名前。 |
| 識別子 | プロバイダーの識別子（slug）。コールバック URL の一部になります。 |
| ステータス | 「有効」または「無効」。有効なプロバイダーのみログインページに表示されます。 |
| Client ID | プロバイダーの Client ID。 |
| 操作 | 編集アイコンで「OAuth プロバイダーを編集」が開きます。⋯ メニューから「削除」を選択できます。 |

**ログイン・紐付け・削除のルール**

1. OAuth の `state` の有効期間は現在約 10 分です。紐付けに使う `state` は、操作を開始したユーザーとセッションにも関連付けられ、別のセッションでは再利用できません。
2. 同じユーザーが同じカスタムプロバイダーに保持できる紐付けは 1 件のみです。同じプロバイダーアカウントを複数のローカルユーザーに紐付けることもできません。
3. プロバイダーを無効にすると、以降のログインと紐付けがブロックされます。既存の紐付けは保持されます。
4. プロバイダーを削除する前に、ユーザーが<a href="/ja/docs/guide/feature-guide/user/security#メールアドレスや外部アカウントを連携する" target="_blank" rel="noopener noreferrer">セキュリティとアクセス</a>ページで紐付けを解除するか、権限を持つ管理者が<a href="/ja/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">ユーザー管理</a>ですべての紐付けを解除する必要があります。紐付けが 1 件でも残っていると、削除リクエストは拒否されます。

#### プロバイダーの追加と編集

- 認証 - カスタム OAuth を追加

![認証 - カスタム OAuth の追加画面](/assets/guide/feature-guide/system-settings-authentication-custom-oauth-add-provider.png)

- 認証 - カスタム OAuth を編集

![認証 - カスタム OAuth の編集画面](/assets/guide/feature-guide/system-settings-authentication-custom-oauth-edit-provider.png)

**前提条件**

- サードパーティプロバイダーの管理画面で OAuth アプリケーションを作成し、Client ID、Client Secret、認可エンドポイント、トークンエンドポイント、ユーザー情報エンドポイントを用意します。

1. 「プロバイダーを追加」をクリックし、「プリセットからクイック設定」でプリセットテンプレートを選択して「API アドレス」を入力するか、空のフォームに直接入力します。
2. 名前、識別子（slug）、クライアント認証情報、3 つのエンドポイント、必要な詳細設定項目を入力します。
3. 「OAuth コールバック URL」カードからコールバック URL をコピーし、プロバイダーの管理画面に登録します。この URL は識別子の入力に合わせてリアルタイムに更新されます。

6. 識別子（slug）を変更する前に、サードパーティの管理画面に登録したコールバック URL を更新します。変更を保存すると、以前の URL は対象のプロバイダーに対応しなくなります。

<Callout type="info" title="ヒント">

- プリセットには GitHub Enterprise、GitLab、Gitea、Nextcloud、Keycloak、Authentik、ORY Hydra が用意されています。エンドポイントは「API アドレス」に各パスを連結して生成されます。「API アドレス」が空欄の場合に入力されるのは、名前、識別子、アイコン、スコープ、フィールドマッピングのみです。
- プリセットは入力を補助するもので、プロバイダーにそのまま接続できることを保証するものではありません。

## ログイン時の検証とセキュリティ

このセクションでは、認証に関するセキュリティチェックの適用範囲を説明します。ここで説明する機能の多くは、このページのフォームで設定する項目ではありませんが、ログインとアカウントのセキュリティに影響します。

- **共通のログイン検証**：ユーザーが 2FA または Passkey を有効にしている場合、一次認証に成功すると共通の検証チャレンジに進みます。有効期間は約 5 分で、検証に成功して初めてセッションが発行されます。この共通の仕組みにより、ログインのセキュリティが強化されます。Passkey で直接ログインした場合、追加のチャレンジはありません。
- **検証証明の使い捨て**：検証証明は HMAC ベースのコンテキストハッシュによって「セッション + アクション」に紐付けられ、1 回だけ使用できます。コールバック、検証、紐付けの処理に失敗した場合は、通常、その処理を最初からやり直す必要があります。同じ証明を再利用しないでください。
- **2FA の適用範囲**：2FA はユーザー単位で設定するセキュリティ機能です。ユーザーは<a href="/ja/docs/guide/feature-guide/user/security#2-段階認証を有効にする" target="_blank" rel="noopener noreferrer">セキュリティとアクセス</a>ページで 2FA を有効化・管理できます。管理者が特定ユーザーの 2FA、バックアップコード、ログインセッションをリセットするには、<a href="/ja/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">ユーザー管理</a>の「2FA をリセット」を使用します。
- **アカウントの紐付け、紐付け解除、削除**：セッションの乗っ取りを防ぐため、アカウントの紐付けを変更したり、アカウントを削除したりする際にも再認証が必要です。2FA または Passkey が有効な場合はその方法を使用し、どちらも有効でない場合はパスワードまたはサードパーティログインを使用します。

<Callout type="warn" title="注意">

2FA または Passkey を有効にすると、一次認証の後に検証チャレンジ（有効期間は約 5 分）を完了してからセッションが発行されます。Root とユーザーには、動作を確認済みの代替ログイン手段を少なくとも 1 つ確保してください。検証証明や OAuth の `state` が期限切れまたは使用済みの場合は、ログインや紐付けを最初からやり直してください。同じ URL を繰り返し再読み込みしても処理は再開されません。

</Callout>

## パスワード転送時の暗号化

パスワード転送時の暗号化は、環境変数 `PASSWORD_LOGIN_ENCRYPTION_ENABLED`（ブール値、デフォルトは `false`）で制御します。このページに対応する設定項目はありません。この変数は起動時にのみ読み込まれるため、変更後は New API の再起動が必要です。

有効にすると、パスワードログイン時や機密性の高い操作でパスワードを検証する際に、フロントエンドがパスワードを RSA-OAEP で暗号化して送信します。ユーザー登録時は暗号化の対象外で、パスワードは平文のまま送信されます。

**動作の仕組み**

- サーバーは起動時にデータベースから RSA 秘密鍵を読み込みます。秘密鍵がなければ、2048 ビットの鍵を自動生成してデータベースに保存します。同じデータベースに接続するノードはこの鍵を共有します。
- フロントエンドはサーバーから有効化の状態と公開鍵を取得し、パスワードを RSA-OAEP v1/v2 のエンベロープ形式で暗号化してリクエストとともに送信します。
- サーバーは秘密鍵でパスワードを復号し、検証します。

<Callout type="warn" title="注意">

- このスイッチはインスタンス単位の環境変数です。複数インスタンス構成では、すべてのノードで同じ値に設定してください。
- ノード間で設定が一致しない場合、一部のログインリクエストが拒否され、「無効なパラメーター」と表示されます。
- 秘密鍵を読み込めない、または書き込めない場合、サービスは起動しません。復号に失敗すると「ユーザー名またはパスワードが正しくないか、ユーザーが凍結されています」と表示されます。
- リバースプロキシの HTTPS/HTTP 構成も確認してください。このスイッチをオフにすると、パスワードはアプリケーション側で暗号化されず、平文で送信されます。

</Callout>

## 保存と反映

保存方法は<a href="/ja/docs/guide/feature-guide/system-settings/system-setting#保存方法" target="_blank" rel="noopener noreferrer">システム設定の概要</a>を、反映と同期のルールは<a href="/ja/docs/guide/feature-guide/system-settings/system-setting#反映範囲と複数インスタンス間の同期" target="_blank" rel="noopener noreferrer">適用範囲と複数インスタンス間の同期</a>を参照してください。ブラウザーに新しい値が表示されるタイミングは<a href="/ja/docs/guide/feature-guide/system-settings/system-setting#フロントエンドの表示とキャッシュ" target="_blank" rel="noopener noreferrer">フロントエンドの表示とキャッシュ</a>、キーの保存済みの値を表示せず、空欄で保存すると既存の値を保持する仕組みは<a href="/ja/docs/guide/feature-guide/system-settings/system-setting#機密設定と監査記録" target="_blank" rel="noopener noreferrer">機密性の高い設定と監査ログ</a>を参照してください。特に記載がない限り、保存後はリクエストを処理したノードで新しい値がすぐに使われます。他のノードにはシステム設定の同期によって約 3 秒以内に反映されます（遅くとも 1 同期周期以内。デフォルトは 60 秒）。同期周期は環境変数 `SYNC_FREQUENCY` で秒単位で調整できます。このページに記載されている環境変数はいずれも起動時にのみ読み込まれるため、変更後は New API の再起動が必要です。各設定項目で新しい値が使われるタイミングは次のとおりです。

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 設定項目 | 保存方法 | 反映タイミング |
| --- | --- | --- |
| 基本認証 › パスワードログイン | ページヘッダーの「変更を保存」 | 次回のパスワードログインリクエストから適用されます。既存のログインセッションには影響しません。 |
| 基本認証 › ユーザー登録を有効化、パスワード登録 | ページヘッダーの「変更を保存」 | 次回の登録リクエストから適用されます。「ユーザー登録を有効化」をオフにすると、OAuth や WeChat で初めてログインする場合も、新しいアカウントは作成されません。 |
| 基本認証 › メールアドレスの確認 | ページヘッダーの「変更を保存」 | 次回の登録からメールアドレスと確認コードが必要になります。登録済みのアカウントには影響しません。 |
| 基本認証 › メールドメイン制限、メールエイリアス制限、メールドメインの許可リスト | ページヘッダーの「変更を保存」 | 次回の確認コード送信時やメールアドレスの紐付け時にチェックされます。既存アカウントのメールアドレスは再チェックされません。 |
| OAuth 連携 › 各プロバイダーのスイッチ、認証情報、エンドポイント | ページヘッダーの「変更を保存」 | 次回のログインまたは紐付けから適用されます。無効化してもユーザーの既存の紐付けは保持されます。 |
| パスキー認証 | ページヘッダーの「変更を保存」。ドメイン設定の変更により有効なドメインが変わる場合、メインドメインを空欄にする場合、または互換ドメインを削除する場合は、確認してから保存します。 | 次回のパスキー登録またはログインから適用されます。削除したドメインのパスキーは使用できなくなります。 |
| ボット対策 | ページヘッダーの「変更を保存」 | 次に保護対象のリクエストを受けたときからサーバーで検証されます。対象範囲は[ボット対策](#ボット対策)を参照してください。 |
| カスタム OAuth | 一覧とダイアログでプロバイダーごとに保存します。ページヘッダーに保存ボタンはありません。 | リクエストを処理したノードに即時反映されます。他のノードでは約 3 秒以内に自動で読み込まれるため、再起動は不要です。読み込まれるまでは従来の設定で処理されます。 |
| パスワード転送時の暗号化 | 環境変数で制御します。 | サービスの再起動が必要です。複数インスタンス構成では設定を揃えてください。詳細は[パスワード転送時の暗号化](#パスワード転送時の暗号化)を参照してください。 |

</div>

**補足**

- **有効化の順序**：GitHub、Discord、OIDC、LinuxDO、WeChat の各ログイン方式やメールドメイン制限を有効にする前に、対応する認証情報や設定を入力して保存します。その後、スイッチをオンにして保存します。対応する設定が未保存の場合、有効化は拒否されます。表示メッセージは[よくある質問](#よくある質問)を参照してください。
- **変更がない場合**：OAuth 連携やパスキー認証の設定に変更がない場合、「保存する変更はありません」と表示されます。
- **未保存の変更**：OAuth 連携の設定に未保存の変更がある状態でページを離れると、「未保存の変更」の確認ダイアログが表示されます。
- **ログインページと登録ページ**：ログイン方法、登録への導線、Turnstile コンポーネントの表示には、ブラウザーにキャッシュされたサイトの状態が使われます。サーバー側の判定にはすでに新しい設定が使われており、開いているページには再読み込み後に新しい内容が表示されます。パスキー、OIDC の表示名、カスタム OAuth を保存すると、保存を行ったブラウザーでは表示が自動更新されます。

## 注意事項

**ログインとコールバック**

- **コールバックの整合性**：ブラウザーからアクセスする公開 URL、「サーバーアドレス」、プロバイダーに登録したコールバック URL、リバースプロキシが転送する Host/Proto を一致させてください。
- **検証証明と `state` の使い捨て**：処理に失敗したら、ログインや紐付けを最初からやり直してください。同じ URL を繰り返し再読み込みしても処理は再開されません。
- **共通のログイン検証**：2FA または Passkey を有効にしているユーザーは、一次認証後に検証チャレンジ（有効期間は約 5 分）を完了する必要があります。

**認証情報とドメイン**

- **Passkey とドメインの紐付け**：ドメインやプロトコルを変更したら、メインドメイン、互換パスキードメイン、パスキーの使用を許可するサイト、「サーバーアドレス」を確認してください。旧ドメインは互換ドメインとして残してください。
- **Turnstile**：サイトキーとシークレットキーが両方とも正しいこと、Cloudflare に接続できること、トークンが有効であることが必要です。スイッチはシステム全体で 1 つです。保護対象のフローは[ボット対策](#ボット対策)を参照してください。
- **Telegram の移行**：旧 Login Widget を使用していた場合は、BotFather の Login Widget でコールバック URL `/oauth/telegram` を登録し、Client ID と Client Secret を取得してください。既存の紐付けは引き続き利用できます。識別子（slug）`telegram` は引き続き組み込み用に予約されています。
- **パスワード暗号化用の鍵の共有**：鍵は起動時に自動生成され、データベースに保存されます。各ノードは同じデータベースに接続する必要があります。

## よくある質問

<Accordions type="multiple" className="[&_h3]:font-semibold [&_h3[data-state=open]]:bg-fd-muted [&_[role=region]>div]:border-t [&_[role=region]>div]:pt-3 [&_[role=region]>div]:pb-3 [&_[role=region]>div]:ps-9 [&_[role=region]>div]:text-sm [&_[role=region]>div]:leading-6 [&_[role=region]>div]:text-fd-muted-foreground [&_[role=region]_strong]:text-fd-foreground [&_[role=region]_p]:my-2 [&_[role=region]_ol]:my-1 [&_[role=region]_ul]:my-1 [&_[role=region]_li]:my-0.5 [&_[role=region]_table]:table-fixed [&_[role=region]_th:nth-child(1)]:w-[40%] [&_[role=region]_th:nth-child(2)]:w-[30%]">

<Accordion title="ユーザー登録を有効にしても登録に失敗する">

パスワード登録スイッチ、メールアドレスの確認、メール送信設定、許可リスト、エイリアスのルール、Turnstile に問題がある可能性があります。

**対処方法**

1. バックエンドから返された具体的なエラーを確認します。

</Accordion>

<Accordion title="メールドメインの許可リストが機能しない">

**考えられる原因**

- ドメイン制限が有効になっていません。
- リストが空です。
- ドメイン名を指定する行に、メールアドレス全体またはワイルドカードが入力されています。

**対処方法**

1. メールドメインの許可リストには小文字を使用します。

</Accordion>

<Accordion title="ドメイン制限の対象となるメールアドレスでもパスワードをリセットできる">

現在、ドメインとエイリアスのルールは主に登録用の確認コードの処理に適用されます。パスワードのリセットには独立した処理フローがあるため、両方に同じルールが適用されるとは限りません。

</Accordion>

<Accordion title="OAuth コールバックでエラーが発生する、または state が無効になる">

**考えられる原因**

- 「サーバーアドレス」、リバースプロキシの Host/Proto、またはプロバイダーの管理画面に登録したコールバック URL に問題があります。
- 使い捨てのフロートークンが期限切れです。

</Accordion>

<Accordion title="OIDC の保存時にディスカバリードキュメントのエラーが表示される">

**考えられる原因**

- Well-Known URL が `http://` または `https://` で始まっていません。
- 設定を保存するブラウザーから、その URL にアクセスできません。

**対処方法**

1. Well-Known URL を空欄にし、エンドポイントを手動で入力します。
2. ネットワークポリシーを確認します。

</Accordion>

<Accordion title="カスタム OAuth で Auto Detect を選んでもトークン交換に失敗する">

「認証方式」が Auto Detect の場合、認証情報はリクエストボディのパラメーターとして送信されます。Basic Auth での再試行は行われません。

**対処方法**

1. プロバイダーの要件に従い、Params (in body) または Header (Basic Auth) を明示的に選択します。

</Accordion>

<Accordion title="カスタム OAuth プロバイダーを削除できない">

**表示メッセージ**  
「この OAuth プロバイダーにはまだユーザーが紐付けられているため、削除できません。先にすべてのユーザーの紐付けを解除してください。」（英語：This OAuth provider still has linked users and cannot be deleted. Unbind all users first.）

プロバイダーを無効にしても、既存の紐付けは保持されます。

**対処方法**

1. ユーザーの「セキュリティとアクセス」ページまたは「ユーザー管理」で、対象プロバイダーの既存の紐付けをすべて解除します。

</Accordion>

<Accordion title="OAuth を無効にしてもユーザーに紐付けが表示される">

無効化の対象は、以降のログインと紐付けです。既存の認証情報の紐付けは保持されます。

**対処方法**

1. 「ユーザー管理」で紐付けを解除します。

</Accordion>

<Accordion title="新しいドメインで Passkey が使えない">

メインドメイン、互換パスキードメイン、パスキーの使用を許可するサイト、HTTPS、または「サーバーアドレス」の設定が、新しいドメインに対応していない可能性があります。

**対処方法**

1. 管理者が「ユーザー管理」でパスキーをリセットし、ユーザーに再登録してもらいます。

</Accordion>

<Accordion title="Turnstile の設定を保存できたが、すべてのリクエストが失敗する">

設定を保存した後も、リクエストごとに実行時の検証が行われます。

サイトキー、シークレットキー、Cloudflare のサイトドメイン、サーバーから外部への接続、またはトークンの有効期間に問題がある可能性があります。

</Accordion>

<Accordion title="ログイン後にセッションが発行されない、または検証に失敗する">

**考えられる原因**

- ユーザーが 2FA または Passkey を有効にしており、共通の検証チャレンジに成功していません。
- 検証証明や OAuth の `state` が使用済み、または期限切れです。

</Accordion>

<Accordion title="パスワード転送時の暗号化を有効にするとログインに失敗する">

**考えられる原因**

- 各ノードの `PASSWORD_LOGIN_ENCRYPTION_ENABLED` の値が一致していません。
- 各ノードが同じデータベースに接続していません。

</Accordion>

<Accordion title="Telegram ログインに失敗する">

**考えられる原因**

- BotFather の Login Widget にコールバック URL `/oauth/telegram` が登録されていません。
- 対応する Client ID と Client Secret が入力されていません。

</Accordion>

<Accordion title="ログイン方法を有効にすると「有効にできません」と表示される">

対応する設定が未保存の場合、スイッチの有効化は拒否されます。主な表示メッセージは次のとおりです。

| 表示メッセージ | 考えられる原因 | 対処方法 |
| --- | --- | --- |
| 「GitHub OAuth を有効にできません。先に GitHub OAuth の Client ID と Client Secret を入力してください！」（英語：Cannot enable GitHub OAuth. Enter the GitHub OAuth Client ID and Client Secret first.）。Discord OAuth、OIDC、LinuxDO OAuth も同様です。 | 対象プロバイダーの認証情報が未保存です。 | スイッチをオフにした状態で認証情報を保存し、その後スイッチをオンにして保存します。 |
| 「メールドメイン制限を有効にできません。先に許可するメールドメインを入力してください！」（英語：Cannot enable the email domain restriction. Enter the allowed email domains first.） | 「メールドメインの許可リスト」が未保存です。 | 許可リストを保存してから「メールドメイン制限」を有効にします。 |
| 「WeChat ログインを有効にできません。先に WeChat ログインの設定を入力してください！」（英語：Cannot enable WeChat login. Enter the WeChat login settings first.） | WeChat のサーバーアドレスが未保存です。 | WeChat の設定を保存してから有効にします。 |
| 「Turnstile 検証を有効にできません。先に Turnstile 検証の設定を入力してください！」（英語：Cannot enable Turnstile verification. Enter the Turnstile settings first.） | サイトキーが未保存で、今回の保存操作でも入力されていません。 | サイトキーとシークレットキーを入力し、スイッチの設定と一緒に保存します。 |
| 「Telegram OAuth が未設定、または無効です。管理者にお問い合わせください。」（英語：Telegram OAuth is not configured or enabled. Please contact your administrator.） | Telegram の Client ID または Client Secret が未保存で、今回の保存操作でも入力されていません。 | Client ID と Client Secret を入力し、スイッチの設定と一緒に保存します。 |

</Accordion>

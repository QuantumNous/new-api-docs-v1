- Root のみアクセスできます。サイドバーの「管理者」→「システム設定」を開き、左側のナビゲーションで「リクエストポリシー」配下のセクションを選択します。
- セッション維持とリトライ予算、チャネルのヘルスチェックと自動無効化ルールを設定し、リクエストの判断記録が書き込まれる条件を確認できます。
- 2 つのセクションは同じリクエストポリシー設定に書き込みます。保存時には設定全体が検証されます。詳しくは[保存と適用](#保存と反映)を参照してください。

<Callout type="info" title="ヒント">

- 「セッション維持」は、旧バージョンの「チャネルアフィニティ」に相当します。一部の確認ダイアログやログでは、「すべてのチャネルアフィニティキャッシュのクリアを確認」「チャネルアフィニティ：アップストリームキャッシュヒット」など、引き続き旧称が使われています。
- チャネル一覧ページのタイトル横にある「最大リトライ: N」バッジには、現在の「最大リトライ回数」が表示されます。Root はバッジ（ツールチップは「リトライ設定」）をクリックして「セッションとリトライ」に移動できます。Admin には数値のみが表示されます。
- チャネルの編集時は、「異常時に自動無効化」スイッチの下に「自動無効化の対象」または「自動無効化の対象外」と「設定元: …」が表示されます。グローバル設定を取得できない場合は「グローバルの自動無効化と、このチャネルのスイッチの両方をオンにする必要があります。」と表示されます。その後ろにある「リクエストポリシー」リンク（Root にのみ表示）から「チャネルの健全性」に移動できます。
- API キーの編集時にグループが `auto` の場合は、「グループをまたいでリトライ」スイッチが表示されます。説明の末尾にある「リクエストポリシー」リンク（Root にのみ表示）から「セッションとリトライ」に移動できます。

</Callout>

## リクエストポリシー設定の概要

リクエストポリシーでは、リクエストで優先するチャネル、失敗時にリトライするかどうか、チャネルを自動で無効化または復旧するタイミングを設定します。左側のナビゲーションの「リクエストポリシー」配下で 2 つのセクションを切り替えられます。デフォルトでは「セッションとリトライ」が開きます。

**セクションの概要**

| セクション | 役割 | セクション内のタブ |
| --- | --- | --- |
| [セッションとリトライ](#セッションとリトライ) | セッション維持、セッションルール、リトライ予算。 | — |
| [チャネルの健全性](#チャネルのヘルス) | 定期的なチャネルテスト、自動無効化、自動復旧。 | — |

<Callout type="info" title="ヒント">

- リトライが機能しない、チャネルが自動無効化された、無効化されたチャネルが復旧しない、またはキャッシュエントリ数が 0 のままの場合は、[よくある質問](#よくある質問)を参照してください。

## 設定セクション

各セクションに専用の保存ボタンがあり、個別に送信できます。書き込み先は共通のリクエストポリシー設定です。検証と書き込みのルールは[保存と適用](#保存と反映)を参照してください。

### セッションとリトライ

- リクエストポリシー - セッションとリトライ

![リクエストポリシーの「セッションとリトライ」セクション](/assets/guide/feature-guide/system-settings-request-policy-session-and-retry.png)

このセクションは「セッションのデフォルト設定」「セッションルール」「リトライ予算」の 3 つのカードで構成されます。ページヘッダーの「変更を保存」ボタンを 1 回クリックすると、3 つのカードの変更がまとめて送信されます。スクリーンショットでは、デフォルトで折りたたまれている「セッションキャッシュ設定」を展開しています。下部バーの「キャッシュエントリ」が `0 / 0` と表示されているのは、撮影環境で Redis を使用しているためです。

**セッション維持の設定手順**

1. 「セッションのデフォルト設定」で「セッション維持を有効にする」がオンになっていることを確認します。新規ルールの「セッション維持」はデフォルトで「グローバルのデフォルトを継承」になるため、グローバルの「セッション維持」では「維持しない」を選ばないでください。ここでの変更は手順 3 でまとめて保存します。
2. 「ルールを追加」→「空のルール」をクリックし、「名前」「モデルの正規表現」と 1 つ以上の「キーの取得元」を入力して、ダイアログの「保存」をクリックします。各フィールドについては、後述の「ルールの追加または編集」を参照してください。新規ルールは表の末尾に追加されます。
   - ルールはリストの順に照合されます。先にあるルールと条件が重複すると、リクエストはそちらに先に一致します（後述の「照合ルール」を参照）。順序の変更が必要な場合は JSON モードで行います。ビジュアルモードでは順序を変更できません。
   - 「Codex CLI」「Claude CLI」の 2 つのテンプレートは、後述の 2 つの組み込みルールと同じです。組み込みルールを削除した場合に限り、テンプレートから追加し直す必要があります。
3. ページヘッダーの「変更を保存」をクリックします。「保存しました」と表示されたら送信は完了です。検証に失敗した場合のメッセージは[保存と適用](#保存と反映)を参照してください。

<Callout type="info" title="ヒント">

- 上記の手順で追加したルールでは、すべての条件を満たし、まだバインドされていないキー値を使うリクエストが成功した場合（HTTP ステータスコードが 400 未満）に、バインディングが書き込まれます。特定のチャネルに固定されたリクエストには、セッションルールが適用されません。
- ルール行の「キャッシュエントリ」列と下部バーの「キャッシュエントリ」は、リクエストに応じて自動更新されません。最新の値を確認するには、下部バーの「統計を更新」をクリックします。セッションルールを変更して保存した場合も、自動で更新されます。
- 後続のリクエストでこのバインディングが使われたかどうかは、[よくある質問](#よくある質問)の「チャネル ID の横に ✦ が表示された場合、セッションバインディングは有効ですか」を参照してください。

</Callout>

**セッションのデフォルト設定**

カードのサブタイトルは「ルールごとに継承または上書きできます。」です。「セッション維持を有効にする」をオフにすると、2 つのバインディング用スイッチがグレーアウトします。「セッション維持」のモードは引き続き変更できますが、メインスイッチを再度オンにするまで適用されません。「セッションキャッシュ設定」はデフォルトで折りたたまれており、展開すると 2 つのキャッシュ設定項目が表示されます。

**セッション維持モード**

| モード | ルールに一致したときの動作 |
| --- | --- |
| 維持しない | ルールの照合と、ルール内のパラメーター上書きテンプレートの適用は通常どおり行われます。セッションバインディングの読み書きは行わず、通常の方法でチャネルを選択します。 |
| 元のチャネルを優先し、失敗時は切り替えを許可 | 初回は、そのセッションにバインド済みのチャネルを優先します。失敗した場合は、通常のリトライ手順に従って別のチャネルに切り替えます。 |
| 元のチャネルを必ず使用 | バインディングがまだない場合は、通常の方法でチャネルを選び、リクエストの成功後にバインドします。ルールに一致したリクエストが失敗した場合は、セッションにチャネルがまだバインドされていなくてもリトライしません。バインド済みのチャネルが利用できない場合は、直ちに HTTP 503 を返します。エラーメッセージは `strict_session_binding_unavailable` です。 |

**セッションのデフォルト設定の項目**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 設定項目 | 定義 | 入力要件と制約 | デフォルト値 |
| --- | --- | --- | --- |
| セッション維持を有効にする | メインスイッチ。オフにすると、セッションルールの照合、セッションバインディングの読み書き、ルール内のパラメーター上書きテンプレートの適用が停止します。 | 真偽値 | オン |
| セッション維持（単一選択） | 「セッション維持を有効にする」の下にある 3 つの選択カードです。画面上に見出しはなく、本ドキュメントでは「セッション維持」と呼びます。グローバルのデフォルトモードで、「セッション維持」が「グローバルのデフォルトを継承」に設定されたルールにのみ適用されます。「元のチャネルを優先し、失敗時は切り替えを許可」の横には「キャッシュヒット率が低下します」と表示されます。 | 維持しない / 元のチャネルを優先し、失敗時は切り替えを許可 / 元のチャネルを必ず使用 | 空。「元のチャネルを優先し、失敗時は切り替えを許可」と表示 |

| チャネルを利用できない場合もセッションバインディングを保持 | オフの場合はバインディングをクリアします。オンの場合は、バインド済みのチャネルが無効化されたり、現在のグループとモデルに対応しなくなったりしても、バインディングを保持します。 | 真偽値。グレーアウトの条件は上と同じです。 | オフ |
| 最大キャッシュセッション数 | 折りたたみセクション「セッションキャッシュ設定」にある、メモリキャッシュの容量です。`0` を入力すると `100000` として扱われます。変更は再起動後に適用されます。Redis を使用する場合、この値は参照されません。 | 非負整数 | `100000` |
| デフォルトのセッション有効期間（秒） | 折りたたみセクション「セッションキャッシュ設定」にあります。ルールの TTL が `0` の場合に使用されます。`0` を入力すると `3600` として扱われます。 | 非負整数 | `3600` |

**セッションルール**

カードのサブタイトルは「セッションを識別し、使用するチャネルを維持する方法を定義します。」です。タイトルの横にルール数が表示されます。セッションルールでは、リクエストから同一セッションを識別する方法と、ルールに一致したときに、そのセッションで使用したチャネルを維持する方法を定義します。チャネルは通常の方法で選ばれた後にバインドされます。

セッションバインディング 1 件につき、キャッシュを 1 エントリ使用します。「キャッシュエントリ」は現在保存されているバインディングの数です。キャッシュをクリアするとバインディングが解除され、後続のリクエストではチャネルが選び直されます。

<Callout type="warn" title="注意">

ルールのダイアログにある「保存」は、ページ上のルールの下書きのみを更新します。ルールの追加、編集、削除、テンプレートの追加、JSON モードでの変更を行った後は、ページヘッダーの「変更を保存」をクリックして送信してください。ページを離れる際に未保存の変更についての警告は表示されず、送信していない変更は失われます。

</Callout>

**カードの構成**

1. ルールは「ビジュアル」と「JSON」の 2 つのモードで編集できます。JSON モードでは「テンプレートを追加」と「ルールを追加」は利用できません。編集欄の下に「ビジュアルモードに切り替えると、ルールやテンプレートを追加できます。」と表示されます。JSON が配列でない場合や形式が不正な場合は、ビジュアルモードに戻せません。「ルールの JSON は配列である必要があります」または「ルールの JSON 形式が正しくありません」と表示されます。
2. ルールがない場合は「ルールがありません」「CLI テンプレートまたは空のルールを追加してください。」と表示され、「テンプレートを追加」ボタンが表示されます。
3. カード下部のバーには、「キャッシュエントリ」が「使用数 / 容量」の形式で表示されます。取得に失敗した場合は「表示できません」と表示されます。Redis を使用している場合、容量は `0` と表示されます。バーの右側には「統計を更新」と「すべてのキャッシュをクリア」があり、その下に「統計を更新すると、エントリ数が更新されます。キャッシュをクリアすると、後続のリクエストはチャネルを選び直します。」と表示されます。

**組み込みルール**

デフォルトでは 2 つの組み込みルールがあり、どちらにもリクエストヘッダーをそのまま転送するためのパラメーター上書きテンプレートが付属しています。

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| ルール名 | モデルの正規表現 | パスの正規表現 | キーの取得元 | セッション維持 |
| --- | --- | --- | --- | --- |
| `codex cli trace` | `^gpt-.*$` | `/v1/responses` | `gjson`：`prompt_cache_key` | 元のチャネルを必ず使用（ルール個別の設定） |
| `claude cli trace` | `^claude-.*$` | `/v1/messages` | `gjson`：`metadata.user_id` | 元のチャネルを必ず使用（ルール個別の設定） |

</div>

<Callout type="warn" title="注意">

2 つの組み込みルールと、「テンプレートを追加」または「ルールを追加 → Codex CLI / Claude CLI」から作成したルールのデフォルトは「元のチャネルを必ず使用」です。該当するルールに一致したリクエストが失敗してもリトライは行われません。

失敗時にチャネルを切り替えるには、ルールを編集し、「セッション維持」を「元のチャネルを優先し、失敗時は切り替えを許可」に変更します。「グローバルのデフォルトを継承」に変更する場合は、グローバルモードが「元のチャネルを必ず使用」以外であることを確認してください。ダイアログの「保存」をクリックしてから、ページヘッダーの「変更を保存」をクリックします。

</Callout>

**ルールの追加または編集**

「ルールを追加」をクリックして「空のルール」「Codex CLI」「Claude CLI」のいずれかを選ぶか、ルール行の編集ボタンをクリックすると、ルールのダイアログが開きます。ダイアログのタイトルは「ルールを追加」または「ルールを編集」で、下部に「キャンセル」と「保存」があります。次の画像は、空のルールで「詳細設定」を展開した状態です。入力欄の灰色のテキストはプレースホルダーとして表示される入力例です。TTL の `0`、「セッション維持」のドロップダウン、キーの取得元の種類 `gjson`、3 つの「…を含める」スイッチには、実際のデフォルト値が表示されています。後述の基本パラメーター、詳細設定、キャッシュキーの各設定表の「デフォルト値」列には、空のルールの初期値を記載しています。

**照合ルール**

1. ルールはリストの順に 1 件ずつチェックされます。以下の条件をすべて満たしたルールが適用されます。そのセッションにまだバインディングがなくても、後続のルールはチェックされません。
   1. モデル、パス、User-Agent の条件がすべて一致する。
   2. 空でないキー値を取得でき、その値が「値の正規表現」による検証に合格する。
2. キーの取得元が複数ある場合は、最初に取得できた空でない値のみを使用します。その値が「値の正規表現」による検証に失敗すると、そのルール全体をスキップします。同じルールの後続の取得元は試しません。
3. モデルの正規表現が空のルールは、表に「すべてのモデル」と表示されていても、どのリクエストにも一致しません。ダイアログでは 1 行以上の入力が必須のため、このようなルールを書き込めるのは JSON モードのみです。
4. セッション維持モードが設定されていないルール（2 つの組み込みルールや、旧バージョンから引き継いだルールなど）では、旧フィールド `skip_retry_on_failure` が `true` なら「元のチャネルを必ず使用」、それ以外なら「元のチャネルを優先し、失敗時は切り替えを許可」と表示されます。設定元は「ルール個別の設定」です。ダイアログを開くと同じモードが選択されており、保存するとモードが明示的に書き込まれます。
5. ダイアログの「キャンセル」をクリックすると、今回の編集内容を破棄します。「保存」は下書きのみを更新します。「セッションルール」の注意事項を参照してください。
6. 送信時にバックエンドが全ルールのモデル、パス、値の正規表現をコンパイルします。いずれかの正規表現が無効な場合は、保存操作全体が拒否され、`rule "<规则名>": error parsing regexp: …` のようなエラーが返ります。

**リトライ予算の設定項目**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 設定項目 | 定義 | 入力要件と制約 | デフォルト値 |
| --- | --- | --- | --- |
| 最大リトライ回数 | 初回の試行を除き、グループごとにカウントします（後述の「リトライルール」の項目 2 を参照）。デフォルトの `0` では、失敗後にリトライしません。 | `0–99` の整数（バックエンドの要件は `0` 以上のみ） | `0` |
| 自動リトライ対象のステータスコード | 2xx、504、524 は常に除外されます。プレースホルダーは「例：401、403、429、500-599」です。保存時に隣接する範囲が統合されます。詳しくは[保存と適用](#保存と反映)を参照してください。 | ステータスコードまたは両端を含む範囲をカンマで区切って入力します。指定できる値は `100–599` です。形式が無効な場合は「ステータスコードのルールが無効です」と表示されます。空欄の場合はステータスコードに基づくリトライを行いません。 | `100-199,300-399,401-407,409-499,500-503,505-523,525-599` |

</div>

**リトライルール**

1. 総試行回数は「最大リトライ回数」に 1 を加えた回数です。リトライのたびにチャネルを選び直し、優先度を 1 段階ずつ下げます。最低の優先度に達した後はその段階にとどまるため、同じチャネルが再び選ばれることがあります。初回の試行でセッションにバインド済みのチャネルを使った場合、最初のリトライは最高の優先度から開始します。
2. API キーのグループが `auto` で、「グループをまたいでリトライ」がオンの場合は、グループごとにリトライ回数が割り当てられます。現在のグループでリトライ回数を使い切ると次のグループに切り替わり、そのグループの最高の優先度から開始します。
3. 失敗するたびに、以下の順で判定します。いずれかに該当すればリトライを停止します。
   1. 「元のチャネルを必ず使用」のルールに一致している。
   2. リクエストが特定のチャネルに固定されている。
   3. エラーがリトライ不可とマークされている。
   4. リトライ回数を使い切っている。
   5. ステータスコードが 2xx、504、524 のいずれかであるか、アップストリームのレスポンスボディを解析できない。
   6. ステータスコードが「自動リトライ対象のステータスコード」に含まれていない。
4. 例外は 2 つあります。
   - チャネル関連のエラー（エラーコードが `channel:` で始まるもの。利用可能なキーがない、キーが無効、パラメーター上書き設定が無効、モデルマッピングに誤りがあるなど）の場合は、判定の 1、2 のみを確認し、該当しなければリトライします。総試行回数には引き続き「最大リトライ回数」の上限が適用されます。
   - ステータスコードが `100–599` の範囲外の場合は、判定の 1〜4 を確認し、いずれにも該当しなければリトライします。判定の 5、6 は行いません。
5. 非同期タスクの送信（動画生成など）では、組み込みルールに従ってリトライを判断します。このとき「自動リトライ対象のステータスコード」は参照されません。429、307、および 504 と 524 を除く 5xx はリトライします。2xx、400、408、504、524 はリトライしません。その他のステータスコードでは、ローカルで発生したエラーはリトライせず、アップストリームから返されたエラー（401、403、404 など）はリトライします。「最大リトライ回数」、チャネルの固定、「元のチャネルを必ず使用」は、非同期タスクにも適用されます。

### チャネルのヘルス

- リクエストポリシー—チャネルのヘルス

![リクエストポリシーのチャネルのヘルスセクション](/assets/guide/feature-guide/system-settings-request-policy-channel-health.png)

**ステータス表示**

1. 「設定元：グローバル設定。変更内容は保存すると反映されます。」と常に表示されます。
2. 「失敗時に無効化」がオンの場合は「グローバルの無効化ルールを適用するには、各チャネルでも『自動無効化』をオンにする必要があります。」と表示されます。オフの場合は「現在の設定では、どのチャネルも自動で無効化されません。」と表示されます。ここでいう「自動無効化」は、チャネル編集画面の「異常時に自動無効化」スイッチを指します。同じ編集画面の「ルーティングポリシー」セクションでは「自動ブロック」と表示されます。
3. 「成功後に再有効化」がオンで「定期チャネルテスト」がオフの場合は、「定期的な復旧処理は実行されていません。一括テストで自動無効化されたチャネルを復旧できます。」とも表示されます。

**チャネルのヘルスチェック**

「チャネルテストモード」と「テスト間隔（分）」は「定期チャネルテスト」の配下にあります。このスイッチがオフでも両項目はグレーアウトされず、変更して保存できます。この場合、定期テストは実行されません。「チャネルテストの同時実行数」と「成功後に再有効化」はこのスイッチの影響を受けず、チャネル管理ページの「すべてのチャネルをテスト」にも適用されます。

**チャネルテストモードの説明**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| モード | テスト範囲 | 無効化可能 | 復旧可能 |
| --- | --- | --- | --- |
| すべてのチャネルを能動的にチェック | 手動で無効化されたチャネルを除くすべてのチャネルをチェックします。障害を能動的に検出し、チャネルを自動で復旧するために使用します。 | はい | はい |
| 自動無効化がオンのチャネルを能動的にチェック | 「異常時に自動無効化」がオンのチャネルのみをチェックします。このオプションがオフのチャネルや、手動で無効化されたチャネルは対象外です。 | はい | はい |
| 自動無効化されたチャネルのみをチェック | システムによって自動無効化されたチャネルのみを再チェックし、復旧を確認したら再有効化します。正常なチャネルは対象外です。 | いいえ | はい |

</div>

</Callout>

**自動無効化が発動する条件**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| シナリオ | 判定基準 | 説明 |
| --- | --- | --- |
| 実際のリクエストが失敗した場合 | チャネル関連のエラー、「自動無効化ステータスコード」、「失敗キーワード」 | 所要時間は判定に使用しません。リトライ不可とマークされたエラーは無効化の対象外です。ただし、チャネル関連のエラーは対象になります。 |
| 定期テストまたは「すべてのチャネルをテスト」 | 上記に加え、「ヘルスチェックの所要時間しきい値（秒）」との比較 | 「自動無効化されたチャネルのみをチェック」モードでは、チャネルを無効化しません。 |
| 個別チャネルのテスト | — | チャネルの無効化も復旧も行いません。 |

1. 上記のシナリオで自動無効化が発動するには、グローバルの「失敗時に無効化」とチャネルの「異常時に自動無効化」の両方がオンである必要があります。
2. 複数の Key を持つチャネルでは、エラーが発生した Key だけが無効化されます。すべての Key が無効化されると、チャネル全体が自動無効化の状態になります。

**自動復旧と通知**

1. 自動復旧には、「成功後に再有効化」がオンで、チャネルが自動無効化されており、定期テストまたは「すべてのチャネルをテスト」でテストに成功する必要があります。グローバルの「失敗時に無効化」がオンの場合は、テストの所要時間が「ヘルスチェックの所要時間しきい値（秒）」以下であることも必要です。個別チャネルのテストでは復旧しません。手動で無効化されたチャネルも復旧の対象外です。
2. 自動無効化と自動復旧のどちらでも通知を送信します。受信者は「チャネル通知」をオンにしている有効な管理者（Admin と Root）です。このスイッチを一度も設定していない場合、デフォルトでは Root のみが受信します。各管理者は<a href="/ja/docs/guide/feature-guide/user/personal-setting#通知と動作を設定する" target="_blank" rel="noopener noreferrer">プロフィール</a>で「チャネル通知」のオン・オフを切り替えられます。
3. 同一チャネルの同一状態に関する通知は、管理者ごとに送信頻度が制限されます。デフォルトでは 10 分間に最大 2 件です。件数は環境変数 `NOTIFY_LIMIT_COUNT`（デフォルトは `2`）、時間枠は `NOTIFICATION_LIMIT_DURATION_MINUTE`（単位は分、デフォルトは `10`、0 以下の場合は 10）で調整できます。このページに対応する設定項目はありません。

**実行条件**

1. 定期テストは Master インスタンスでのみ実行されます。`NODE_TYPE=slave` のノードでは実行されません。テストは設定した間隔でスケジュールされ、前回のテストが終了するまで次のテストは開始されません。
2. 環境変数はページの設定値を上書きします。`CHANNEL_TEST_FREQUENCY`（正の整数、単位は分）を設定すると、定期テストが強制的にオンになり、その値がテスト間隔に使用され、モードは「すべてのチャネルを能動的にチェック」に固定されます。`CHANNEL_TEST_ENABLED`（ブール値）を設定すると、「定期チャネルテスト」スイッチの状態を強制的に指定できます。`CHANNEL_TEST_ENABLED` は `CHANNEL_TEST_FREQUENCY` の後に適用されるため、`false` にすると定期テストはオフになります。
3. これらの変数を設定した後も、ページ上の定期テスト関連の 3 項目は変更して保存できます。実際の動作には環境変数の値が適用されます。どちらの変数も起動時にのみ読み込まれるため、変更後は New API を再起動してください。

## リクエストの判定記録

リクエストポリシーは、問題の調査に使えるよう、リクエストごとのルーティングとリトライの判定を記録します。

- **表示場所**は、<a href="/ja/docs/guide/feature-guide/user/log#リクエストポリシーの判定" target="_blank" rel="noopener noreferrer">利用ログ</a>の各エントリにある「詳細」→「リクエストポリシーの判定」です。Admin と Root のみが閲覧でき、ページ右上で「すべて」を選択した場合にだけ表示されます。
- **記録内容**には、選択されたチャネル、マッチしたセッションルール、失敗の理由、リトライまたは停止の判定とその根拠となった設定のほか、所要時間、グループ、ステータスコード、チャネルのヘルスに関する処理がステップごとに表示されます。
- 成功したリクエストの判定記録は、消費ログとともに書き込まれます。<a href="/ja/docs/guide/feature-guide/system-settings/settings-operations#ログのメンテナンス" target="_blank" rel="noopener noreferrer">運用設定</a>の「クォータ使用量を記録」（デフォルトでオン）を有効にする必要があります。
- 失敗した試行の判定記録は、環境変数 `ERROR_LOG_ENABLED=true` が設定されている場合に限り、エラーログとともに書き込まれます。デフォルトは `false` です。このページに対応する設定項目はなく、変更後は New API の再起動が必要です。リクエストが最終的に失敗した場合も、集約した記録は別途書き込まれません。
- 「元のチャネルを必ず使用」にマッチしたものの、紐付け先のチャネルが利用できず、HTTP 503 を直接返すリクエストには判定記録が残りません。

## 保存と反映

保存方法は<a href="/ja/docs/guide/feature-guide/system-settings/system-setting#保存方法" target="_blank" rel="noopener noreferrer">システム設定の概要</a>を、設定の反映と複数インスタンス間の同期ルールは<a href="/ja/docs/guide/feature-guide/system-settings/system-setting#反映範囲と複数インスタンス間の同期" target="_blank" rel="noopener noreferrer">反映範囲と複数インスタンス間の同期</a>を参照してください。特に記載がない限り、保存リクエストを処理したノードでは保存後すぐに新しい値が適用されます。他のノードにはシステム設定の同期によって約 3 秒以内、遅くとも 1 同期周期（デフォルトは 60 秒）以内に反映されます。同期周期は環境変数 `SYNC_FREQUENCY` で秒単位で調整できます。このページで説明する環境変数はすべて起動時にのみ読み込まれるため、変更後は New API を再起動してください。各設定項目が新しい値を読み込むタイミングは以下のとおりです。

**リトライとセッション維持**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 設定項目 | 保存方法 | 反映タイミング |
| --- | --- | --- |
| 最大リトライ回数、自動リトライステータスコード | ページ上部の「変更を保存」で 3 枚のカードを一括保存 | リクエストが失敗するたびに、リトライするかどうかの判定時に新しい値を読み込みます。 |
| セッション維持のスイッチ、モード、セッションルール | ページ上部の「変更を保存」 | 次にリクエストをルールと照合するときから反映されます。保存済みのセッションの紐付けは、期限切れになるか消去されるまで保持されます。 |
| デフォルトのセッション有効期間（秒） | ページ上部の「変更を保存」 | 以後、新しく書き込まれる紐付けに適用されます。 |
| キャッシュするセッションの最大数 | ページ上部の「変更を保存」 | メモリキャッシュの容量を変更するには、サービスを再起動する必要があります。Redis の使用時は適用されません。 |
| すべてのキャッシュをクリア、個別ルールのキャッシュをクリア | 確認後に即時実行。保存ボタンの操作は不要 | 確認直後に、該当するセッションの紐付けが解除されます。Redis を有効にしていない複数インスタンス構成では、そのリクエストを処理したノードのキャッシュにのみ適用されます。 |

</div>

**チャネルテストと自動無効化**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 設定項目 | 保存方法 | 反映タイミング |
| --- | --- | --- |
| 定期チャネルテスト | ページ上部の「変更を保存」で一括保存 | Master インスタンスは約 15 秒ごとに実行条件を確認します。有効化後、前回のテスト終了から設定した間隔を超えていれば、次の確認時にテストを開始します。実行中のテストは中断されません。 |
| テスト間隔（分） | ページ上部の「変更を保存」で一括保存 | 次の実行条件の確認から新しい値で判定します。 |
| チャネルテストモード、チャネルテストの同時実行数 | ページ上部の「変更を保存」 | 次回のテスト開始時に読み込みます。実行中のテストには開始時の設定が適用されます。 |
| 失敗時に無効化、自動無効化ステータスコード、失敗キーワード | ページ上部の「変更を保存」 | 次回のリクエスト失敗時またはチャネルテストの判定時に読み込みます。 |
| ヘルスチェックの所要時間しきい値（秒）、成功後に再有効化 | ページ上部の「変更を保存」 | 次回の定期または一括チャネルテスト時に読み込みます。 |

</div>

**補足**

- **一括保存**。送信されるのは、このセクションで変更された項目のみです。バックエンドは、送信された項目をリクエストポリシー全体にマージして検証し、1 つのトランザクションで書き込みます。成功すると「保存しました」と表示されます。無効な項目が 1 つでもあると、その送信に含まれる項目はすべて書き込まれません。「セキュリティと制限」などの設定領域では項目ごとに保存されます。
- **変更がない場合**。「保存する変更がありません」と表示されます。
- **検証失敗時の表示**。ほとんどのフィールドはまずフロントエンドで検証され、無効な値があると送信されません。バックエンドでの検証に失敗すると、バックエンドが返した英語の原文がポップアップに表示されます。これは主にルールの正規表現や JSON スキーマを変更したときに発生します。「セッションとリトライ」では、カードの下にもエラーが赤字で表示されます。このセクションで変更した設定に無効な値があると、下部に「無効な設定を修正してから保存してください。」と表示されます。
- **範囲の結合**。「自動リトライステータスコード」または「自動無効化ステータスコード」を変更して保存すると、フロントエンドが隣接する範囲を結合してから送信します。たとえば、`409-499,500-503` は `409-503` に結合されます。対象となるステータスコードは同じです。
- **競合検出と未保存の変更に関する警告**。リクエストポリシーではバージョンの競合を検出しないため、複数人が同時に編集した場合は、後から保存した内容が先に保存した内容を上書きします。ページから移動する際にも警告は表示されず、未保存の変更は失われます。

## 注意事項

- **組み込み CLI ルールにマッチしたリクエストは失敗してもリトライされません**。2 つの組み込みルールとテンプレートから生成されたルールでは、デフォルトで「元のチャネルを必ず使用」が設定されています。[セッションとリトライ](#セッションとリトライ)を参照してください。
- **リトライのたびにチャネルを選択し直します**。すべての優先度を試した後は、同じチャネルが再び選ばれる場合があります。「最大リトライ回数」のデフォルトは `0` で、リトライは行われません。[セッションとリトライ](#セッションとリトライ)を参照してください。
- **「すべてのチャネルをテスト」は実際にチャネルを無効化または復旧します**。手動で無効化されたチャネルを除くすべてのチャネルをテストし、[チャネルのヘルス](#チャネルのヘルス)のルールに従って自動で無効化または復旧します。
- **環境変数は定期テストの設定を上書きします**。`CHANNEL_TEST_FREQUENCY` または `CHANNEL_TEST_ENABLED` が設定されている場合、ページ上の定期テスト設定が反映されないことがあります。[チャネルのヘルス](#チャネルのヘルス)を参照してください。
- **失敗した試行の判定を記録するには環境変数の設定が必要です**。`ERROR_LOG_ENABLED=true` が設定されている場合にのみ書き込まれます。[リクエストの判定記録](#リクエストの判定記録)を参照してください。

<Accordion title="リトライが行われない">

**対処方法**。以下の順に確認してください。

1. 「最大リトライ回数」がデフォルト値の `0` のままになっていないか。
2. 失敗時のステータスコードが「自動リトライステータスコード」に含まれているか。
3. リクエストが、2 つの組み込み CLI ルールを含め、「元のチャネルを必ず使用」のルールにマッチしていないか。
4. リクエストが特定のチャネルに固定されていないか。
5. 2xx、504、524 など、常にリトライの対象外となるケースに該当していないか。
6. 利用可能なチャネルが 1 つしかないか、最低優先度のチャネルが同じ 1 つのチャネルだけではないか。この場合もリトライは実行されますが、同じチャネルが再び選ばれ、リトライされていないように見えることがあります。
</Accordion>

<Accordion title="組み込み CLI ルールにマッチしたリクエストが失敗してもリトライされない">

**説明**。`gpt-*` モデルの `/v1/responses` リクエスト本文に `prompt_cache_key` が含まれる場合、または `claude-*` モデルの `/v1/messages` リクエスト本文に `metadata.user_id` が含まれる場合は、対応する組み込み CLI ルールにマッチします。

**考えられる原因**。この 2 つのルールでは、デフォルトで「元のチャネルを必ず使用」が設定されています。ルールにマッチすると、チャネルへの紐付けがまだない場合でもリトライされません。

**対処方法**

1. 2 つのルールの「セッション維持」を「元のチャネルを優先し、失敗時は切り替えを許可」に変更します。「グローバルのデフォルト設定を継承」に変更する場合は、グローバルモードが「元のチャネルを必ず使用」以外に設定されていることを確認してください。
2. ダイアログで「保存」をクリックします。
3. ページ上部の「変更を保存」をクリックします。
</Accordion>

<Accordion title="チャネルが自動で無効化された">

**説明**。所要時間のしきい値との比較は、定期テストと「すべてのチャネルをテスト」でのみ行われます。

**考えられる原因**。グローバルの「失敗時に無効化」、チャネルの「異常時に自動無効化」、「自動無効化ステータスコード」、または「失敗キーワード」が想定どおりに設定されていません。
</Accordion>

<Accordion title="チャネルが自動で復旧しない">

**説明**。個別チャネルのテストでは復旧しません。手動で無効化されたチャネルも復旧の対象外です。

**考えられる原因**。グローバルの「失敗時に無効化」がオンで、テストの所要時間が「ヘルスチェックの所要時間しきい値（秒）」を超えています。

**対処方法**

1. 「成功後に再有効化」をオンにします。
2. 定期テストまたは「すべてのチャネルをテスト」で対象チャネルのテストが成功したことを確認します。
</Accordion>

<Accordion title="定期テストの間隔がページの設定と一致しない">

**説明**。`NODE_TYPE=slave` のノードでは定期テストが実行されません。

**考えられる原因**。デプロイ環境に `CHANNEL_TEST_FREQUENCY` または `CHANNEL_TEST_ENABLED` が設定されており、ページ上の設定値が上書きされています。
</Accordion>

<Accordion title="「キャッシュをクリア」ボタンが使えない、またはキャッシュエントリが「該当なし」と表示される">

**考えられる原因**

- そのルールで「ルール名を含める」がオンになっていません。
- キャッシュ統計の取得に失敗しました。
- ページ上部の「変更を保存」でルールをまだ保存していません。
</Accordion>

<Accordion title="キャッシュエントリ数が 0 のまま変わらない">

**説明**。Redis を使用している場合、容量が `0` と表示されるのは正常です。

**対処方法**。使用中のエントリ数が 0 のままの場合は、以下の順に確認してください。

1. リクエスト送信後に「統計を更新」をクリックしたか。キャッシュ統計は自動では更新されません。
2. ページ上部の「変更を保存」でルールを送信したか。ダイアログの「保存」では下書きだけが更新されます。
3. 「セッション維持を有効化」がオンか、ルールに実際に適用されるモードが「維持しない」になっていないか。
4. リクエストがルールのすべての条件を満たしているか。空でない Key が取得でき、Value が正規表現にマッチしていることも確認してください。
5. 一覧の先頭に近い別のルールに先にマッチしていないか。実際にマッチしたルール名は、「リクエストポリシーの判定」の「マッチしたセッションルール」ステップで確認できます。
6. リクエストが失敗していないか。失敗したリクエストの紐付けは書き込まれません。
7. リクエストが特定のチャネルに固定されていないか。固定されたリクエストにはセッションルールが適用されません。
</Accordion>

<Accordion title="保存時に英語のエラーが表示される">

**説明**。バックエンドの検証で返されたエラーの原文です。今回の送信に含まれる項目はすべて書き込まれていません。

**対処方法**

1. 設定を修正してから、再度保存します。
</Accordion>

<Accordion title="利用ログに失敗したリクエストの判定記録が表示されない">

**対処方法**

1. 環境変数 `ERROR_LOG_ENABLED=true` を設定します。
</Accordion>

<Accordion title="チャネル ID の横に ✦ が表示されたら、セッションの紐付けは有効になっているか">

**説明**。利用ログでチャネル ID の右上にある琥珀色の ✦ は、リクエストがセッションルールに関連付けられていることを示します。カーソルを合わせるとルール名とグループを確認できます。紐付けが有効になっているかどうかは、✦ の表示だけでは判断できません。

- ルールにパラメーター上書きテンプレートがない場合、初回の試行で既存の紐付けを使用したときにのみ ✦ が表示されます。新しい Key を使う最初のリクエストには表示されず、2 件目以降に表示されます。

**対処方法**

1. カード下部の「統計を更新」をクリックし、該当ルールの行で「キャッシュエントリ」列の値が増えたかを確認します。
2. 同じ Key で再度リクエストを送信し、利用ログの 2 件の記録でチャネル ID が同じかどうかを確認します。
</Accordion>

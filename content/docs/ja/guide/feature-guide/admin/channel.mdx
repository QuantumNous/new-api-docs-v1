- Admin と Root のみアクセスできます。サイドバーの「管理者」→「チャネル」から開きます。
- アップストリームの AI サービスに接続するチャネルを設定し、認証情報、モデル、グループ、ルーティングポリシー、リクエストの書き換えルールを管理します。
- チャネルはリクエストの送信先を決定します。モデル情報、料金、ユーザーグループは別のページで設定します。

<Callout type="info" title="ヒント">

- チャネルには組み込み、プラグイン、ゲートウェイ、カスタムの 4 種類があります。作成時に選択ダイアログで種類を選びます。詳しくは[チャネルの作成と編集](#チャネルの作成と編集)を参照してください。
- Admin が実行できるチャネル操作は、Root が管理者権限の設定で付与します。詳しくは[権限とセキュリティ上の境界](#権限とセキュリティ境界)を参照してください。
- モデルカタログ、料金、ユーザーグループは、<a href="/ja/docs/guide/feature-guide/admin/model" target="_blank" rel="noopener noreferrer">モデル管理</a>、<a href="/ja/docs/guide/feature-guide/system-settings/settings-billing" target="_blank" rel="noopener noreferrer">課金と支払いの設定</a>、<a href="/ja/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">ユーザー管理</a>とあわせて設定します。
- すべてのチャネルに適用するリクエストの書き換えは、<a href="/ja/docs/guide/feature-guide/admin/request-processing" target="_blank" rel="noopener noreferrer">リクエスト処理</a>ページで設定します。
</Callout>

## よく使う操作

このセクションでは、チャネルの作成と編集、プラグイン・ゲートウェイ・高度なカスタムの 3 種類の特殊なチャネル、テスト、残高確認、モデルの更新、複製、有効化・無効化・削除、タグ、優先度、複数キー、整合性の修復などのメンテナンス操作を、利用する順に説明します。

### チャネルの作成と編集

**操作手順**

1. ページ右上の「チャネルを作成」をクリックします。編集する場合は、行内の編集アイコンをクリックするか、カードの ⋯ メニューで「編集」をクリックします。
2. 選択ダイアログでプロバイダーまたはプラグインを選びます。
3. 必要に応じて、ドロワー上部のクイック設定を有効にします。
4. 「接続とモデル」「ルーティングとマッピング」「リクエストとレスポンス」「その他の設定」の 4 つのタブを順に設定します。
5. 「チャネルを作成」または「チャネルを更新」をクリックします。

<Callout type="info" title="ヒント">

- ドロワーのタイトル下にある「プロバイダーを変更」から、タイプやプラグインを選び直せます。
- 各タブの横には、「未完了」「エラー」「準備完了」「設定済み」のいずれかを示すステータスドットが表示されます。
- アカウントに「機密性の高いチャネル設定を編集」権限がない場合、ドロワー上部に「このアカウントでは、機密性の高いチャネル設定は閲覧のみ可能です。モデル、グループ、優先度、重みなど、機密性のない運用項目は引き続き編集できます。」と表示されます。
- 保存時には、まずページ上でフォームを検証し、その後サーバー側でチャネルのタイプ、認証情報、プラグインの紐付け、高度な設定を確認します。
</Callout>

<Callout type="info" title="ヒント">

- 「プラグイン」カテゴリは、アカウントに「タスクプラグインを紐付け」権限がある場合にのみ表示されます。プラグイン一覧の読み込みに失敗した場合は「プラグインの読み込みに失敗しました」というメッセージと再試行ボタンが表示され、紐付け可能なプラグインがない場合は「紐付け可能なプラグインはありません」と表示されます。
- 検索ボックスでは名前、プラグイン、タイプ番号で検索できます。一覧にない番号を入力すると「チャネルタイプ … を使用」カードが表示されます。アダプターが利用できるのは、対応する番号に限られます。
- インストール済みのプラグインが一部の旧組み込みタイプ（Sora、可灵、即梦など）を置き換えている場合、作成時にはプラグインのカードのみが表示されます。旧タイプ名や番号で検索しても、そのプラグインが見つかります。
</Callout>

**4 種類のチャネルの選び方**

- **標準的なプロバイダーやプロトコル**は組み込みチャネルを選び、そのタイプ専用の認証情報を使用し、デフォルトのアドレスの案内に従います。
- **インストール済みのプラグイン**は「プラグイン」を選び、モデル、アップストリームのタイプ、デフォルトのアドレスを確認してから、プラグインに必要な認証情報を設定します。
- **New API/Sub2API のアップストリームゲートウェイ**は「ゲートウェイ」を選び、専用のゲートウェイアダプターを使用します。カスタム（#8）での代用は避けてください。
- **複数の受信パス、プロトコル、プロバイダーを扱う場合**は高度なカスタムを選びます。受信パス、アップストリームのパス、認証、コンバーターを事前に設計する必要があります。

ドロワーのタイトル行の右側にあるスイッチは、各タブの同名の設定と連動します。表示される項目はタイプによって異なります。

**接続情報を貼り付ける手順**

1. 別の New API サイトで、API キーの ⋯ メニューから「接続情報をコピー」をクリックします。
2. このサイトでチャネルを作成するときに、ドロワー右上の「接続情報を貼り付け」をクリックします。

<Callout type="info" title="ヒント">

- 接続情報が認識されると「API キー」と「API アドレス」が自動で入力され、「接続情報を入力しました」と表示されます。
- ドロワーを開いたときにクリップボードに接続情報がある場合、上部に「クリップボードに接続情報が見つかりました」と表示されます。「入力」または「無視」をクリックできます。
- クリップボードに認識できる内容がない場合は、「クリップボードに接続情報が見つかりませんでした」と表示されます。
</Callout>

### 独立プラグインチャネル

- チャネル管理 - プラグインチャネル

![チャネル管理 - プラグインチャネル画面](/assets/guide/feature-guide/create-channel-plugin-channel.png)

チャネル機能を備えたプラグインのチャネルでは、接続テスト、モデルの取得、アップストリームのモデル更新の検出ができます。プラグインが残高情報を提供する場合は、残高も照会できます。プラグインのモデルは、プラグインが定義した初期値であり、アップストリームの認証情報が有効であることを示すものではありません。対応するモデル、ルート、リクエストの種類は、インストールされているバージョンによって異なる場合があります。

`/v1/images/generations`、`/v1/images/edits`、`/v1/responses`、`/v1/videos` などの共通エンドポイントでは、同じモデルを扱う通常チャネルとプラグインチャネルが、グループ、優先度、重みに基づいて同じ選択処理の対象となります。通常チャネルが選ばれた場合、リクエストはプラグインを経由せず、そのチャネルを通じて転送されます。

**前提条件**

- 選択ウィンドウに「プラグイン」カテゴリが表示されるのは、アカウントに「タスクプラグインを紐付ける」権限がある場合のみです。
- 対象のプラグインがインストールされ、有効になっている必要があります。<a href="/ja/docs/guide/feature-guide/admin/task-plugins#プラグインチャネルの作成" target="_blank" rel="noopener noreferrer">プラグイン管理</a>を参照してください。

**操作手順**

1. 「プラグイン」カテゴリで登録済みのプラグインを選択します。
2. プラグインに必要な認証情報、グループ、その他の項目を入力します。「API キー」の下に表示される「キーの形式」の案内は、プラグインが提供します。
3. プラグインに設定項目が定義されている場合は、「プラグイン設定」セクションに入力します。
4. 「チャネルを作成」をクリックします。アップストリームのアカウントへのログインが必要なプラグインでは、ボタンのラベルは「保存してログイン」になります。
5. 保存後にログインウィンドウが自動で開きます。画面の案内に従ってログインを完了します。

<Callout type="info" title="ヒント">

- プラグインを選択すると、名前が空欄の場合はプラグイン名が入力されます。プラグインが定義したモデルとデフォルトのアドレスも自動入力されます。
- プラグインにデフォルトのアドレスがある場合は、「API アドレス」の下に「プラグインのデフォルト値：…」と「デフォルト値を使用」が表示されます。デフォルトのアドレスがない場合は入力が必須です。
- 「プラグイン設定」で変更していない項目には保存済みの値が保持され、空欄にした項目にはプラグインのデフォルト値が使用されます。入力チェックに失敗すると、「強調表示された項目を修正してから保存してください」と表示されます。
- チャネルの編集中にプラグインを変更した場合は、保存してからログインしてください。

</Callout>

**認証情報**

アップストリームのアカウントへのログインが必要なプラグインでは、「接続とモデル」の「API キー」が「認証情報」セクションに切り替わります。

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| 状況 | 「認証情報」セクションの表示 | 次の操作 |
| --- | --- | --- |
| 作成時 | 「このチャネルはプロバイダーのアカウントでログインします。チャネルを保存するとログインできます。」 | 「保存してログイン」をクリックします。 |
| 保存済み、未ログイン | 「未ログイン」「ログインすると、このチャネルを使用できます。」 | 「ログイン」をクリックします。 |
| ログイン済み | アカウント名（またはアカウント ID）、「… に有効期限切れ」 | 「アカウントを追加」をクリックしてアカウントを追加できます。追加すると複数キーチャネルになり、「キーを管理」をクリックできるようになります。単一キーチャネルでは「アカウントを切り替え」も使用できます。各アカウントの行に「再ログイン」があります。 |
| 認証情報が無効 | 「ログインが必要」 | 「再ログイン」をクリックします。 |

</div>

<Callout type="info" title="ヒント">

- ログインウィンドウのタイトルは「ログイン …」または「再ログイン …」です。手順はプラグインによって異なり、ログインページへの移動、コールバック URL の貼り付け、デバイスコードの入力、フォームへの入力などがあります。
- ログインに成功すると「ログイン済み」、失敗すると「ログインに失敗しました」と「再試行」が表示されます。デバイスコードの有効期限が切れると、「確認コードの有効期限が切れました」と「最初からやり直す」が表示されます。

</Callout>

### ゲートウェイチャネル：New API と Sub2API

- チャネル管理 - New API ゲートウェイチャネル

![チャネル管理 - New API ゲートウェイチャネル画面](/assets/guide/feature-guide/create-channel-newapi-gateway-channel.png)

New API と Sub2API は、ゲートウェイの Base URL にリクエストパスを連結します。通常の設定では `/v1` が自動補完されないため、Base URL の末尾に `/v1` を付けないでください。どちらも OpenAI、Responses、Claude、Gemini などのゲートウェイ機能を提供できます。対応範囲は実際のゲートウェイのデプロイ構成によって異なります。

New API では、「アップストリームのタスクプラグイン」で、アップストリームの New API に対応したタスクプラグイン拡張も紐付けられます。画面には「このチャネルでは、選択した各プラグインのモデルが利用可能になります。アップストリームの New API ゲートウェイにも同じプラグインをインストールする必要があります。」と表示されます。拡張を紐付けても、チャネルの種類は New API ゲートウェイチャネル（#60）のままです。[独立プラグインチャネル](#独立プラグインチャネル)とは区別してください。

<Callout type="info" title="ヒント">

- 「アップストリームのタスクプラグイン」は、「タスクプラグインを紐付ける」権限を持つアカウントにのみ表示されます。
- 拡張の紐付けや解除、拡張付きチャネルの複製には、「タスクプラグインを紐付ける」権限が必要です。紐付け対象に変更がなければ、この権限がなくても保存できます。
- 別の New API サイトから接続情報をコピーして、ワンクリックで入力できます。[チャネルの作成と編集](#チャネルの作成と編集)を参照してください。

</Callout>

### 高度なカスタムチャネル

- チャネル管理 - 高度なカスタムチャネル

![チャネル管理 - 高度なカスタムチャネル画面](/assets/guide/feature-guide/create-channel-advanced-custom-channel.png)

高度なカスタムチャネルを選択した場合は、有効なルートを少なくとも 1 件残す必要があります。

**操作手順**

1. 「接続とモデル」の「高度なカスタムルーティング」で「ルートを設定」をクリックします。
2. 「ルート転送」で「ルートを追加」または「テンプレートを追加」をクリックし、下の表に従って各ルートを設定します。
3. 必要に応じて、「モデル一覧」と「残高照会」に管理用ルートをそれぞれ 1 件追加します。
4. 「変更を保存」をクリックし、チャネルを保存します。

<Callout type="info" title="ヒント">

- 同じエンドポイントへのリクエストは、クライアントが指定する `model` に基づいて振り分けられます。最後のルートのモデルルールを空欄にして、フォールバックにします。順序が正しくない場合は「フォールバックは最後に配置してください」と表示されます。「順序を修正」をクリックすると修正できます。
- 「テンプレートを追加」で転送ルートを置き換える前に、「転送ルートを置き換えますか？」と確認されます。モデル一覧と残高照会のルートは保持されます。
- ルートの設定に誤りがあると、保存できないか、該当エンドポイントから転送できなくなります。

</Callout>

- チャネル管理 - 高度なカスタムルーティング

![チャネル管理 - 高度なカスタムルーティング画面](/assets/guide/feature-guide/create-channel-advanced-custom-channel-advanced-custom-routing.png)

**ルートの設定項目**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| ルートの項目 | 説明 |
| --- | --- |
| 受信パス | `/` で始まる必要があり、クエリ文字列は含められません。例は `/v1/chat/completions` です。ドロップダウンから DeepSeek Search（`/v1/tools/search`）と DeepSeek Fetch（`/v1/tools/fetch`）も選択できます。 |
| アップストリームパス | 完全な `http(s)` URL または相対パスを指定できます。相対パスはチャネルの Base URL を基準に解決されます。パスに `{model}` を使用できますが、管理用ルートでは使用できません。 |
| モデルルール | 空のリストは、そのエンドポイントのフォールバックルールになります。通常の名前は完全一致し、`re:` で始まるルールは正規表現として扱われます。個別のルールはフォールバックルールより前に配置してください。 |
| コンバーター | 受信側のプロトコルと一致している必要があります。ネイティブ転送には「ネイティブ転送」を使用します。ルート単位の「パススルー」はネイティブ転送ルートでのみ使用できます。チャネル単位の「リクエストボディをパススルー」はすべてのルートに適用され、有効にすると形式変換が必要なルートではリクエストを処理できなくなります。一部のルートだけでパススルーを使う場合は、ルート単位のスイッチを使用してください。 |
| 認証 | 「デフォルト Bearer」「認証なし」「リクエストヘッダー」「Query」のいずれかを選択します。「リクエストヘッダー」と「Query」には名前と値が必要です。値には `{api_key}` を使用できます。 |
| モデル一覧ルート | `/v1/models` を最大 1 件設定でき、ネイティブ転送を使用する必要があります。アップストリームのモデルチェックを有効にする場合は必須です。 |
| 残高照会ルート | `/v1/dashboard/billing/credit_grants` を最大 1 件設定できます。モデルルール、コンバーター、パススルー、`{model}` には対応していません。 |

</div>

<Callout type="warn" title="注意">
保存する前に、受信側とアップストリームのプロトコルが一致していること、認証情報が漏えいしないこと、相対パスを使用する場合は Base URL が設定されていることを確認してください。
</Callout>

### 接続テスト

- チャネル管理 - チャネルの接続テスト

![チャネル管理 - チャネルの接続テスト画面](/assets/guide/feature-guide/channel-management-test-channel-connection.png)

クイックテストでは、行内の「接続テスト」アイコンをクリックすると、チャネルのテストモデルを使ってリクエストを 1 回送信します。テストモデルが未設定の場合は、チャネルのモデル、デフォルトのテストモデルの順に使用します。詳細テストでは、テストウィンドウでエンドポイント、ストリーミングモード、モデルを選択します。

**操作手順**

1. ⋯ メニューで「接続テスト」をクリックします。カードビューでは「チャネルの接続テスト」アイコンも使用できます。
2. 「エンドポイントの種類」を選択します。「自動検出（デフォルト）」ではチャネルの種類に応じてデフォルトのエンドポイントが選択され、Codex でエンドポイントを指定しない場合は Responses が使用されます。プラグインチャネルには対応するエンドポイントのみが表示され、自動検出ではその先頭のエンドポイントが使用されます。
3. 必要に応じて「ストリーミングモード」を有効にします。Embeddings、画像生成、Rerank、Responses Compaction はストリーミングに対応していません。
4. 1 つ以上のモデルを選択し、テストを実行します。
5. 成否、応答時間、エラーの詳細を確認します。
6. テストに失敗したモデルを削除する前に、一時的なネットワーク障害、レート制限、プロキシ、エンドポイント、価格設定が原因でないことを確認します。

<Callout type="info" title="ヒント">

- 複数モデルのテストは、1 バッチにつき最大 5 モデルまで実行されます。「テストを停止」で停止するのは後続のバッチのみです。送信済みのリクエストがキャンセルされるとは限りません。
- 結果から「成功したモデルを選択（…）」または「失敗したモデルを削除（…）」を実行できます。価格未設定で失敗した場合は「設定へ」が表示され、モデルの価格設定画面に移動できます。
- 個別チャネルのテストでは結果のみが表示され、チャネルの状態は変更されません。

</Callout>

### 残高と稼働状況の照会

- チャネル管理 - 残高照会

![チャネル管理 - 残高照会画面](/assets/guide/feature-guide/channel-management-check-balance.png)

**操作手順**

1. 「使用済み / 残り」列の残高をクリックするか、⋯ メニューで「残高照会」をクリックします。
2. 「残高照会」ウィンドウで「残高を更新」をクリックします。

<Callout type="info" title="ヒント">

- 通常チャネルの残高照会では、チャネルの種類ごとに異なるアップストリームの API を呼び出します。残高照会に対応するのは一部の種類のみです。
- 組み込みタイプの複数キーチャネルは残高照会に対応していません。
- プラグインチャネルは、プラグインが残高情報を提供する場合のみ残高照会に対応します。未対応の場合は残高列に「-」が表示され、⋯ メニューに「残高照会」は表示されません。
- 複数キーのプラグインチャネルでは、キーごとに残高を照会します。「複数キーの管理」には「残高」列が表示されます。
- 照会に失敗すると、残高の横に警告アイコンが表示されます。機密データが表示されている場合は、マウスを合わせると「前回の更新日時：」と「前回のエラー：」を確認できます。
- vLLM/SGLang では、残高欄から推論サービスの稼働状況を確認できます。Codex では、使用量とクォータのリセット情報が表示されます。

</Callout>

**すべての残高を更新**

ページ上部の ⋯ メニューにある「すべての残高を更新」は、バックグラウンドで有効なチャネルを順次処理します。組み込みタイプの複数キーチャネルは対象外です。現在のフィルターで表示されていないチャネルも処理するため、アップストリームへのリクエストが大量に発生する場合があります。

- 実行すると「バックグラウンドで残高を更新しています。一覧は自動的に更新されます。」と表示されます。進捗は <a href="/ja/docs/guide/feature-guide/admin/system-info" target="_blank" rel="noopener noreferrer">システム情報</a>の「システムタスク」で確認できます。タスクの種類は「残高の一括更新」です。
- 照会した残高が 0 以下の場合、「異常時に自動で無効化」が有効なチャネルは「残高不足」を理由に自動で無効化されます。この処理はチャネル単位の設定のみに従い、グローバル設定の「失敗時に無効化」の影響を受けません。複数キーのプラグインチャネルでは、残高不足のキーだけが無効化されます。
- 環境変数 `CHANNEL_UPDATE_FREQUENCY` を設定すると、指定した間隔で「すべての残高を更新」が自動実行されます。単位は分で、デフォルトでは未設定です。値は整数である必要があり、それ以外では起動に失敗します。未設定の場合は手動でのみ実行できます。この項目は画面から設定できません。

### モデルの取得とアップストリームのモデル更新

- チャネル管理 - モデルの取得

![チャネル管理 - モデル取得画面](/assets/guide/feature-guide/channel-management-fetch-models.png)

**モデルを取得する手順**

1. ⋯ メニューで「モデルを取得」をクリックし、アップストリームにモデル一覧をリクエストします。
2. 「新規モデル」「既存モデル」「削除済みモデル」を切り替えます。
3. プロバイダーごとにグループ化されたモデルから、個別のモデルまたはグループ全体を選択します。
4. 「モデルを保存」をクリックすると、チャネルに反映されます。キャンセルした場合やリクエストに失敗した場合は、保存済みの一覧が保持されます。

**アップストリームの更新を適用する手順**

1. ⋯ メニューで「アップストリームの更新」をクリックし、「アップストリームのモデル変更をプレビュー」を開きます。
2. 「追加するモデル」と「削除するモデル」で、適用する変更を選択します。必要に応じて「再検出」をクリックします。
3. 「選択した変更を確認」をクリックし、「モデル変更の確認」で「選択した変更を適用」をクリックします。

<Callout type="info" title="ヒント">

- 「アップストリームのモデル更新チェック」が有効なチャネルでは、名前の横に追加予定のモデル数が「+…」、削除予定のモデル数が「-…」と表示されます。クリックするとプレビューを直接開けます。
- ページ上部の ⋯ メニューにある「すべてのアップストリームの更新を検出」は、バックグラウンドタスクとして実行されます。「アップストリームのモデル検出タスクが開始されました。進捗は『システム情報』で確認できます。完了後に画面を更新すると、適用待ちの更新を確認できます。」と表示されます。
- 「すべてのアップストリームの更新を適用」は確認ダイアログを表示せず、検出済みの全チャネルで、追加予定と削除予定のモデルを一括で反映します。
- 既存チャネルのモデルを取得するには「チャネルを運用する」権限が必要です。作成・編集ドロワーで未保存の接続情報を使ってモデルを取得するには、「チャネルの機密設定を編集する」権限が必要です。

</Callout>

### チャネルの複製

- チャネル管理 - チャネルの複製

![チャネル管理 - チャネル複製画面](/assets/guide/feature-guide/channel-management-duplicate-channel.png)

**操作手順**

1. ⋯ メニューで「チャネルを複製」をクリックし、「名前の接尾辞」（デフォルトは `_copy`）を入力します。
2. 「残高と使用済みクォータをリセット」（デフォルトで選択済み）を選択するかどうかを確認します。
3. 複製を確定します。

<Callout type="info" title="ヒント">

- 新しいチャネルには、元のチャネルの設定の大部分と認証情報がコピーされ、新しい ID と作成日時が割り当てられます。テスト日時と応答時間はリセットされます。
- 複製には「チャネルの機密設定を編集する」権限が必要です。タスクプラグインが紐付けられたチャネルの複製には、「タスクプラグインを紐付ける」権限も必要です。
- 認証情報のローテーションにチャネルの複製を使用しないでください。

</Callout>

### 有効化、無効化、削除

**有効化または無効化の手順**

1. 行内の有効化または無効化アイコンをクリックします。一括で操作する場合は、一括操作モードでチャネルを選択し、「選択したチャネルを有効化」または「選択したチャネルを無効化」をクリックします。

**削除手順**

1. ⋯ メニューで「削除」をクリックし、「チャネルを削除」ダイアログで確定します。一括で削除する場合は「選択したチャネルを削除」をクリックします。
2. 無効なチャネルをすべて削除する場合は、ページ上部の ⋯ メニューで「無効なチャネルをすべて削除」をクリックし、「無効なチャネルをすべて削除しますか？」ダイアログで確定します。

<Callout type="warn" title="注意">

- 手動で指定できる状態は、有効または手動無効のみです。自動無効化は信頼性を管理する仕組みによって実行されます。[チャネルの状態](#チャネルの状態)を参照してください。
- 個別削除、一括削除、「無効なチャネルをすべて削除」には、「チャネルの機密設定を編集する」権限が必要です。
- 「無効なチャネルをすべて削除」は、データベース全体を対象に、手動または自動で無効化されたチャネルを削除します。**現在の検索条件、種類、グループ、タグ、ページ分けによる絞り込みは適用されません**。確認ダイアログには「手動または自動で無効化されたすべてのチャネルを完全に削除します。この操作は取り消せません。」と表示されます。
- 削除したチャネルは New API から復元できません。実行前に設定をエクスポートするか、記録してください。

</Callout>

### タグによるチャネル管理

- チャネル管理 - 一括操作

![チャネル管理 - 一括操作画面](/assets/guide/feature-guide/channel-management-batch-mode.png)

**タグを設定する手順**

1. ページ上部の「一括操作」スイッチをオンにし、チャネルを選択します。
2. 一覧の下部にある「選択したチャネルにタグを設定」をクリックし、「タグを設定」でタグを入力します。空欄にするとタグが削除されます。

**タグ単位で管理する手順**

1. ページ上部の「タグモード」スイッチをオンにします。同じタグが付いたチャネルが 1 行にまとめられます。
2. まとめられた行で編集アイコンの「タグを編集」をクリックするか、⋯ メニューで「一括編集」「すべて有効化」「すべて無効化」のいずれかをクリックします。
3. 「タグを編集：…」または「タグ単位で一括編集」でタグ名、モデル、モデルマッピング、グループを変更し、「変更を保存」をクリックします。タグ名を空欄にすると、グループ化が解除されます。

<Callout type="info" title="ヒント">

- 一括選択による操作は、現在選択されているチャネルに適用されます。タグ単位での有効化、無効化、編集は、現在のページで選択された行に関係なく、該当するタグのチャネル全体に適用されます。
- まとめられた行は複数のチャネルを表すため、通常のチャネルと同じ方法では編集できません。
- タグ単位で無効化したチャネルは、手動無効として扱われます。

</Callout>

ツールバーの「ドラッグモード」をクリックすると、チャネルの左側（カードビューでは左上）のドラッグハンドルを使って優先度を調整できます。ボタンは「並べ替えを完了」に変わり、もう一度クリックするとモードを終了します。別のチャネルの中央にドロップすると「同じ優先度に追加」、2 つの優先度の間にドロップすると「新しい優先度を挿入」となり、優先度の値は自動で計算されます。ドロップするとすぐに保存され、一覧の下にある「元に戻す」で直前の調整を取り消せます。

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| 項目 | 説明 |
| --- | --- |
| 利用条件 | 並べ替えが「優先度」（昇順または降順）で、「タグモード」がオフになっており、「チャネルルーティングを編集する」権限が必要です。条件を満たさない場合はボタンが無効になり、その理由が表示されます。フィルター、ページ分け、ビューの切り替えにかかわらず利用できます。 |
| 適用範囲 | ドロップ先は現在のページに表示されているチャネルに限られますが、優先度の値は全チャネルの優先度レベルを基に計算されます。2 つの優先度レベルの間に空いている整数値がない場合、隣接するレベルがまとめて 1 ずれるため、現在のビューに表示されていないチャネルが変更されることがあります。ドラッグ中は一覧の下に影響を受けるチャネル数が表示されます。 |
| 優先度と重み | 変更対象は「優先度」のみです。同じ優先度のチャネルは、引き続き「重み」に基づいて選択されます。 |
| キーボード操作 | ドラッグハンドルにフォーカスを合わせ、方向キーを押すと、チャネルが隣のチャネルの前または後ろに移動し、すぐに保存されます。Esc キーでドラッグをキャンセルできます。 |
| 競合 | ドラッグ開始後（取り消し操作の場合は前回の保存後）にチャネルの優先度が変更されている場合、保存や取り消しは拒否され、「チャネルの優先度が変更されました。画面を更新してから再試行してください。」と表示されます。 |
| ガイド | カードビューとテーブルビューでは、初めてドラッグモードに切り替えたときに、それぞれデモが 1 回自動で表示されます。その後は「ドラッグモード」の横にある「?」をクリックすると再表示できます。 |

</div>

### 複数キーチャネルの管理

- チャネル管理 - 複数キーの管理

![チャネル管理 - 複数キーの管理画面](/assets/guide/feature-guide/channel-management-key-management.png)

作成時に「複数キーモード」を選択すると、複数の認証情報を 1 つのチャネルに保存できます。[チャネルの作成と編集](#チャネルの作成と編集)の「追加モード」を参照してください。「ランダム」は、現在有効なキーからランダムに選択します。「ラウンドロビン」は、現在有効なキーを順番に選択し、選択位置を進めます。このモードはキャッシュコンポーネントに依存します。

**操作手順**

1. ⋯ メニューで「キーを管理」をクリックし、「複数キーの管理」を開きます。
2. 状態でキーを絞り込み、個別のキーを有効化、無効化、または削除します。
3. 一括処理が必要な場合は、「すべて有効化」「すべて無効化」「自動無効化されたキーを削除」のいずれかをクリックします。

<Callout type="warn" title="注意">

- 一覧はページ分けされ、キーごとにインデックス、状態、無効化の理由、無効化日時が表示されます。上部の「有効」「手動無効」「自動無効」の集計カードは、フィルターにかかわらず、常にすべてのキーを集計します。
- 個別のキーを有効化または無効化した場合は、そのキーの状態だけが変わります。
- 個別のキーを削除すると、後続のキーのインデックスが振り直されます。最後の 1 つは削除できません。削除には「チャネルの機密設定を編集する」権限が必要です。
- 「自動無効化されたキーを削除」は、自動で無効化されたキーのみを削除します。手動で無効化されたキーは保持されます。このボタンは、自動で無効化されたキーがある場合のみ表示されます。
- 使用可能なキーがなくなると、チャネル全体が無効化されます。復旧ルールは[チャネルの状態](#チャネルの状態)を参照してください。

</Callout>

### チャネルの整合性の修復

- チャネル管理 - チャネルの整合性の修復

![チャネル管理 - チャネルの整合性修復画面](/assets/guide/feature-guide/channel-management-fix-channel-consistency.png)

「チャネルの整合性を修復」は、全チャネルの設定を基に、対応モデル、グループ、優先度、重みのインデックスを再構築します。アップストリームの認証情報、プロキシ、モデル価格の問題は修復の対象外です。

**操作手順**

1. ページ上部の ⋯ メニューで「チャネルの整合性を修復」をクリックします。
2. 「チャネルの整合性を修復しますか？」ダイアログで「修復」をクリックします。

<Callout type="warn" title="注意">
処理中は一時的にルーティングが不完全になる場合があるため、トラフィックの少ない時間帯に実行してください。確認ダイアログには「すべてのチャネル設定を基に、対応モデル、グループ、優先度、重みを含むチャネルルーティングのインデックスを再構築します。再構築中は一時的にルーティングが不完全になる場合があります。続行しますか？」と表示されます。
</Callout>

### パススルーと上書きの適用範囲

- チャネル管理 - リクエストボディのパススルーを有効にする確認

![チャネル管理 - リクエストボディのパススルーを有効にする確認画面](/assets/guide/feature-guide/create-channel-pass-through-request-body-description.png)

- チャネル管理 - リクエストヘッダーのパススルーを有効にする確認

![チャネル管理 - リクエストヘッダーのパススルーを有効にする確認画面](/assets/guide/feature-guide/create-channel-pass-through-request-headers-description.png)

パススルーを有効にする前に、パススルー時に利用できなくなる機能を一覧表示する確認ダイアログが開きます。「パススルーを有効にする」をクリックすると、設定が反映されます。

**実行ルール**

- グローバルまたはチャネル単位のリクエストボディのパススルーは、通常の変換経路をスキップします。モデルマッピング、パラメーターの上書き、プロトコル変換が通常どおり実行されることを前提にしないでください。
- チャネルで「リクエストボディのパススルー」を有効にすると、サイドバーの「リクエスト処理」ページにある「形式変換前」「送信前」の各段階のインスタンスは実行されません。このチャネルに追加したインスタンスは「リクエスト読み取り前」の段階でも実行されません。「最終チェック」「レスポンスチェック」は通常どおり実行されます。詳細は<a href="/ja/docs/guide/feature-guide/admin/request-processing#注意事項" target="_blank" rel="noopener noreferrer">リクエスト処理</a>を参照してください。
- リクエストヘッダーのパススルーでは、`*` または `re:`/`regex:` ルールを使ってクライアントのリクエストヘッダーをコピーします。Authorization、`x-api-key`、`x-goog-api-key`、WebSocket ハンドシェイク用ヘッダー、その他のセキュリティ関連ヘッダーは対象外です。
- リクエストヘッダーの上書きはパススルーの後に適用され、明示的な上書きが優先されます。`{client_header:NAME}` はヘッダー値全体として指定する必要があります。クライアントのリクエストに該当するヘッダーがなければ、追加されません。
- ストリーミングモードはクライアントリクエストで指定してください。パラメーターの上書きで JSON 内の `stream` を変更しても、ゲートウェイ、アダプター、アップストリームのストリーミング処理状態が連動して切り替わる保証はありません。

**フィールドのパススルー制御**

- 「リクエストとレスポンス」の「フィールドのパススルー制御」にあるスイッチは、デフォルトですべてオフです。項目はチャネルタイプに応じて表示され、「`service_tier` のパススルーを許可」は、この欄に表示されるすべてのタイプに適用されます。
- OpenAI 系チャネルには、「`store` のパススルーを禁止」「`safety_identifier` のパススルーを許可」「`include` の使用量難読化のパススルーを許可」「推論の地理的位置のパススルーを許可」もあります。
- Claude 系チャネルには「`speed` のパススルーを許可」もあります。Anthropic チャネルには、さらに「`inference_geo` のパススルーを許可」「Claude beta クエリのパススルーを許可」があります。

### パラメーター上書きの仕組み

- チャネル管理 - パラメーターの上書き

![チャネル管理 - パラメーターの上書き画面](/assets/guide/feature-guide/create-channel-request-and-response-parameter-overrides-visual-editor.png)

パラメーターの上書きは、リクエストの変換後、アップストリームへの送信前に実行されます。完全なプロトコル変換には対応しておらず、クライアントのストリーミング状態も自動では同期されません。ビジュアルエディターと JSON モードでは、同じパラメーター上書きルールを編集します。

**適用順序と適用範囲**

- 上書きは、リクエストが該当する relay 処理経路に入った場合にのみ実行されます。リクエストボディのパススルーでは、通常の変換処理と一部の上書き処理をスキップします。
- サイドバーの「リクエスト処理」ページにある<a href="/ja/docs/guide/feature-guide/admin/request-processing#グローバルパラメーター上書き" target="_blank" rel="noopener noreferrer">グローバルパラメーター上書き</a>のインスタンスは、チャネルのパラメーター上書きより先に実行されます。同じパラメーターにはチャネル側の設定が優先されます。グローバルパラメーター上書きの「カスタムエラーを返す」は、常に HTTP 400 を返します。
- ルールリスト（`operations`）は配列の順に実行され、各操作の結果が次の操作の入力になります。
- 旧形式のトップレベルフィールドとルールリスト（`operations`）が両方ある場合は、旧形式のフィールドを先に適用し、その後にルールリストを適用します。
- セッションルールに一致すると、そのルールのパラメーター上書きテンプレートがチャネルのパラメーター上書き設定とマージされます。詳細は<a href="/ja/docs/guide/feature-guide/system-settings/settings-request-policies#セッションとリトライ" target="_blank" rel="noopener noreferrer">セッションとリトライ</a>を参照してください。
- デフォルトは「いずれかの条件を満たす（OR）」です。「すべての条件を満たす（AND）」（`logic: "AND"`）を選択した場合に限り、すべての条件を満たす必要があります。
- 条件は、その時点のリクエスト JSON と実行コンテキストを参照します。先行する操作でモデルを変更すると、後続の条件が変更後の値を参照することがあります。`original_model` や `upstream_model` などのコンテキスト値は、リクエスト JSON に自動では書き込まれません。
- 「カスタムエラーを返す」（`return_error`）は、処理を中断してカスタムエラーを返します。ステータスコードとエラーフィールドに指定できる値は、バックエンドが解析できる範囲に限られます。入力欄に入力できるという理由だけで、すべての値が利用可能と判断しないでください。
- 条件の比較でエラーが発生すると、リクエストは `channel:param_override_invalid` で失敗し、チャネルエラーとして処理されます。条件の不一致とは区別されます。たとえば、「完全一致」（`full`）で比較する値の型が異なる場合、数値比較の片方が数値でない場合、「正規表現」（`regex`）の式が無効な場合にエラーが発生します。

**ビジュアルエディターと JSON**

「リクエストとレスポンス」で「ビジュアル編集」をクリックすると、「パラメーターの上書き」ウィンドウが開きます。「モード」では「ビジュアル」または「JSON テキスト」を選択できます。ビジュアルモードはルールを個別に編集するのに適しており、JSON モードはルール全体をコピーするのに適しています。

**操作早見表（フィールドと内容）**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 操作タイプ | 主なフィールド | 説明 |
| --- | --- | --- |
| フィールドを設定（`set`）、フィールドを削除（`delete`） | `path`、`value`。フィールドの設定時は元の値を保持（`keep_origin`）を指定可能 | JSON フィールドを設定または削除します。 |
| 末尾に追加（`append`）、先頭に追加（`prepend`） | `path`、`value`、元の値を保持（`keep_origin`） | 文字列または配列の末尾や先頭に内容を追加します。元の値を保持する場合は、既存の内容を上書きしません。 |
| フィールドを移動（`move`）、フィールドをコピー（`copy`） | `from`、`to` | 移動では移動元のフィールドを削除し、コピーではコピー元のフィールドを保持します。 |
| プレフィックスを削除（`trim_prefix`）、サフィックスを削除（`trim_suffix`） | `path`、`value` | 一致するプレフィックスまたはサフィックスを削除します。 |
| プレフィックスを保証（`ensure_prefix`）、サフィックスを保証（`ensure_suffix`） | `path`、`value` | 指定のプレフィックスまたはサフィックスがなければ追加します。 |
| 前後の空白を除去（`trim_space`）、小文字に変換（`to_lower`）、大文字に変換（`to_upper`） | `path` | 文字列から空白を除去するか、大文字・小文字を変換します。 |
| 文字列置換（`replace`）、正規表現による置換（`regex_replace`） | `path`、`from`、`to` | 文字列または正規表現を使って置換します。 |
| オブジェクト要素を除去（`prune_objects`） | `path`、条件 | 条件に従ってオブジェクト要素を除去します。 |

</div>

**操作早見表（リクエストヘッダーと処理フロー）**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 操作タイプ | 主なフィールド | 説明 |
| --- | --- | --- |
| リクエストヘッダーを設定（`set_header`）、リクエストヘッダーを削除（`delete_header`） | ヘッダー名と値。ヘッダーの設定時は元の値を保持（`keep_origin`）を指定可能 | ヘッダーの上書き設定を変更します。後続の処理でアダプターが再生成するネイティブヘッダーまで削除できる保証はありません。 |
| リクエストヘッダーをコピー（`copy_header`）、リクエストヘッダーを移動（`move_header`） | `from`、`to`、元の値を保持（`keep_origin`） | 実行時のリクエストヘッダー上書きテーブル内でコピーまたは移動します。 |
| リクエストヘッダーをパススルー（`pass_headers`） | ヘッダー名のリスト、元の値を保持（`keep_origin`） | リストにあるクライアントのリクエストヘッダーを、元の名前のまま実行時のヘッダー上書きテーブルにコピーします。リクエストヘッダーの上書きにおける `*` や `re:` のパススルーとは異なり、この操作ではセキュリティ関連ヘッダーも対象になります。`Authorization` や `x-api-key` もリストにあればそのままコピーされるため、必要なヘッダーだけを指定してください。 |
| フィールドを同期（`sync_fields`） | JSON またはヘッダーの同期元と同期先 | リクエストフィールドとリクエストヘッダーの間で値を同期します。 |
| カスタムエラーを返す（`return_error`） | エラーオブジェクト | リクエスト処理をその場で終了し、カスタムエラーを返します。拒否条件が明確な場合に適しています。 |

</div>

**条件、パス、セキュリティ関連フィールド**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 条件項目 | 説明 |
| --- | --- |
| 完全一致（`full`）、前方一致（`prefix`）、後方一致（`suffix`）、部分一致（`contains`） | 文字列または比較可能な値の照合方法です。 |
| 正規表現（`regex`） | フィールドの文字列表現を正規表現で照合します。条件値は文字列である必要があります。 |
| より大きい（`gt`）、以上（`gte`）、未満（`lt`）、以下（`lte`） | 比較する両方の値は JSON の数値である必要があります。文字列を数値として比較することはできません。 |
| 一致結果を反転（`invert`） | 照合結果を反転します。フィールドが欠落している場合は、「フィールドがない場合は条件を満たす」（`pass_missing_key`）で先に判定します。 |
| フィールドがない場合は条件を満たす（`pass_missing_key`） | パスが存在しなくても条件を満たしたものとします。デフォルトでは条件を満たさないと判定します。 |
| いずれかの条件を満たす（OR）、すべての条件を満たす（AND）（`logic`） | 「すべての条件を満たす（AND）」では、すべての条件を満たす必要があります。省略時は「いずれかの条件を満たす（OR）」になります。 |
| JSON パス | `messages.0.content`、`messages.-1.content` などのパスに対応します。 |
| 実行コンテキスト | 元のモデル、アップストリームモデル、ユーザーやグループなどを条件に照合できます。これらの名前をリクエストボディの固定フィールドとして扱わないでください。 |

</div>

<Callout type="warn" title="注意">
パラメーターの上書きは、リクエストの意味、リクエストヘッダー、エラー処理を変更できます。`stream` の切り替えには使用せず、信頼できないアップストリームにはクライアントのキーをパススルーしないでください。正規表現による置換、ヘッダーの同期、カスタムエラーも慎重に有効化してください。
</Callout>

**複数キーを持つチャネルのキーの状態**

「複数キー管理」では、各キーの状態が「有効」「手動無効」「自動無効」のいずれかとして表示されます。上部の集計カードには、すべてのキーが集計されます。

- 「複数キー管理」でキーを無効化または削除し、使用可能なキーがなくなると、チャネルは手動無効になります。いずれかのキーを再有効化すると、チャネルは自動で復旧します。
- すべてのキーがシステムによって自動無効化されると、チャネルは自動無効になります。「複数キー管理」でいずれかのキーを再有効化するか、「すべて有効化」を選択すると、チャネルも自動で復旧します。「成功後に再有効化」がオンの場合は、次回の定期テストまたは「すべてのチャネルをテスト」でも復旧できます。
- その後、管理者が個別に、またはタグ単位で手動で無効化したチャネルは、自動では復旧しません。

## 保存と反映

チャネルはデータベースに保存されます。メモリキャッシュが無効な場合、各ノードはリクエストごとにデータベースを直接読み取るため、下表の操作は各ノードの次のリクエストから反映されます。メモリキャッシュが有効な場合（Redis を有効にした構成を含む）、操作リクエストを処理したノードは即座にキャッシュを更新し、ほかのノードは約 3 秒以内にチャネルを再読み込みします（遅くとも 1 同期周期以内、デフォルトは 60 秒）。リクエスト失敗後の自動無効化とテスト後の自動復旧については、下記の「自動変更とバックグラウンドタスク」を参照してください。同期周期は環境変数 `SYNC_FREQUENCY` で調整できます。単位は秒で、デフォルトは 60 秒です。このページに記載されている環境変数はすべて起動時にのみ読み込まれます。変更後は New API を再起動してください。

**管理者による操作**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| --- | --- | --- |
| チャネルを作成（一括作成を含む） | ドロワーで「チャネルを作成」をクリック | メモリキャッシュが有効な場合、各ノード（操作リクエストを処理したノードを含む）は約 3 秒以内に新しいチャネルの使用を開始します（遅くとも 1 同期周期以内、デフォルトは 60 秒）。 |
| チャネルを編集 | ドロワーで「チャネルを更新」をクリックすると、4 つのタブの内容が一括で保存されます。 | 次のリクエストから新しい設定でルーティングします。 |
| 優先度と重みの変更、タグ操作、有効化、無効化、削除、複製、複数キーの管理 | リストでの変更時、または確認直後に書き込まれます。ドロワーでの保存操作は不要です。 | 次のリクエストから新しい設定でルーティングします。 |
| モデルを取得、アップストリームモデルを更新 | 「モデルを保存」または「選択した変更を適用」をクリックすると、チャネルに書き戻されます。 | 次のリクエストから新しいモデルリストでルーティングします。 |
| チャネルの整合性を修復 | クリックすると同期的に実行され、完了後に「チャネルの整合性の修復が完了しました（成功 … 件、失敗 … 件）」と表示されます。 | 通知が表示された後、次のリクエストから再構築された機能インデックスでルーティングします。 |

</div>

**自動変更とバックグラウンドタスク（自動実行）**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 操作 | 保存方法 | 反映タイミング |
| --- | --- | --- |
| 自動無効化 | リクエストの失敗、「すべてのチャネルをテスト」、定期テスト、または「すべての残高を更新」で自動無効化の条件を満たすと、自動で実行されます。 | 問題を検出したノードは、そのチャネルの使用を即座に停止します。ほかのノードは、同期周期（デフォルトは 60 秒）に従って再読み込みした後に使用を停止します。 |
| 自動復旧 | 「成功後に再有効化」をオンにしている場合、定期テストまたは「すべてのチャネルをテスト」が成功すると自動で実行されます。 | メモリキャッシュが有効な場合、各ノード（テストを実行したノードを含む）は、同期周期（デフォルトは 60 秒）に従って再読み込みした後にチャネルの使用を再開します。 |
| アップストリームモデルを自動同期 | 「アップストリームモデルを自動同期」をオンにすると、Master インスタンスが定期的に変更を検出します。デフォルトは 30 分ごとです。<br/>環境変数 `CHANNEL_UPSTREAM_MODEL_UPDATE_TASK_INTERVAL_MINUTES` で検出間隔を調整できます（単位は分、デフォルトは 30、1 未満の場合は 30 を使用）。`CHANNEL_UPSTREAM_MODEL_UPDATE_TASK_ENABLED` のデフォルトは `true` です。`false` に設定すると定期検出が停止します。手動検出には影響しません。`CHANNEL_UPSTREAM_MODEL_UPDATE_MIN_CHECK_INTERVAL_SECONDS` は、定期検出で同じチャネルを続けて検出する際の最小間隔です（単位は秒、デフォルトは 300、0 未満の場合は 300 を使用）。この制限は手動検出には適用されません。これら 3 項目に対応するページ上の設定はありません。 | 新しいモデルがチャネルのモデルリストに追加されると、次のリクエストからルーティングの対象になります。メモリキャッシュが有効な場合、ほかのノードは約 3 秒以内にチャネルを再読み込みします（遅くとも 1 同期周期以内、デフォルトは 60 秒）。 |

**自動変更とバックグラウンドタスク（手動実行）**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| 操作 | 保存方法 | 反映タイミング |
| --- | --- | --- |
| すべてのチャネルをテスト、すべてのアップストリーム更新を検出 | クリックするとバックグラウンドタスクとして登録されます。 | Master インスタンスがタスクを引き受けます。操作リクエストを処理したノードが Master インスタンスの場合は即座に開始し、それ以外の場合は約 15 秒以内に開始します。同種のタスクがすでにある場合は、実行リクエストが拒否されます。手動検出で記録されるのは追加予定と削除予定のモデルのみで、変更を適用した時点でモデルリストが更新されます。 |
| すべての残高を更新 | クリックするとバックグラウンドタスクとして登録され、「バックグラウンドで残高を更新しています。リストは自動的に更新されます。」と表示されます。 | Master インスタンスがタスクを引き受けて実行します。リストは 5 秒ごとに更新され、完了後に「すべての残高を更新しました」または「残高の更新に失敗しました」と表示されます。残高更新がすでに進行中の場合は、「残高の更新はすでに進行中です。」と表示され、既存タスクの進捗が反映されます。残高が不足しているチャネルは自動で無効化されます。 |
| 接続テスト、残高を確認（単一チャネル） | テストダイアログでテストを実行するか、残高をクリックします。 | テスト日時、応答時間、または残高のみを更新します。チャネルの状態やルーティングには影響しません。 |

</div>

**補足**

- **ドロワーでの保存**：4 つのタブは 1 つのフォームを共有します。保存に成功すると「チャネルを作成しました」または「チャネルを更新しました」と表示されます。保存に失敗すると、ドロワーは開いたままになり、失敗の理由が表示されます。
- **テストの実行**：保存時に行うのは設定の書き込みのみです。アップストリームへの接続やテストは自動では行われません。必要に応じて[接続テスト](#接続テスト)から手動でテストしてください。
- **進行中の接続**：チャネルを無効化（自動無効化を含む）または削除すると、そのチャネルで進行中の Realtime および Responses の WebSocket 接続が切断されます。Redis が有効な場合は、ほかのノードの該当する接続も切断されます。
- **同期完了前のルーティング**：メモリキャッシュが有効な場合、ノード間で一時的にルーティングが一致しないことがあります。
- **バックグラウンドタスクの進捗**：「すべてのチャネルをテスト」「すべてのアップストリーム更新を検出」「すべての残高を更新」の進捗は、<a href="/ja/docs/guide/feature-guide/admin/system-info" target="_blank" rel="noopener noreferrer">システム情報</a>の「システムタスク」で確認できます。

## 注意事項

- **一括操作はすべてのチャネルが対象です**。「すべてのチャネルをテスト」「すべての残高を更新」「すべてのアップストリームの更新を検出」「すべてのアップストリームの更新を適用」「無効なチャネルをすべて削除」「チャネルの整合性を修復」は、現在の一覧の絞り込みに関係なく実行されます。トラフィックの少ない時間帯に実行することをおすすめします。
- **テストや残高更新でチャネルの状態が変わることがあります**。「すべてのチャネルをテスト」を実行すると、チャネルが自動で無効化または復旧されることがあります。「すべての残高を更新」を実行すると、残高不足のチャネルが自動で無効化されることがあります。詳しくは[保存と反映](#保存と反映)の「自動変更とバックグラウンドタスク」を参照してください。
- **自動同期はモデル一覧を直接変更します**。「アップストリームのモデルを自動同期」を有効にすると、定期チェックで検出された新しいモデルがチャネルのモデル一覧に直接追加されます。自動同期は追加のみを行い、無視するよう設定したモデルは対象外です。
- **「すべてのアップストリームの更新を適用」では個別の確認を行いません**。更新を検出したすべてのチャネルについて、追加予定と削除予定のモデルを一括で反映します。個別に確認するには、「アップストリームのモデル変更をプレビュー」で対象にチェックを入れ、「選択した変更の適用を確定」をクリックします。
- **機密性の高い操作には「チャネルの機密設定を編集」権限が必要です**。この権限を持たない Admin は、チャネルの作成、複製、削除を行えません。認証情報、タイプ、Base URL、プロキシ、リクエストヘッダーの上書き、パラメーターの上書きなど、機密性の高い設定の変更も保存できません。詳しくは[権限とセキュリティ境界](#権限とセキュリティ境界)を参照してください。
- **削除したチャネルは復元できず、複製時には認証情報が引き継がれます**。削除したチャネルは New API から復元できません。複製先には元のチャネルの認証情報が引き継がれるため、複製は認証情報のローテーションには使えません。詳しくは[有効化、無効化、削除](#有効化無効化削除)と[チャネルの複製](#チャネルの複製)を参照してください。

<Accordion title="チャネルのテストで認証に失敗する">
**説明**

テストに失敗すると「… のテストに失敗しました」（英語では … test failed）と表示され、アップストリームから返されたエラーの詳細が表示されます。

**考えられる原因**

- Base URL に API の完全なパスを含めている。
- 認証情報の形式が正しくない、または組織、プロジェクト、リージョンの指定に誤りがある。
- プロキシまたはエンドポイントのタイプがアップストリームの仕様に合っていない。

**対処方法**

1. エラーの詳細に従って該当する項目を修正します。
2. 詳細テストでエンドポイントのタイプまたはモデルを変更し、再度テストします。詳しくは[接続テスト](#接続テスト)を参照してください。
</Accordion>

<Accordion title="ユーザーに特定のモデルが表示されない">
**説明**

呼び出し元が取得するモデル一覧には、所属グループ内の有効なチャネルが提供する、価格設定済みのモデルのみが含まれます。モデル広場に表示するかどうかは、モデル管理の「広場に表示」で別途設定します。詳しくは<a href="/ja/docs/guide/feature-guide/admin/model#広場での表示状態" target="_blank" rel="noopener noreferrer">モデル管理</a>を参照してください。

**考えられる原因**

- チャネルのモデル一覧に該当する名前が含まれていない。モデルマッピングを使用する場合は、マッピング元のモデル名もモデル一覧に追加する必要があります。
- チャネルのグループがユーザーまたは API キーのグループと一致していない。
- API キーで利用可能なモデルが制限されている。
- 該当するモデルを提供するチャネルが無効になっている。
- モデルの価格が設定されていない。サイトで「自分用モード」が有効になっている場合、またはユーザーが「価格未設定のモデルを許可」を有効にしている場合は、この制限は適用されません。

**対処方法**

1. チャネルのモデル、グループ、状態と、API キーのモデル制限を確認します。
2. 価格が未設定の場合は、Root に<a href="/ja/docs/guide/feature-guide/system-settings/settings-billing#モデルの価格設定" target="_blank" rel="noopener noreferrer">課金と支払いの設定</a>で価格を設定するよう依頼してください。
</Accordion>

<Accordion title="リクエストが想定外のチャネルにルーティングされる">
**考えられる原因**

- 優先度、重み、チャネルの状態、またはタグの適用範囲が想定と異なる。
- リクエストパスが異なる、セッションルールに該当している、または<a href="/ja/docs/guide/feature-guide/system-settings/settings-request-policies#セッションとリトライ" target="_blank" rel="noopener noreferrer">再試行設定</a>が適用された。
- 共通のエントリーポイントでは、通常のチャネルとプラグインチャネルの両方が選択対象になる。

**対処方法**

1. 使用ログの詳細にある<a href="/ja/docs/guide/feature-guide/system-settings/settings-request-policies#リクエストの判定記録" target="_blank" rel="noopener noreferrer">リクエストポリシーの判定</a>で、実際の選択過程を確認します。
</Accordion>

<Accordion title="パラメーターの上書きが反映されない">
**考えられる原因**

- リクエストボディのパススルーが有効になっており、パラメーターの上書き処理がスキップされている。
- 操作の順序、条件で指定したパス、または JSON の型が想定と異なる。
- リクエストが、パラメーターの上書きを実行するリレー処理を経由していない。

**対処方法**

1. [パラメーター上書きシステム](#パラメーター上書きの仕組み)の「適用順序と適用範囲」に沿って、一つずつ確認します。
</Accordion>

<Accordion title="チャネルが頻繁に自動で無効化される">
**考えられる原因**

- アップストリームから返されたステータスコードやエラーメッセージが、<a href="/ja/docs/guide/feature-guide/system-settings/settings-request-policies#チャネルのヘルス" target="_blank" rel="noopener noreferrer">チャネルのヘルス設定</a>の自動無効化ルールに該当している。テスト用モデル、プロキシ、アップストリームのレート制限による失敗などが該当します。
- 「すべての残高を更新」の実行時に残高が 0 以下だったため、チャネルが「残高不足」を理由に自動で無効化された。

**対処方法**

1. チャネルの無効化理由を確認し、自動で無効化されたのか、手動で無効化されたのかを確認します。
2. チャネルのヘルス設定のルールに照らして、チャネルやテストの設定を調整します。
</Accordion>

<Accordion title="モデルの取得に失敗する">
**表示メッセージ**

「モデルの取得に失敗しました」（英語では Failed to fetch models）、または「このチャネルタイプはモデルの取得に対応していません」（英語では This channel type does not support fetching models）と表示されます。サーバーまたはアップストリームから失敗理由が返された場合は、そのメッセージがそのまま表示されます。

**説明**

取得に失敗しても、保存済みのモデル一覧は置き換わりません。

**考えられる原因**

- チャネルタイプがモデルの取得に対応していない。
- 認証情報、Base URL、またはネットワークに問題がある。
- 高度なカスタムチャネルにモデル一覧を取得するルートが設定されていない。

**対処方法**

1. 問題を修正してから、モデルを再取得します。
</Accordion>

<Accordion title="残高が更新されない">
**表示メッセージ**

「複数キーのチャネルは残高照会に対応していません」（英語では Multi-key channels do not support balance queries）と表示されます。プラグインが残高を提供しないプラグインチャネルでは、「このチャネルのプラグインは残高を提供しません。」（英語では The plugin of this channel does not report a balance）と表示されます。

**考えられる原因**

- チャネルタイプが標準の残高照会 API に対応していない、組み込みタイプの複数キーのチャネルである、またはプラグインが残高を提供しないプラグインチャネルである。
- 「すべての残高を更新」がバックグラウンドで実行中である。完了するまでは、一覧に更新前の残高が表示されることがあります。
- Codex、vLLM/SGLang の稼働情報は別の画面で確認します。詳しくは[残高と稼働状態の確認](#残高と稼働状況の照会)を参照してください。
</Accordion>

<Accordion title="複数キーのチャネルを利用できない">
**考えられる原因**

チャネル内のキーが手動または自動で無効化され、利用できるキーが残っていません。チャネル全体の状態には、個々のキーの状態は反映されません。

**対処方法**

1. 各キーの状態と自動無効化の理由を確認します。詳しくは[複数キーのチャネルの管理](#複数キーチャネルの管理)と[チャネルの状態](#チャネルの状態)を参照してください。
</Accordion>

<Accordion title="「チャネルの整合性を修復」を実行してもルーティングできない">
**説明**

ボタンをクリックすると、修復処理が同期的に完了します。メモリキャッシュを有効にした複数インスタンス構成では、他のノードが約 3 秒以内（遅くとも 1 同期周期、デフォルトは 60 秒）にチャネルを再読み込みし、新しいインデックスを使い始めます。修復タスクがすでに実行中の場合は、「修復タスクがすでに実行中です。しばらくしてから再試行してください」（英語では A repair task is already running. Please try again later）と表示されます。

**考えられる原因**

チャネルのモデル、グループ、優先度、重みが想定と異なるか、認証情報またはアップストリームに問題があります。この修復処理が行うのはインデックスの再構築のみです。

**対処方法**

1. 一覧を更新し、モデル、グループ、優先度、重みを確認します。
2. 認証情報とアップストリームに問題がないか確認します。
</Accordion>

<Accordion title="チャネルを保存しても、一部のリクエストが以前の設定でルーティングされる">
**説明**

メモリキャッシュを有効にしている場合（Redis を有効にした構成を含む）、他のノードは約 3 秒以内（遅くとも 1 同期周期、デフォルトは 60 秒）にチャネルを再読み込みします。再読み込みが完了するまでは、ノードによってルーティング結果が異なることがあります。リクエスト失敗後の自動無効化やテスト後の自動復旧は、他のノードが同期周期（デフォルトは 60 秒）に従って再読み込みします。メモリキャッシュを無効にしている場合は、ルーティング時にデータベースを直接参照します。

**対処方法**

1. 複数インスタンス構成の場合は、Root がチャネル一覧の右上にあるノードの状態を確認します。「… 件のノードの更新に失敗しました」と表示された場合は、クリックして該当するノードを特定し、そのログを確認します。
2. 数秒待ってから再試行します。自動で無効化または復旧されたチャネルの場合は、最大で 1 同期周期（デフォルトは 60 秒）待ちます。
</Accordion>

<Accordion title="「すべてのチャネルをテスト」を実行すると、タスクがすでに実行中と表示される">
**表示メッセージ**

「チャネルのテストタスクがすでに実行中か、実行待ちです。今回の手動タスクは開始できません」（英語では A channel test task is already running or queued. Cannot start this manual task）と表示されます。「すべてのアップストリームの更新を検出」を実行した場合は、「モデルの更新タスクがすでに実行中か、実行待ちです。今回の手動タスクは開始できません」（英語では A model update task is already running or queued. Cannot start this manual task）と表示されます。

**考えられる原因**

同じ種類のシステムタスク（定期実行のタスクを含む）が実行中か、実行待ちになっています。

**対処方法**

1. <a href="/ja/docs/guide/feature-guide/admin/system-info" target="_blank" rel="noopener noreferrer">システム情報</a>の「システムタスク」で進捗を確認します。
2. タスクの完了後に再実行します。
</Accordion>

</Accordions>

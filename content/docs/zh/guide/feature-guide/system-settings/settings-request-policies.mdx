## 请求策略配置简介

请求策略决定一个请求在发往上游前是否被拦截、优先使用哪个渠道、失败后是否重试，以及渠道何时被自动禁用或恢复。请求策略包含三个分区：

<div className="[&_table]:min-w-[48rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| 分区 | 入口 | 主要用途 |
| --- | --- | --- |
| [请求检查](#请求检查) | `/system-settings/request-policies/filtering` | 按关键词拦截请求文本。 |
| [会话与重试](#会话与重试) | `/system-settings/request-policies/routing` | 会话保持、会话规则与重试预算。 |
| [渠道健康](#渠道健康) | `/system-settings/request-policies/health` | 定期渠道测试、自动禁用与自动恢复。 |

</div>

**其他入口**（以下跳转链接只对 Root 显示）：

1. 渠道列表页标题旁的徽标「最大重试: N」显示当前的「最多重试次数」。Root 点击徽标（提示为「重试设置」）可跳转到「会话与重试」；Admin 只能看到数值。
2. 编辑渠道时，「异常自动禁用」开关下方的说明显示「参与自动停用」或「不参与自动停用」，以及「来源: …」；其后的「请求策略」链接跳转到「渠道健康」。
3. 编辑 API 密钥时，分组为 `auto` 会出现「跨分组重试」开关，其说明末尾的「请求策略」链接跳转到「会话与重试」。

- 匹配与拦截规则

1. 按不区分大小写的子串匹配：请求文本中包含任一关键词即命中。
2. 检查对象是从请求中提取、用于计费估算的合并文本，例如消息文本、工具名和参数；不检查图片、音频和生成的响应内容。
3. 命中后，请求在发往上游前被拒绝，返回 HTTP 500，错误码为 `sensitive_words_detected`，错误消息形如 `user sensitive words detected: <命中词> (request id: …)`。命中词为该关键词的小写形式；匹配到第一个关键词即停止，因此消息中通常只有一个词。
4. 被拒绝的请求不会重试，不影响渠道健康状态，也不会触发自动禁用。
5. 该功能只做拦截，不替换或遮盖文本，也不过滤上游返回的内容。

<Callout type="warn">
- 命中敏感词时返回的是 HTTP 500，客户端会把它当作服务端错误处理，需要按错误码 `sensitive_words_detected` 区分。
- 错误消息会把命中的关键词回显给调用方。词表本身需要保密时，应考虑这一点。
</Callout>

- 保存

页头按钮为「保存敏感词」。没有修改时点击不会发出请求，也不显示提示。

**三种会话保持模式**

| 模式 | 规则命中后的行为 |
| --- | --- |
| 不保持 | 规则仍会匹配，规则中的参数覆盖模板照常生效，但不读取也不写入会话绑定，按正常方式选择渠道。 |
| 优先原渠道，失败允许切换 | 首次尝试优先使用该会话已绑定的渠道；失败后按正常重试流程切换到其他渠道。 |
| 必须使用原渠道 | 尚无绑定时按正常方式选择渠道，请求成功后建立绑定。但只要命中规则，本次请求的任何失败都不再重试，即使该会话还没有绑定渠道。已有绑定但绑定的渠道不可用时，直接返回 HTTP 503，错误信息为 `strict_session_binding_unavailable`。 |

1. 关闭「启用会话保持」后，两个绑定开关置灰；「会话保持」单选仍可修改，但在重新开启总开关前不起作用。
2. 「会话缓存设置」默认折叠，展开后才显示两个缓存字段。

- 会话规则

会话规则定义如何从请求中识别同一会话，以及命中后如何保持该会话已使用的渠道；规则本身不指定渠道，渠道仍按正常方式选出后再绑定。卡片标题旁显示规则数量。

每条会话绑定在缓存中占一个条目：「缓存条目」即当前保存的绑定数，清空缓存即解除这些绑定，之后的请求重新选择渠道。

<Callout type="warn">
规则弹窗中的「保存」只更新页面上的规则草稿。添加、编辑、删除规则，填充模板，或在 JSON 模式中修改后，都必须点击页头「保存更改」才会提交；离开页面时没有未保存提醒，未提交的修改会丢失。
</Callout>

1. 规则可在「可视化」和「JSON」两种模式间切换。JSON 模式下「填充模板」和「添加规则」不可用；JSON 不是数组或格式错误时，无法切回可视化模式。
2. 没有规则时显示「暂无规则」。
3. 卡片底栏显示「缓存条目」，格式为“已用 / 容量”，读取失败时显示「无法展示」。使用 Redis 时，容量显示为 `0`。

**从零配置会话保持**

1. 在「会话默认设置」中确认「启用会话保持」已开启。新规则的「会话保持」默认为「继承全局默认」，因此全局「会话保持」不能选「不保持」。这里的修改在第 3 步一并保存。
2. 点击「添加规则」→「空白规则」，填写「名称」「模型正则」和至少一个「Key 来源」，然后点击弹窗中的「保存」，字段说明见下文「添加或编辑规则」。新规则排在表格末尾，其「会话保持」列不应显示「不保持」。
   - 规则按列表顺序匹配，条件不要与前面的规则重叠，否则请求会先命中前面的规则（见下文「匹配顺序与注意事项」）。可视化模式不能调整顺序，需要时在 JSON 模式中调整。
   - 「Codex CLI」「Claude CLI」两个模板与下方的两条内置规则相同，内置规则仍在时无需添加；删除过内置规则时，才需要用模板重新添加。
3. 点击页头「保存更改」，提示「保存成功」即表示已提交；校验失败时的提示见[保存与生效](#保存与生效)。
4. 发送一个满足该规则全部条件、使用尚未绑定过的 Key 值的请求。请求成功（HTTP 状态码小于 400）后才会写入绑定；被固定到某个渠道的请求不经过会话规则。然后点击卡片底栏的「刷新缓存」（缓存统计不会自动更新），确认该规则行的「缓存」列和「缓存条目」都已增加。如何确认后续请求用上了这条绑定，见[变更后验证](#变更后验证)第 4 条。

默认有两条内置规则，二者都附带请求头透传的参数覆盖模板：

<div className="[&_table]:min-w-[48rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| 规则名 | 模型正则 | 路径正则 | Key 来源 | 会话保持 |
| --- | --- | --- | --- | --- |
| `codex cli trace` | `^gpt-.*$` | `/v1/responses` | `gjson`：`prompt_cache_key` | 必须使用原渠道（规则单独设置） |
| `claude cli trace` | `^claude-.*$` | `/v1/messages` | `gjson`：`metadata.user_id` | 必须使用原渠道（规则单独设置） |

</div>

<Callout type="warn">
两条内置规则，以及通过「填充模板」或「添加规则 → Codex CLI / Claude CLI」生成的规则，默认都是「必须使用原渠道」，命中后请求失败也不会重试。

如需失败时切换渠道：编辑规则，把「会话保持」改为「优先原渠道，失败允许切换」（或改为「继承全局默认」，并确认全局模式不是「必须使用原渠道」），在弹窗中点击「保存」后，再点击页头「保存更改」。
</Callout>

**Key 来源类型**

<div className="[&_table]:min-w-[48rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| 类型 | 填写内容 | 说明 |
| --- | --- | --- |
| `context_int` | 请求上下文键名，例如 `token_id` | 读取上下文中的正整数并转换为字符串；值不存在或不大于 `0` 时尝试下一个来源。 |
| `context_string` | 请求上下文键名，例如 `username` | 读取上下文字符串并去除首尾空白；空值时尝试下一个来源。 |
| `request_header` | 请求头名称，例如 `X-Session-ID` | 读取指定请求头并去除首尾空白；客户端需要实际携带该请求头。 |
| `gjson` | JSON Body 的 GJSON 路径，例如 `metadata.conversation_id` | 从请求体中提取值；路径不存在或结果为空时尝试下一个来源。 |

</div>

**高级设置**

**匹配顺序与注意事项**

1. 规则按列表顺序逐条检查。某条规则同时满足以下条件即生效，后面的规则不再检查（即使该会话还没有绑定）：
   1. 模型、路径、User-Agent 条件都匹配；
   2. 取到非空 Key，且该值通过 Value 正则校验。
2. 多个 Key 来源只取第一个非空值。该值未通过 Value 正则时，跳过整条规则，不会再尝试该规则后面的 Key 来源。
3. 模型正则为空的规则不会匹配任何请求，即使表格中显示「所有模型」。弹窗要求至少填写一行，这种规则只会通过 JSON 模式写入。
4. 规则没有设置会话保持模式时（例如两条内置规则，以及从旧版本保留下来的规则），按旧字段 `skip_retry_on_failure` 显示为「必须使用原渠道」（值为 `true`）或「优先原渠道，失败允许切换」，来源为「规则单独设置」。在弹窗中打开时预填同样的模式，保存后写入明确的模式。
5. 弹窗中的「取消」放弃本次编辑；「保存」只更新草稿，见「会话规则」中的提示。
6. 提交时后端会编译所有规则的模型正则、路径正则和 Value 正则；任一正则不合法，整次保存都会被拒绝，错误形如 `rule "<规则名>": error parsing regexp: …`。

- 重试预算

<div className="[&_table]:min-w-[52rem] [&_table]:table-fixed [&_th:nth-child(1)]:w-[13%] [&_th:nth-child(2)]:w-[24%] [&_th:nth-child(3)]:w-[11%] [&_th:nth-child(4)]:w-[18%] [&_td]:align-top [&_td_code]:wrap-anywhere">

| 页面字段 | 配置键 | 默认值 | 校验与范围 | 说明 |
| --- | --- | --- | --- | --- |
| 最多重试次数 | `RetryTimes` | `0` | 整数 `0–99`（后端只要求不小于 `0`） | 不含首次，按分组计算（见下方「重试如何进行」第 2 条）。默认 `0` 表示失败后不重试。 |
| 自动重试状态码 | `AutomaticRetryStatusCodes` | `100-199,300-399,401-407,409-499,500-503,505-523,525-599` | 逗号分隔的状态码或闭区间，取值 `100–599`；格式无效时提示「状态码规则无效」；留空表示不按状态码重试 | 2xx、504、524 始终排除。占位文字为「例如 401、403、429、500-599」。保存时相邻区间会合并，见[保存与生效](#保存与生效)。 |

</div>

**重试如何进行**

1. 总尝试次数为 1 加「最多重试次数」。每次重试都会重新选择渠道，并依次使用更低一级的渠道优先级；优先级用完后停留在最低一级，可能再次选中同一个渠道。首次尝试使用了会话绑定的渠道时，第一次重试从最高优先级开始。
2. API 密钥的分组为 `auto` 且开启了「跨分组重试」时，每个分组各有一份重试次数：当前分组用完后切换到下一个分组，并从该分组的最高优先级开始。
3. 每次失败后按以下顺序判断，满足任一项即停止重试：
   1. 命中「必须使用原渠道」的规则；
   2. 请求被固定到某个渠道；
   3. 错误被标记为不可重试；
   4. 重试次数已用完；
   5. 状态码为 2xx、504、524，或上游响应体无法解析；
   6. 状态码不在「自动重试状态码」中。
4. 两种例外：
   - 渠道类错误（错误码以 `channel:` 开头，例如渠道没有可用密钥、密钥无效、参数覆盖配置无效、模型映射错误）只检查第 1、2 项，之后直接重试，总尝试次数仍受「最多重试次数」限制。
   - 状态码不在 `100–599` 范围内时，检查完第 1–4 项后直接重试，不检查第 5、6 项。
5. 异步任务提交（如视频生成）使用内置规则，不读取「自动重试状态码」：429、307 和除 504、524 外的 5xx 重试；2xx、400、408、504、524 不重试；其余状态码中，本地错误不重试，上游返回的错误（例如 401、403、404）重试。「最多重试次数」、固定渠道和「必须使用原渠道」对它同样有效。

**何时触发自动禁用**

<div className="[&_table]:min-w-[48rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| 场景 | 判断依据 | 说明 |
| --- | --- | --- |
| 真实请求失败 | 渠道类错误、「自动禁用状态码」、「失败关键词」 | 不比较耗时；被标记为不可重试的错误不触发禁用，但渠道类错误除外。 |
| 定时测试或「测试所有渠道」 | 同上，另外比较「健康检查耗时阈值（秒）」 | 「仅检查被自动禁用的渠道」模式不禁用渠道。 |
| 单个渠道测试 | — | 既不禁用也不恢复渠道。 |

</div>

1. 以上场景都要求全局「失败时禁用」和渠道「异常自动禁用」同时开启。
2. 多 Key 渠道只禁用出错的那个 Key；所有 Key 都被禁用后，整个渠道才变为自动禁用。

- 自动恢复与通知

1. 恢复条件：开启「成功后重新启用」，渠道状态为自动禁用，并在定时测试或「测试所有渠道」中测试成功；全局「失败时禁用」开启时，测试耗时还不能超过「健康检查耗时阈值（秒）」。单个渠道测试不会恢复渠道，手动禁用的渠道也不会恢复。
2. 自动禁用和自动恢复都会发送通知。接收者是开启了「渠道通知」的已启用管理员（Admin 和 Root）；从未设置过该开关时，只有 Root 默认接收。各管理员可在[个人设置](/zh/docs/guide/feature-guide/user/personal-setting#设置通知和行为偏好)中开关「渠道通知」。
3. 同一渠道同一状态的通知对每位管理员限频，默认 10 分钟内最多 2 条，可通过环境变量 `NOTIFY_LIMIT_COUNT`、`NOTIFICATION_LIMIT_DURATION_MINUTE` 调整。

- 运行条件

1. 定期测试只在主节点运行，`NODE_TYPE=slave` 的节点不运行。测试按间隔排队，上一轮未结束时不会重复启动。
2. 环境变量会覆盖页面值：设置 `CHANNEL_TEST_FREQUENCY`（正整数）时，强制开启定期测试，间隔取该值（分钟），模式固定为「主动检查全部渠道」；设置 `CHANNEL_TEST_ENABLED`（布尔值）时，强制设定「定期渠道测试」开关。后者在前者之后应用，设为 `false` 时仍会关闭定期测试。

## 保存与生效

- 三个分区分别保存，每次只提交本分区中有变化的项；成功后提示「保存成功」。「会话与重试」和「渠道健康」没有修改时提示「没有需要保存的更改」，「请求检查」没有修改时不做任何提示。
- 后端先把提交的项合并进整套请求策略并整体校验，再在一个事务中写入：任一项不合法，本次提交的所有项都不会写入。这与「安全与限制」等设置域逐项保存的方式不同。
- 校验失败时的提示：
  1. 多数字段先在前端校验，不合法时不会提交。
  2. 后端校验失败时，以弹出提示显示后端返回的英文原文，常见于规则正则或 JSON 模式中的修改，例如 `rule "<规则名>": error parsing regexp: …`、`negative affinity TTL`、`invalid session mode for rule "<规则名>"`。
  3. 「会话与重试」还会在卡片下方用红字显示后端返回的错误；该分区有修改且存在无效值时，底部提示「请修正无效配置后再保存。」
- 修改「自动重试状态码」或「自动禁用状态码」并保存时，前端会先合并相邻区间再提交，例如 `409-499,500-503` 会合并为 `409-503`，覆盖的状态码不变。
- 请求策略没有版本冲突检测，多人同时修改时，后保存的覆盖先保存的。离开页面时也没有未保存提醒，未保存的修改会丢失。
- 保存后当前节点立即更新；多节点部署中的其他节点按 `SYNC_FREQUENCY` 周期（默认 60 秒）重新载入，同步完成前各节点可能短暂不一致。
- 「最多缓存会话数」只在首次使用会话缓存时读取，修改后需重启服务才会改变内存缓存容量；使用 Redis 时不适用。「默认会话有效期（秒）」对之后新写入的绑定立即生效。

## 请求决策记录

请求策略会记录每个请求的路由与重试决策，供排查使用。

- 位置：[使用日志](/zh/docs/guide/feature-guide/user/log)中某条记录的「详情」→「请求策略决策」。只有 Admin 和 Root 能看到。
- 内容：按步骤列出选择的渠道、命中的会话规则、失败原因、重试或停止的判断及其依据来源，以及耗时、分组、状态码和对渠道健康的处理。
- 成功请求的记录随消费日志写入，需要开启[运维配置](./settings-operations#日志维护)中的「记录配额使用量」（默认开启）。
- 失败尝试的记录随错误日志写入，只有设置环境变量 `ERROR_LOG_ENABLED=true` 时才会写入。请求最终失败时，不会再单独写一条汇总记录。
- 以下请求不会留下决策记录：被敏感词拒绝的请求，它们在进入重试流程、发往上游之前就已结束，既不写消费日志也不写错误日志；命中「必须使用原渠道」但绑定渠道不可用、直接返回 HTTP 503 的请求。

## 变更后验证

1. 刷新浏览器页面后逐个打开三个分区，确认数值与保存的一致。
2. 开启请求文本过滤后，用包含测试词的请求验证：应返回 HTTP 500 和错误码 `sensitive_words_detected`。
3. 把「最多重试次数」设为 `1` 以上，用一个可控的失败渠道（例如使用无效密钥的测试渠道）发送请求，在使用日志详情的「请求策略决策」中核对重试次数和停止原因。若所有尝试都失败，需先设置环境变量 `ERROR_LOG_ENABLED=true`，否则使用日志中没有该请求的决策记录。
4. 验证会话规则：按[会话与重试](#会话与重试)中「从零配置会话保持」第 4 步，用一个尚未绑定过的 Key 值发送满足规则条件的请求。请求成功后必须先点击「刷新缓存」（统计不会自动更新），再查看该规则行的「缓存」列是否增加。然后用同一 Key 再请求一次，在使用日志中确认两条记录的渠道 ID 相同。渠道 ID 右上角的琥珀色 ✦ 表示该请求关联了会话规则，悬停可看到规则名和分组：
   - 规则没有参数覆盖模板时，✦ 只在首次尝试使用了已有绑定时出现：新 Key 的第一条请求没有 ✦，第二条起才有。
   - 规则带参数覆盖模板时（包括两条内置规则），只要命中规则就显示 ✦，第一条请求和「不保持」模式下也会显示，因此 ✦ 不能证明绑定已生效，应以渠道 ID 和「缓存」列为准。
5. 用「测试所有渠道」验证自动禁用原因和自动恢复；避免在业务高峰期制造大量失败。

## 常见问题

- **敏感词没有拦截**：确认「启用过滤」和「检查用户提示」都已开启、关键词列表非空；匹配方式为不区分大小写的子串匹配；图片、音频和响应内容不检查。该检查只作用于普通中转请求和 Responses WebSocket 请求，Midjourney 和异步任务的提交不经过此检查。
- **命中敏感词后客户端收到 500**：这是当前实现，客户端应按错误码 `sensitive_words_detected` 识别并处理。
- **重试没有生效**：依次检查：
  1. 「最多重试次数」是否仍为默认值 `0`；
  2. 失败的状态码是否在「自动重试状态码」中；
  3. 请求是否命中了「必须使用原渠道」的规则，包括两条内置 CLI 规则；
  4. 请求是否被固定到某个渠道；
  5. 是否属于 2xx、504、524 这类始终不重试的情况；
  6. 可用渠道是否只有一个，或最低一级优先级只有同一个渠道：此时仍会重试，但可能再次选中同一渠道，看起来像没有重试。
- **命中内置 CLI 规则的请求失败后不重试**：`gpt-*` 模型的 `/v1/responses` 请求体带有 `prompt_cache_key`，或 `claude-*` 模型的 `/v1/messages` 请求体带有 `metadata.user_id` 时，会命中两条内置 CLI 规则。它们默认是「必须使用原渠道」，命中后即使还没有绑定渠道也不重试。把这两条规则的「会话保持」改为「优先原渠道，失败允许切换」，或改为「继承全局默认」并确认全局模式不是「必须使用原渠道」；在弹窗中点击「保存」后，再点击页头「保存更改」。
- **渠道被自动禁用**：检查全局「失败时禁用」、渠道「异常自动禁用」、「自动禁用状态码」和「失败关键词」；耗时阈值只在定时测试和「测试所有渠道」中比较。
- **渠道没有自动恢复**：需要开启「成功后重新启用」，并有一次成功的定时测试或「测试所有渠道」；全局「失败时禁用」开启时，测试耗时不能超过「健康检查耗时阈值（秒）」；单个渠道测试不会恢复渠道，手动禁用的渠道不会恢复。
- **定期测试间隔与页面不一致**：部署环境可能设置了 `CHANNEL_TEST_FREQUENCY` 或 `CHANNEL_TEST_ENABLED`，它们会覆盖页面值；`NODE_TYPE=slave` 的节点不执行定期测试。
- **找不到「清空该规则缓存」，或缓存列显示「不适用」**：该规则没有开启「包含规则名」。
- **缓存条目一直是 0**：使用 Redis 时容量显示 `0` 属于正常。已用数一直为 0 时，依次检查：
  1. 发送请求后是否点击了「刷新缓存」，缓存统计不会自动更新；
  2. 规则是否已通过页头「保存更改」提交，弹窗中的「保存」只更新草稿；
  3. 「启用会话保持」是否开启，规则的实际模式是否为「不保持」；
  4. 请求是否满足规则的全部条件，包括取到非空 Key 且通过 Value 正则；
  5. 请求是否被列表中前面的规则抢先命中，实际命中的规则名可在「请求策略决策」的「命中会话规则」一步中查看；
  6. 请求是否失败，失败的请求不写入绑定；
  7. 请求是否被固定到某个渠道，这类请求不经过会话规则。
- **保存时提示英文错误**：这是后端校验返回的原文，本次提交的所有项都没有写入，修正后重新保存。
- **使用日志中看不到失败请求的决策记录**：需要设置环境变量 `ERROR_LOG_ENABLED=true`。

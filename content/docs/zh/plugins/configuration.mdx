## 创建 Task Plugin 渠道

安装并启用插件后，在自己的 New API 实例中打开「渠道」管理，添加渠道：

1. 选择 **Task Plugin（任务插件，类型 61）**。
2. 选择已经注册的插件。
3. 填写上游 Base URL 和插件要求的认证信息。
4. 选择插件支持的模型，并配置可用分组、优先级和权重。
5. 保存渠道，再为相关模型[设置价格](/zh/docs/plugins/billing)。

渠道通过 `setting.task_plugin_key` 绑定插件。插件必须处于可用状态，模型应与插件实际声明的名称一致。渠道的分组还需要与调用用户或 API 密钥的可用分组匹配。

插件管理由 Root 操作；管理员绑定插件渠道需要 `task_plugin:bind` 权限及相应渠道管理权限。

## Base URL 的含义

**Base URL 是上游服务地址，不是 `plugin.js` 的下载地址。** 安装地址用于导入代码，渠道地址用于实际发起生成请求。

| 配置                          | 行为                                                     |
| ----------------------------- | -------------------------------------------------------- |
| 明确填写 Base URL             | 保存并使用管理员填写的地址                               |
| 留空且插件声明 `meta.baseUrl` | 对 Task Plugin 渠道，宿主把插件默认地址写入渠道配置      |
| 留空且插件没有默认地址        | 需要提供插件实际使用的上游地址，不能假定宿主知道厂商地址 |
| 插件后续更改 `meta.baseUrl`   | 已保存渠道继续使用原地址，需管理员决定是否修改           |

插件默认地址只用于类型 61 渠道。已有渠道类型继续遵循各类型的地址配置规则。

## 认证与允许的主机

按插件文档填写 API Key 或对应认证配置，不同插件的认证方式可能不同。`meta.auth` 可以声明 API Key、无认证或宿主管理的 OAuth 认证方式；OAuth 凭据解析由宿主负责。

默认允许访问渠道 Base URL 所在主机。需要请求其他主机时，插件须在 `meta.allowedHosts` 声明额外的 `host` 或 `host:port`。该列表不接受协议、路径或查询参数。

<Callout title="更换上游地址">
  修改渠道域名后，插件原先的默认域名不会自动加入允许列表。如果插件仍构造指向旧域名的请求，宿主会拒绝它。应核对插件如何使用
  `ctx.baseUrl`，而不是随意扩大允许的主机范围。
</Callout>

## 模型与模型映射

先从[插件市场](/zh/plugins)的详情查看支持模型，再配置渠道模型列表。插件声明协议或原生路由时，还可能对某一入口进一步限制模型范围。

若使用渠道模型映射，插件会收到两个模型标识：

- `ctx.model`：用户请求的模型名，用于计费和对外展示，可能是别名。
- `ctx.upstreamModel`：映射后的上游模型名。请求上游、选择模型用量配置时使用此值；未映射时与原模型一致。

开发插件时，通常使用 `ctx.upstreamModel || ctx.model` 构造上游 body，不能随意把请求描述符顶层的 `model` 改成上游名。

## 已有渠道类型与共享模型

部分官方插件通过 `meta.channelTypes` 支持已有渠道类型，例如 OpenAI、Gemini 或厂商专用类型。其支持范围以市场详情为准，已有渠道无需一律改成类型 61。

同一旧渠道类型只能由一个插件拥有；冲突会在启用时检查。多个插件可以在同一宿主协议上声明相同模型，最终根据所选渠道决定使用哪个插件：旧渠道依据渠道类型，类型 61 渠道依据插件 key。

共享模型不代表用量字段或价格相同。应检查每个插件对应的[计费配置](/zh/docs/plugins/billing)。

## 配置后验证

使用可访问该分组和模型的 API 密钥，按[调用指南](/zh/docs/plugins/usage)发起一次小规模测试，确认任务创建、状态查询和产物读取均符合预期，再检查任务日志中的模型与用量。

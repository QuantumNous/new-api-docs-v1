## Common Operations

This section covers creating, editing, enabling, and disabling plans, followed by resetting the quota for subscriptions under a plan.

### Create a Subscription Plan

- Subscription Management – Create Plan

![Subscription Management – Create Plan Page](/assets/guide/feature-guide/subscription-management-create-subscription.png)

**Prerequisites**

- Root must accept the payment compliance terms under “System Settings” → “Billing & Payments” → “Payment Gateways”.
- Determine the plan’s intended users, price, validity period, total quota, and quota reset method.
- If the plan changes a user’s group, first create and verify the upgrade and downgrade groups in <a href="/en/docs/guide/feature-guide/system-settings/settings-billing#pricing-groups" target="_blank" rel="noopener noreferrer">Group Pricing</a>.
- If you need third-party payments, configure the corresponding gateway’s global credentials, callback URL, and webhook first.
- Decide whether users can purchase the plan with their wallet balance and whether they can continue using that balance after they exhaust the subscription quota.

<Callout type="warn" title="Caution">
Saving a plan does not make every payment method available. Third-party payments also depend on the plan’s product ID, global gateway configuration, callback reachability, and the product’s status on the payment platform.
</Callout>

**Steps**

1. Click “New Plan” on the Subscription Management page.
2. In “Basic Information”, enter the plan title, price, quota, groups, purchase limit, sort order, and any other applicable fields.
3. Choose whether to enable the plan immediately, allow purchases with wallet balance, and allow users to use wallet balance after exhausting the quota.
4. In “Validity Period Settings”, select the unit and enter the value.
5. In “Quota Reset”, select the reset cycle. If you select a custom cycle, enter the number of seconds.
6. To accept payments through Stripe, Creem, or Waffo Pancake, enter or select the corresponding product identifier.
7. Click “Save Changes”.

<Callout type="info" title="Tip">
The “Enabled” toggle determines whether the plan is visible to users as soon as you save it. The toggle is on by default for new plans.
</Callout>

**Configuration reference**

The drawer has four sections in the following order. “Basic Information”, “Validity Period Settings”, “Quota Reset”, and “Third-Party Payment Configuration”. The tables follow the drawer’s order.

**Basic Information (name, price, and groups)**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | Section | Definition | Requirements and Limits | Default |
| --- | --- | --- | --- | --- |
| Plan Title | Basic Information | The name shown in the admin list and on plan cards visible to users. | Required. A title containing only whitespace is rejected. | Blank |
| Plan Subtitle | Basic Information | Describes who the plan is for or summarizes its benefits. | Optional. Has no effect on billing. | Blank |
| Plan Price | Basic Information | The amount users pay for the plan. The payment channel determines the payment currency. | 0–9999. Plan prices are always stored in US dollars. The gateway configuration still governs the payment currency and settlement behavior. | `0` |
| Quota | Basic Information | The total quota included in the plan and available in each billing cycle. `0` means unlimited. | Must be non-negative. The label and unit follow the instance’s currency or token display settings. The quota is saved in the entitlement snapshot when a user subscription is created. | `0` |
| Upgrade Group | Basic Information | The group the user moves to when the subscription is created. | On creation, the system moves the user to the target group and records their pre-purchase group. If the target group does not exist, the plan cannot be saved. Options come from the current group configuration. | No Upgrade |
| Downgrade Group | Basic Information | The group the user moves to after the subscription expires. | When the subscription expires, is voided, or is deleted, the system gives priority to the specified group. If left blank, it attempts to restore the pre-purchase group when the applicable conditions are met. Options come from the current group configuration. | Revert to the pre-purchase group |

</div>

<Callout type="info" title="Tip">
The “Quota” field’s label and input increment follow the instance’s currency or token display settings. When you save the plan, the system converts the value to internal quota units. Enter the value using the unit displayed on your instance.
</Callout>

**Basic Information (purchase limit, sort order, and toggles)**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | Section | Definition | Requirements and Limits | Default |
| --- | --- | --- | --- | --- |
| Purchase Limit | Basic Information | The maximum number of subscription records a single user can have under this plan. | Must be a non-negative integer. The help text reads “0 means unlimited”. The count includes all of the user’s remaining subscription records for this plan, including expired and voided subscriptions and subscriptions added by an administrator. To free up a slot, delete a record. | `0` |
| Sort Order | Basic Information | The order in which plans are displayed. | Must be an integer. Higher values appear first in both the admin list and the user interface. Shown as “Priority” in the list. | `0` |
| Enabled | Basic Information | Whether the plan is visible to users and available through the standard purchase flow. | Existing subscriptions remain active when the plan is disabled. | On |
| Allow Wallet Balance Purchases | Basic Information | Whether users can buy the plan with their wallet balance. | When enabled, users with sufficient wallet balance can use it to buy the plan. When disabled, “Pay with Balance” is unavailable in the purchase dialog, which displays “This plan cannot be purchased with wallet balance”. | On |
| Allow Wallet Balance After Quota Is Exhausted | Basic Information | Whether users can continue using their wallet balance when their subscription quota is insufficient. | Saved in the entitlement snapshot when the subscription is created. Whether billing falls back to the wallet also depends on the user’s billing preference. | On |

</div>

**Validity period and quota reset**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | Section | Definition | Requirements and Limits | Default |
| --- | --- | --- | --- | --- |
| Validity Period Unit | Validity Period Settings | Determines how the subscription end time is calculated from its creation time. | Years, months, days, hours, or Custom (seconds). | Months |
| Validity Period Value | Validity Period Settings | The length of the validity period. Years and months follow the calendar, days are added in 24-hour increments, and hours are added as a fixed number of hours. | Must be a positive integer. Selecting “Custom (seconds)” replaces this field with “Custom Seconds”. | `1` |
| Custom Seconds | Validity Period Settings | Adds the specified number of seconds directly to the subscription creation time. | When the unit is “Custom (seconds)”, the value must be greater than `0`. A value of zero or less prevents subscription creation. | `0` |
| Reset Cycle | Quota Reset | Determines when the subscription quota next resets. | No Reset, Daily, Weekly, Monthly, or Custom (seconds). Daily resets advance to the next day, weekly resets to the next Monday, and monthly resets to the first day of the next month. | No Reset |
| Custom Seconds | Quota Reset | Adds the specified number of seconds to the reference time used for the current calculation. | Available only when the reset cycle is “Custom (seconds)”. The value must be greater than `0`. The system skips scheduling a reset if it would fall after the subscription end time. | `0` |

</div>

<Callout type="info" title="Tip">

- The system calculates and saves the validity period when it creates each user subscription. Later changes to the plan’s validity period have no effect on existing subscriptions.
- A quota reset sets used quota to zero. The plan’s total quota and the subscription end time stay the same.

</Callout>

**Third-party payments**

EPay has no plan-level product ID. Once EPay is enabled globally, at least one payment method is configured, and the plan price is at least `0.01`, users can create an EPay order at the plan price. Purchases with wallet balance also work without a third-party product ID.

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | Section | Definition | Requirements and Limits | Default |
| --- | --- | --- | --- | --- |
| Stripe Price ID | Third-Party Payment Configuration | Links the plan to a Stripe Price and creates the initial purchase session in Stripe Checkout’s `subscription` mode. | The global Stripe API Secret, Webhook Secret, and Stripe Price ID for top-ups must also be configured. The plan Price ID and the system-wide top-up Price ID are configured separately. The plan’s Price must support subscription mode. | Blank |
| Creem Product ID | Third-Party Payment Configuration | Links the plan to a Creem product. | The global Creem API Key, Webhook Secret, and product list must also be configured. The plan Product ID and system-wide top-up products are configured separately. | Blank |
| Waffo Pancake Product ID | Third-Party Payment Configuration | Selects a one-time product from the saved store to use for the plan. | The product list and “+ New” endpoints require Root and depend on the Merchant ID, Private Key, Store ID, and callback configuration. The gateway is currently considered enabled only if the system also has a Pancake Product ID for wallet top-ups. Use the designated Product ID for each purpose. | Blank |

</div>

<Callout type="warn" title="Caution">

- When an order is placed, Stripe uses the plan’s external Price ID and Creem uses its external Product ID. The third-party product determines the amount and currency charged. New API uses the local “Plan Price” in its lists and order records. Before publishing, verify that the external product and local price match exactly. Changes on either side require a manual update on the other side.
- Stripe plans use `subscription` mode to create recurring subscriptions. Stripe automatically renews the subscription at the interval specified by the selected Price until the subscription is canceled. Subsequent Stripe renewal charges have no effect on subscription creation or expiration in New API. The local subscription still expires according to the plan’s validity period. Before going live, verify how cancellation works in the Stripe Dashboard and tell users how renewals are handled.

</Callout>

**Create a Waffo Pancake product**

Clicking “+ New” next to “Waffo Pancake Product ID” uses the plan title and price from the current form to create and publish a one-time product in the saved Pancake store. The returned product ID is then entered in the form.

**Prerequisites for product creation**

- You are signed in as Root.
- The Waffo Pancake credentials and store are configured in Billing & Payments.
- The plan title is filled in.
- The plan price is greater than `0`.

<Callout type="warn" title="Caution">
This action creates the product on the third-party platform first. You still need to save the plan form. If Pancake creates the product but the plan fails to save, the product remains in Pancake. Check the third-party platform and remove the product if needed.
</Callout>

![Subscription Management – Edit Plan Page](/assets/guide/feature-guide/subscription-management-edit-subscription.png)

### Reset Subscription Quota

- Subscription Management – Reset Subscription Quota

![Subscription Management – Reset Subscription Quota Page](/assets/guide/feature-guide/subscription-management-reset-subscription-quota.png)

The reset action in the plan list applies to all active subscriptions under the selected plan.

**Steps**

1. Click the reset icon to the right of the target plan.
2. Choose whether to leave “Advance Next Reset Time” on. The toggle is on by default.
3. Click “Reset Quota”.

**Reset options**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Option | Behavior |
| --- | --- |
| “Advance Next Reset Time” on | Sets used quota to zero and recalculates the next reset time based on the plan’s current reset rules. |

- An audit log entry for each affected user reads “Administrator reset the quota for subscription plan … (ID: …)”. A separate entry is recorded for the administrator who performed the action. See [Audit Log](/en/docs/guide/feature-guide/user/audit-log#event-categories).

</Callout>

## Rules and Behavior

This section covers how plan edits and disabling affect existing subscriptions, how group upgrades and reversion work, how payment methods and renewals work, and how the system handles expiration and quota resets.

### Effects of Plan Changes

Plan edits primarily affect future purchases and new subscriptions. Existing subscriptions keep the entitlements recorded at creation.

**Effects by field**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Plan Fields | Effect on Existing Subscriptions |
| --- | --- |
| Price, Allow Wallet Balance Purchases, Enabled, Sort Order, payment product IDs | Affect future plan display or purchases. Purchased subscriptions keep their existing entitlements. |
| Validity period, total quota, upgrade group, downgrade group, Allow Wallet Balance After Quota Is Exhausted | Saved in the entitlement snapshot when the subscription is purchased. Plan edits leave the corresponding values in existing subscriptions intact. |
| Quota reset cycle, custom reset seconds | The system reads the plan’s current rules during automatic resets or when an administrator chooses to advance the next reset time. Changes may therefore affect existing active subscriptions. |
| Purchase limit | Future purchases and subscriptions added by administrators count existing records again and apply the current limit. |

</div>

**When a plan is disabled**

- Subscriptions users have already purchased continue without cancellation or suspension.
- Existing subscription quotas and end times stay the same.
- Past orders remain valid.
- Existing pending orders can still complete after a successful payment callback.
- Administrators can still add the plan for a specific user in User Management.

### Group Upgrades and Reversion

If the plan specifies an upgrade group, the system immediately attempts to move the user to that group when the subscription is created and records the user’s pre-purchase group in the subscription. When the subscription expires or an administrator voids or deletes it, the system applies the following rules in order.

1. If the user has another active subscription with an upgrade group configured, the user stays in their current group.
2. Otherwise, if the subscription specifies a downgrade group, the system moves the user directly to that group, even if someone manually changed the user’s group.
3. If the subscription has no downgrade group, the system restores the pre-purchase group only if the user is still in this subscription’s upgrade group. If the user was already in the upgrade group at the time of purchase, there is no pre-purchase group on record and the user stays in their current group.

<Callout type="warn" title="Caution">
Before voiding or deleting a subscription, check the user’s current group and any other active subscriptions.
</Callout>

### Payment Methods and Renewal Behavior

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Payment Method | Plan Requirements | How the Subscription Is Created |
| --- | --- | --- |
| Wallet Balance | “Allow Wallet Balance Purchases” is enabled, and the user has sufficient balance. | The system multiplies the plan price by the quota per US dollar, rounds up, deducts that amount from the internal quota balance, and creates one subscription immediately. |
| EPay | EPay is enabled globally and has an available payment method. The plan price is at least `0.01`. | A successful payment callback creates one subscription. No plan product ID is required. |
| Stripe | The plan has a Stripe Price ID, and the global Stripe and webhook configuration is complete. | Confirmation of the initial Checkout payment creates one local subscription. |
| Creem | The plan has a Creem Product ID, and the global Creem and callback configuration is complete. | A successful payment callback creates one subscription. |
| Waffo Pancake | The plan has its own Waffo Pancake Product ID, and the global credentials, store, and callback configuration are complete. | The user purchases a one-time product, and a successful callback creates one subscription. |

</div>

<Callout type="info" title="Tip">

- On the Wallet page, users can choose “Subscription First”, “Wallet First”, “Subscription Only”, or “Wallet Only”.
- “Allow Wallet Balance After Quota Is Exhausted” applies only when the user selects “Subscription First”. If the subscription quota is insufficient, billing falls back to wallet balance only if that option is enabled on every active subscription the user has. The user’s billing preference still takes precedence.
- For information about purchases, subscription status, and billing preferences, see <a href="/en/docs/guide/feature-guide/user/wallet" target="_blank" rel="noopener noreferrer">Wallet</a>.

</Callout>

### Automatic Maintenance

Background maintenance tasks handle subscription expiration and scheduled quota resets.

- The tasks run only on Master instances.
- The tasks run once after the service starts, then check approximately once per minute.
- Each batch processes up to 300 records.
- Expiration processing updates the subscription status and reverts the user’s group when the applicable conditions are met.
- Scheduled quota resets apply only to subscriptions that are still active.

## Saving Changes and When They Take Effect

Changes submitted on this page are written to the database immediately. The sections below explain how the system reads plans and user subscriptions.

**Plans**

Order placement, payment callbacks, purchases using wallet balance, subscriptions added by administrators, quota resets, and scheduled subscription quota resets all read from the plan cache. With Redis enabled, all nodes share the cache and changes take effect as soon as they are saved. In multi-instance deployments without Redis, other nodes usually pick up changes within about 3 seconds, with a default maximum delay of about 5 minutes.

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Operation | How to Save | When It Takes Effect |
| --- | --- | --- |
| Create a plan | Click “Save Changes” in the “Create Plan” drawer. The UI displays “Created successfully.” | The plan is saved immediately and appears in the user-facing plan list after it refreshes. |
| Edit the price, allow redemption using wallet balance, change the sort order, or edit the payment product ID | Click “Save Changes” in the edit drawer. The UI displays “Updated successfully.” | Changes apply only to how the plan is displayed and purchased going forward. Existing subscriptions retain their terms. |
| Edit the validity period, total quota, upgrade group, downgrade group, or whether users can pay from their wallet balance after using up their quota | Click “Save Changes” in the edit drawer. | The system saves a snapshot of these settings when a subscription is purchased. Existing subscriptions keep their saved settings. |
| Edit the quota reset cycle or custom reset interval in seconds | Click “Save Changes” in the edit drawer. | Existing active subscriptions use the new rules at the next automatic reset or when an administrator resets the quota with “Advance Next Reset Time” enabled. |
| Edit the purchase limit | Click “Save Changes” in the edit drawer. | The system recounts subscriptions against the new limit each time a user makes a purchase or an administrator adds a subscription. |
| Enable or disable a plan | Click the status icon and confirm in the “Confirm Enable” or “Confirm Disable” dialog. The UI displays “Enabled” or “Disabled.” | The plan immediately appears in or disappears from the user-facing plan list. Existing subscriptions, payment callbacks for pending orders, and subscriptions added by administrators are unaffected. |
| Reset subscription quotas | Click the reset icon, then click “Reset Quota” in the confirmation dialog. The UI displays “Reset quota for … active subscriptions.” | The reset runs immediately and applies only to active subscriptions under this plan that have yet to reach their end time. The system records one audit log entry for each affected user and one for the administrator who performed the reset. |

</div>

<Callout type="info" title="Environment Variables">

- `SUBSCRIPTION_PLAN_CACHE_TTL` sets the cache lifetime in seconds. It must be greater than 0 and defaults to 300.
- Restart the system after changing this environment variable to apply the new value.
</Callout>

**Subscriptions and Expiration**

User subscription changes are written directly to the database and take effect immediately on all nodes.

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Operation | How to Save | When It Takes Effect |
| --- | --- | --- |
| Add, reset, void, or delete a user subscription | Submit each operation individually under “User Management” → “Manage Subscriptions.” | Changes take effect immediately. ## Important Notes

- **Resetting subscription quotas affects all active subscriptions under the plan.** To reset a single user's quota, go to “User Management” → “Manage Subscriptions.” See [Reset Subscription Quotas](#reset-subscription-quota).
- **Voiding or deleting a subscription triggers a group rollback.** Check the user's current group and any other active subscriptions before proceeding. See [Group Upgrades and Rollbacks](#group-upgrades-and-reversion).
- **Editing a plan affects pending orders.** The payment callback reads the plan again when it completes the order. If you change the validity period, quota, or group while payment is pending, the user may receive different benefits from those available when they placed the order. See [Edit a Subscription Plan](#edit-a-subscription-plan).
- **Disabling a plan preserves existing subscription benefits.** The page has no option to delete a plan. See [Enable or Disable a Plan](#enable-and-disable-plans).
- **Payment availability depends on more than saving the plan.** Third-party payments also depend on the product ID, global payment gateway configuration, and payment callbacks. See [Create a Subscription Plan](#create-a-subscription-plan) and [Payment Methods and Renewal Limitations](#payment-methods-and-renewal-behavior).

<Accordion title="The subscription has expired, but its status is still Active or the user's group has not rolled back">

A background maintenance task on the Master instance processes expirations about once a minute. Once a subscription reaches its end time, the system stops deducting quota from it even if the task has yet to mark it as expired.

**Possible Causes**

- No Master instance is running.
- The background maintenance task failed, and the application logs contain the corresponding error.
- The subscription just expired, and the task has yet to run.

**Resolution**

1. Check whether the Master instance and the background task are running.
2. Review the application logs.
3. If you need to end the subscription immediately, void it under “User Management” → “Manage Subscriptions.”
</Accordion>

<Accordion title="Adding or purchasing a subscription shows “Purchase limit for this plan has been reached”">

**Exact Message**

“Purchase limit for this plan has been reached”

**Possible Cause**

The number of existing subscription records for this user under the plan has reached the purchase limit. Expired and voided subscriptions count toward the limit, as do subscriptions added by administrators.

**Resolution**

1. Increase the plan's purchase limit.
2. Alternatively, delete the user's old subscription records. Deletion is permanent.
</Accordion>

<Accordion title="Saving a plan returns an invalid parameter error">

The server displays the following messages when validation fails.

| Exact Message | Possible Cause | Resolution |
| --- | --- | --- |
| “Subscription plan title cannot be empty” | The plan title is blank. | Enter a title. |
| “Price cannot exceed 9999” | The price exceeds 9999. | Lower the price. |
| “Upgrade group does not exist” or “Downgrade group does not exist” | The selected group has not been created in Group Pricing. | Create the group first in <a href="/en/docs/guide/feature-guide/system-settings/settings-billing#pricing-groups" target="_blank" rel="noopener noreferrer">Group Pricing</a>. |
| “Custom reset cycle must be greater than 0 seconds” | The custom cycle is set to 0 seconds or less. | Enter a value greater than 0 seconds. |
</Accordion>

<Accordion title="Users cannot see a newly created plan">

**Possible Causes**

- The plan is disabled.
- Root has yet to confirm the payment compliance terms. Until then, the user-facing plan list is empty.

**Resolution**

1. Turn on the plan's “Enabled” setting.
2. Ask Root to confirm the compliance terms under “System Settings” → “Billing & Payments” → “Payment Gateway.”
</Accordion>

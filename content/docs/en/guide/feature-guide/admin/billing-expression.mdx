## Common tasks

This section covers opening the pricing editor, setting prices and request rules, estimating costs, converting legacy pricing, configuring task model pricing, and saving changes.

### Open the pricing editor

**Steps**

1. Open the pricing editor from any of these locations.
   - Under **System Settings** → **Billing & Payments** → **Model Pricing** → **Model Prices**, click **Add Model** or the edit icon in a model row.
   - In the **Models** list, click **Pricing** in a model row.
   - In the model edit drawer, select the **Pricing** tab.
2. Select **Billing Expression** in the billing mode tabs.
3. Under **Editor Mode**, select **Visual Editor** or **Expression Editor**.

<Callout type="info" title="Tip">

- Only Root users can view and edit model prices. When an Admin opens **Pricing** on the Models page, the page displays “Model pricing is managed by the super administrator.”
- All three entry points edit the same model pricing configuration. See [Save model prices](#save-model-prices).
- For the entry point on the Models page, see <a href="/en/docs/guide/feature-guide/admin/model#pricing" target="_blank" rel="noopener noreferrer">Model Management</a>.
</Callout>

### Set prices in the visual editor

**Steps**

1. Select **Visual Editor** under **Editor Mode**, or click a preset under **Preset Templates** as a starting point.
2. In the tier card, enter a **Tier Name** such as `base` or `standard`.
3. To add a conditional tier, click **Add Billing Branch** and configure **Tier Conditions** in the new card.
4. Under **Branch Billing Method**, select **Per Token** or **Per Call**.
5. If you select **Per Token**, select the price items you want to bill separately and enter their unit prices.
6. If you select **Per Call**, enter a **Price per Request**.
7. To price images or audio, expand **Media Pricing** and enter the prices.

<Callout type="info" title="Tip">

- Each tier corresponds to one `tier()` in the expression. The usage log records the name of the matched tier.
- **Add Billing Branch** inserts a conditional branch before the current tier.
- Rules are evaluated in order. The first match determines the tier.
- The last tier is the fallback. Its card displays **Fallback Tier** and “None of the preceding rules matched.” A single tier displays “Always matches (default tier)” and omits the **Fallback Tier** label.
- **Media Pricing** is collapsed by default and expands automatically when media prices are already set. Click **Media Pricing** to expand or collapse it manually.
</Callout>

### Configure request rules

- Billing expressions — tier conditions, fallback tier, and request rules

![Add model pricing — request rule example](/assets/guide/feature-guide/system-settings-billing-and-payments-model-pricing-model-prices-add-model-pricing.png)

**Request Rule Billing** appears only in the visual editor. It applies a Ratio to the final price based on request parameters, request headers, or time conditions.

**Steps**

1. Under **Request Rule Billing** at the bottom of the editing area, click **Add Rule Group**.
2. In the rule group, click **Add Parameter/Header** or **Add Time Condition** to add a condition.
3. Under **Ratio**, enter the Ratio to apply when the group matches.

<Callout type="info" title="Tip">

- The note below **Request Rule Billing** reads “When the conditions are met, the final price is multiplied by X. Ratios from matching rules are multiplied together. Values below 1 apply a discount.”
- Every condition in a group must be met for that group to match. Ratios from all matching groups are multiplied together.
- If the rule is too complex, the editor displays “This expression is too complex for the visual editor. Switch to expression mode to edit it.”
</Callout>

**Saved expression**

- Rules are saved as multiplication factors appended to the base expression, in the form `(base expression) * (condition ? ratio : 1)`. Switch to the expression editor to see them.
- A factor is recorded as a request rule in the usage log only if its condition references `param`, `header`, or a time function, its match value is numeric, and its non-match value is `1`.

**Configuration fields**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Field or action | Required input | Description |
| --- | --- | --- |
| Request Body Parameter | Parameter path, comparison operator, and value | Reads a JSON path from the original request body sent by the client. For example, use `service_tier` to distinguish service tiers. Operators include **Equals**, **Contains**, **Exists**, **Greater Than**, **Greater Than or Equal To**, **Less Than**, and **Less Than or Equal To**. |
| Request Header | Header name, comparison operator, and value | Matches the request headers actually sent. Operators include **Equals**, **Contains**, and **Exists**. |
| Time | Time field, time zone, and comparison value or range | Specify a time zone such as `Asia/Shanghai`. Time fields include **Hour**, **Minute**, **Day of Week**, **Month**, and **Day of Month**. Operators include **Equals**, **Greater Than or Equal To**, **Less Than**, and **Time Range**. Ranges include the start and exclude the end. A start greater than the end indicates a range that crosses midnight, such as 21 to 6. |
| Ratio | Ratio to apply | Every condition in a group must be met for that group to match. Ratios from all matching groups are multiplied together. A value below `1` applies a discount. |

</div>

<Callout type="warn" title="Caution">

- Before applying a surcharge based on a request parameter such as `service_tier`, verify that the Channel forwards the parameter to the upstream provider.
- Channels remove `service_tier` by default. Enable **Allow `service_tier` Passthrough** in the Channel. Otherwise, the user pays the surcharge while the upstream provider may still charge for standard service.
</Callout>

### Write expressions in the expression editor

Select **Expression Editor** under **Editor Mode** and enter the expression directly in the input field. The quick reference below the field lists the available variables and functions. For details on variables, functions, and syntax, see [Rules and behavior](#rules-and-behavior).

You can use an LLM to help design billing expressions. **LLM-Assisted Design Prompt** appears only in **Expression Editor** mode. The built-in prompt is in English and automatically includes the current model name at the end.

<div className="[&_pre]:w-full [&_pre]:whitespace-pre-wrap [&_pre]:break-words [&_[role=region]]:max-h-[400px]">

```text title="Copy the following prompt into an LLM such as ChatGPT or Claude to help design a billing expression"
You are an AI API billing expression design assistant. The user needs help designing a billing expression for an AI API gateway.

## Expression Language

Expressions are based on standard arithmetic with ternary operators.

### Token Variables

Input side:
- p — input token count (for pricing). Automatically excludes sub-categories priced separately (e.g., if cr is used, cache tokens are deducted from p)
- len — total input context length (for condition checks). Not affected by auto-exclusion; always reflects the full input length. Use in tier conditions
- cr — cache-hit (read) token count
- cc — cache-create token count (Claude 5-min TTL, OpenAI 30-min TTL)
- cc1h — cache-create token count (1-hour TTL, Claude-specific)
- cc12h — cache-create token count (12-hour TTL, OpenAI-specific)
- img — image input token count
- ai — audio input token count

Output side:
- c — output token count. Also auto-excludes sub-categories priced separately
- img_o — image output token count
- img_cr — image cache input tokens; deducted from img and cr only when the upstream reports a valid image cache breakdown
- ao — audio output token count

### p/c Auto-exclusion

p and c are fallback variables representing all tokens not separately priced in the expression. If the expression uses a sub-category variable (e.g., cr), those tokens are deducted from p to avoid double-billing. Unused sub-category tokens remain in p/c at base price.

Important: len is NOT affected by auto-exclusion. Tier conditions should use len instead of p to prevent cache hits from lowering p and misidentifying the tier.

### Built-in Functions

- tier(name, value) — labels the billing tier; must wrap the cost expression
- fixed(amount) — a finite non-negative USD price per request, used only as tier("name", fixed(0.01)); replaces token charges in that leaf. Other leaves may still use token prices. Group/request multipliers and existing tool surcharges still apply. Unsupported for task usage expressions and Realtime.
- max(a, b), min(a, b) — maximum/minimum
- ceil(x), floor(x), abs(x) — ceiling, floor, absolute value
- header(name) — reads a request header
- param(path) — reads a request body JSON path (gjson syntax)
- has(source, substr) — substring check
- hour(tz), minute(tz), weekday(tz), month(tz), day(tz) — time functions, tz is a timezone like "Asia/Shanghai"

### Price Coefficients

Numbers in the expression are $/1M tokens prices. For example, p * 2.5 means input $2.50/1M tokens.

## Expression Examples

Simple pricing:
tier("base", p * 2.5 + c * 15)

With cache:
tier("base", p * 2.5 + c * 15 + cr * 0.25)

Multi-tier (use len for conditions):
len <= 200000
  ? tier("standard", p * 3 + c * 15 + cr * 0.3 + cc * 3.75 + cc1h * 6)
  : tier("long_context", p * 6 + c * 22.5 + cr * 0.6 + cc * 7.5 + cc1h * 12)

Image model:
tier("base", p * 2 + c * 8 + img * 2.5)

Multimodal with audio:
tier("base", p * 0.43 + c * 3.06 + img * 0.78 + ai * 3.81 + ao * 15.11)

Three-tier example:
len <= 128000
  ? tier("standard", p * 1.1 + c * 4.4)
  : (len <= 1000000
    ? tier("medium", p * 2.2 + c * 8.8)
    : tier("long", p * 4.4 + c * 17.6))

## Rules

1. Every leaf branch must be wrapped in tier("name", cost_expr)
2. Use English tier names, e.g. "base", "standard", "long_context"
3. Use len for tier conditions (not p), supports <, <=, >, >=
4. Multi-tier uses nested ternary: cond1 ? tier(...) : (cond2 ? tier(...) : tier(...))
5. Price coefficients are the provider's official $/1M tokens prices
6. If cache/image/audio don't need separate pricing, omit those variables; their tokens are included in p/c automatically

Please generate a billing expression based on the model information and pricing requirements provided.

Current model: claude-opus-5-5
```

</div>

**Steps for LLM-assisted design**

1. Select **Expression Editor** under **Editor Mode**, then click **LLM-Assisted Design Prompt** to expand and view the built-in prompt.
2. Click **Copy Prompt** on the right side of the panel. If copying fails, select and copy the text manually.
3. Open a tool such as ChatGPT or Claude and paste the prompt into the chat input. Keep the built-in syntax instructions so the model can generate an expression in the supported format.
4. Append the model name, prices, pricing method, tier conditions, and Ratio rules. Specify the pricing units. If you are revising an existing expression, include it and identify the parts to change.
5. Send the full prompt and ask the LLM for a ready-to-paste expression, an explanation of the rules, and test cases.
6. Check the prices, variables, condition boundaries, and Ratios, then paste the expression itself into the input field.
7. Enter usage in the **Token Estimator** and check the cost and matched tier. For request or time conditions, also use **Request Simulation**.
8. If the result differs from what you expect, share the expression, error message or test inputs, actual result, and expected result with the LLM. Once the results match, save the expression. See [Save model prices](#save-model-prices).

<Callout type="info" title="Tip">

- Provide pricing information explicitly so the LLM has more than the model name to work from.
- If information is missing or ambiguous, ask the LLM to confirm the details before filling in prices or rules.
- Paste only the expression itself, omitting Markdown fences, explanations, and test data.
- Test just below, at, and just above each threshold, as well as cases with missing fields. Request simulation excludes Group Ratios.
- Copying the prompt or editing a simulation example leaves the pricing configuration in draft.
</Callout>

### Estimate costs and simulate requests

The **Token Estimator** appears below the editing area. It contains a **Request Simulation** section that is collapsed by default. Both tools calculate results in the browser for preview purposes.

**Steps**

1. Enter **Input Tokens** and **Output Tokens** in the **Token Estimator**. To test tier boundaries, enter **Override Total Input Context Length**.
2. Check the **Estimated Cost** and **Matched Tier**.
3. If the expression includes request rules, request conditions, or time conditions, click **Request Simulation** to expand it.
4. Fill in **Simulated Request Body** and **Simulated Request Headers**, then choose a **Simulation Time**.
5. Check the **Simulated Request Cost**, **Matched Tier**, and whether each rule matched.

<Callout type="info" title="Tip">

- The estimator evaluates only the base expression, excluding request rules and Group Ratios. Request simulation includes request rules and excludes Group Ratios.
- Request simulation recalculates automatically when the input changes.
- For task model expressions, the estimator displays “This expression requires task usage data to estimate costs. Check the model's task plugin configuration.”
</Callout>

### Convert from a legacy mode

**Steps**

1. Select **Per Token (Deprecated)** or **Per Request (Deprecated)** in the billing mode tabs.
2. Click **Convert to Billing Expression** below the notice.
3. Review both sides of the **Pricing Migration Preview**, then click **Apply to Draft**.
4. Click **Save Model Prices**. See [Save model prices](#save-model-prices).

<Callout type="info" title="Tip">

- The legacy mode tab displays “Legacy pricing modes are deprecated. Convert the current price to a billing expression draft, then save it to apply the change.”
- If a billing expression draft already exists, the button is disabled and the panel displays “A billing expression draft already exists. Open the Billing Expression tab to continue editing.”
- If conversion is unavailable, the panel displays the reason. See the conversion rules below.
</Callout>

**Conversion rules**

- Per Token mode generates `tier("base", p * … + c * … …)`. The base input unit price is the model Ratio × 2, in USD per million Tokens at the default Quota per USD. The configured completion, cache, and image Ratios determine the corresponding terms.
- Per Request mode generates `tier("request", fixed(price))`.
- Per-image pricing generates `tier("image", fixed(price)) * image_count` and carries over the existing size and quality Ratios.
- Automatic conversion is unavailable for task plugin models, video, Realtime, OpenRouter Claude pricing that infers cache writes from upstream costs, models with different audio prices on the Gemini and OpenAI interfaces, models without a configured input price, models whose routing cannot be verified, and models already using a billing expression.
- Conversion retains the legacy price fields, so you can switch back to the old mode.
- After conversion, pre-deduction and rounding follow billing expression rules. The effective unit price stays the same, though individual charges may differ slightly after rounding.

### Set task model prices

For models provided by task plugins, such as video or asynchronous image models, an extra row of provider tabs appears at the top of the editor. It includes **Default Price**, **Regular Price** when the model is priced by task usage, and a tab for each plugin.

**Steps**

1. Open the model's pricing editor and set the model-level expression or price in the **Default Price** tab.
2. To set a separate price for a plugin, open its tab.
3. Enable **Set a Separate Price for This Provider** and configure the plugin's price.
4. Click **Save Model Prices**. See [Save model prices](#save-model-prices).

<Callout type="info" title="Tip">

- When **Set a Separate Price for This Provider** is off, the plugin inherits the model-level expression or price.
- If a plugin cannot evaluate the model-level expression, the **Default Price** tab displays “The following providers cannot evaluate the model-level expression: …” Click a plugin name to open its tab.
- The **Regular Price** tab displays “Set a separate regular price and keep existing plugin prices. Changes take effect after saving.” Click **Configure Regular Price** to set the price for regular requests.
- If a plugin no longer provides the model, its tab displays “This provider currently does not provide this model.”
- If the plugin has a saved price, click **Delete Saved Price** to remove it.
- For task expression syntax, inheritance rules, and the **Pricing Pending** status, see [Task models](#task-models).
</Callout>

### Save model prices

Editor changes remain in the draft until you click **Save Model Prices**. The save flow depends on where you opened the editor.

**Save from Billing & Payments**

1. Under **Billing & Payments** → **Model Pricing** → **Model Prices**, click **Save Model Prices**.
2. In **Confirm Price Changes**, review the **Current Price** and **Price After Saving** for each model.
3. Click **Confirm Save** to submit the entire batch.

**Save from the Models page**

## Rules and behavior

This section covers expression units and Quota conversion, usage variables, functions and syntax, pre-deduction, settlement, logs, task model pricing, and validation on save.

### Units and Quota conversion

Price coefficients in expressions are denominated in USD. The system converts the result to Quota using the rules below.

**Conversion rules**

- **Units.** Token coefficients are in USD per million Tokens. `p * 2.5` means $2.50 per million input Tokens, and `fixed(0.01)` means $0.01 per request.
- **Conversion.** Quota equals the expression result ÷ 1,000,000 × Quota per USD (500,000 by default) × Group Ratio, rounded to the nearest integer.
- **Version prefix.** An expression can start with `v1:`. Expressions without a prefix use v1.

**Conversion examples**

- For `tier("base", p * 2 + c * 8)` with 1,000 input Tokens, 500 output Tokens, and a Group Ratio of 1, the result is 6,000, or $0.006. At the default Quota per USD, the charge is 3,000 Quota.
- The system also multiplies the `fixed()` amount by 1,000,000 internally before including it in the result. Under the same conditions, `fixed(0.01)` charges 5,000 Quota per request.

### Usage variables

**Variables**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_td:nth-child(2)]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Variable | Name | Definition |
| --- | --- | --- |
| `len` | Full Input Context Length | Used to select a tier by length, independently of the automatic deductions below. For non-Claude formats, it equals the total input Tokens reported by the upstream provider. For the Claude format, it equals the sum of text input, cache read, and cache creation Tokens. |
| `p` | Base Input Tokens | Usage billed at the base input price. Cache, image, and audio input priced separately in the expression is automatically deducted from `p`. Other input usage remains in `p`. |
| `c` | Base Output Tokens | Usage billed at the base output price. When the expression prices `img_o` or `ao` separately, that usage is automatically deducted from `c`. |
| `cr` | Cache Read Tokens | Input usage that hits and reuses an existing prompt cache. |
| `cc` | Cache Creation Tokens | Claude's 5-minute cache writes, OpenAI's 30-minute cache writes, or generic cache writes from other upstream providers. |
| `cc1h` | 1-Hour Cache Creation Tokens | Claude's 1-hour cache creation usage. `1h` is the cache lifetime. |
| `cc12h` | 12-Hour Cache Creation Tokens | OpenAI's 12-hour cache write usage. |
| `img` | Image Input Tokens | Token usage associated with input images. |
| `img_cr` | Image Cache Read Tokens | Image input usage served from cache. The system separates this usage only when the expression references `img_cr` and the upstream provider supplies a valid image cache breakdown. Otherwise, the value is 0. |
| `img_o` | Image Output Tokens | Output Token usage associated with model-generated images. |
| `ai` | Audio Input Tokens | Token usage associated with input audio. |
| `ao` | Audio Output Tokens | Output Token usage associated with model-generated audio. |
| `image_count` | Billable Image Count | Number of images billed individually. Accepts an integer from 1 to 128 and defaults to 1 if omitted. It can multiply a `fixed()` tier. Pre-deduction uses the requested count, and settlement uses the actual number returned. |

</div>

**Deduction rules**

- Suppose the upstream provider reports 1,000 input Tokens, including 200 cache read Tokens and 100 image Tokens. In `p * 3 + c * 15`, `p = 1000`. In `p * 3 + c * 15 + cr * 0.3`, `p = 800`. Adding `img * 2` reduces `p` to 700.
- These automatic deductions apply only to non-Claude formats such as OpenAI. Input Tokens reported in the Claude format already exclude cache usage, so cache reads and writes without separate prices are added to the input count. If deductions bring `p` or `c` below 0, that variable is set to 0.
- When long-lived cache writes lack separate prices, `cc1h` is billed at 1.6 times the `cc` price and `cc12h` at twice the `cc` price. If `cc` also lacks a separate price, the same factors apply to the `p` price.

### Functions

**Pricing and numeric functions**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Function | Parameters | Behavior and return value | Example |
| --- | --- | --- | --- |
| `tier(name, value)` | `name` is the tier name string. `value` is the pricing expression. | Returns the pricing result and records the matched tier name. | `tier("base", p * 2 + c * 8)` |
| `fixed(amount)` | `amount` is a finite, non-negative numeric literal in USD per request. | Sets the base per-request price. Place it directly in the second argument of `tier()`. The tier can be multiplied by `image_count` or a request rule Ratio. Adding a fixed tier to Token charges or summing multiple `tier()` calls is invalid. These rules also apply to branches that can never match. Realtime requests and task usage expressions exclude `fixed()`. Group Ratios, request rule Ratios, and tool call surcharges still apply. | `tier("request", fixed(0.01))`, `tier("image", fixed(0.04)) * image_count` |
| `max(a, b)` | Two numeric values. | Returns the larger value. Use it to set a lower bound. | `max(p * 2 + c * 8, 1000)` sets a minimum charge of $0.001 for the Token expression. |
| `min(a, b)` | Two numeric values. | Returns the smaller value. Use it to cap a value. | `min(p, 100000)` caps input usage at 100,000. |
| `ceil(x)` | One numeric value. | Rounds up to the next integer if needed. | `ceil(1.2)` returns `2`. |
| `floor(x)` | One numeric value. | Rounds down to the previous integer if needed. | `floor(1.8)` returns `1`. |
| `abs(x)` | One numeric value. | Returns the absolute value. | `abs(-2)` returns `2`. |

</div>

**Request functions, usage functions, and reserved names**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap [&_td_code]:wrap-anywhere">

| Function | Parameters | Behavior and return value | Example |
| --- | --- | --- | --- |
| `header(name)` | `name` is the request header name string. | Reads a header sent by the client and returns its value as a string. Names are case-insensitive. Leading and trailing whitespace is trimmed from names and values. Missing headers return an empty string, and headers with empty values are treated as missing. If a name occurs more than once, the function uses only the first value. | `header("service-tier") == "priority"` |
| `param(path)` | `path` is the request body field path string. | Returns the field value with its original type, such as string, number, or boolean. Missing fields return `nil`. Supports dot-separated paths for nested fields. Reads only the original client request body with a JSON `Content-Type`. For image generation requests with expressions that use `image_count`, only `model`, `n`, `size`, `quality`, and `parameters` are available. | `param("service_tier") == "priority"`, `param("stream_options.fast_mode") == true` |
| `has(source, text)` | `source` is the value to check. `text` is the substring to find. | Converts a non-`nil` source to text and performs a case-sensitive substring check. Returns `false` if the source is `nil` or the search text is empty. | `has(header("anthropic-beta"), "fast-mode")` |
| `u(key)` | `key` is the name of a usage field declared by the task plugin. | Reads usage reported by a task plugin and is available only for task models. Using `u()` in an expression for a regular model causes validation to fail on save. See [Task models](#task-models). | `u("seconds") * 0.4` |
| `_trace`, `_trace_int` | — | Reserved for internal use and unavailable in expressions. | — |

</div>

**Time functions**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Function | Return value | Example |
| --- | --- | --- |
| `hour(tz)` | Hour, `0–23`. | `hour("Asia/Shanghai") >= 21` matches 21:00 or later local time. |
| `minute(tz)` | Minute, `0–59`. | `minute("UTC") < 30` matches the first 30 minutes of the current hour. |
| `weekday(tz)` | Day of the week, `0–6`, where `0` is Sunday and `6` is Saturday. | `weekday("Asia/Shanghai") == 0` matches Sundays. |
| `month(tz)` | Month, `1–12`. | `month("Asia/Shanghai") == 12` matches December. |
| `day(tz)` | Day of the month, `1–31`. | `day("Asia/Shanghai") == 1` matches the first day of each month. |

</div>

<Callout type="info" title="Tip">

- Use an IANA time zone name such as `Asia/Shanghai` or `UTC`. The visual editor flags invalid time zones in tier conditions. In the expression editor, a misspelled or blank time zone silently defaults to UTC in both server-side evaluation and browser simulation.
- Pre-deduction and settlement each evaluate the expression at their respective times. If a request crosses a time boundary, the time window at settlement, when the request ends, determines the final charge.
</Callout>

### Common syntax

**Operators and literals**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Syntax | Meaning | Example |
| --- | --- | --- |
| `+`, `-`, `*`, `/` | Addition, subtraction, multiplication, and division. | `p * 2 + c * 8` |
| `>`, `>=`, `<`, `<=` | Numeric comparisons that return a boolean. | `len <= 200000` |
| `==`, `!=` | Equality and inequality. | `param("priority") == true` |
| `&&` | Logical AND. Both conditions must be true. | `len < 32000 && c < 200` |
| `\|\|` | Logical OR. At least one condition must be true. | `hour("UTC") >= 21 \|\| hour("UTC") < 6` |
| `!` | Logical negation. | `!(param("priority") == true)` |
| `condition ? A : B` | Evaluates A if the condition is true, or B otherwise. | `len <= 200000 ? tier("short", p * 2) : tier("long", p * 4)` |
| `(...)` | Groups terms to control evaluation order. | `(base expression) * (condition ? 2 : 1)` illustrates the structure. Replace the placeholders with an expression and a condition. |
| `"text"`, `true`, `false`, `nil` | String, boolean, and null values. | `true` is a boolean, while `"true"` is a string. |

</div>

### Pre-deduction, settlement, and logs

Before sending a request, the system pre-deducts Quota based on estimated usage. After the upstream provider responds, it settles the charge based on actual usage and records the billing details in the usage log.

**Processing rules**

- **Pre-deduction.** Before sending the request, the system uses locally estimated input Tokens for both `p` and `len` and sets `c` and all other usage variables to 0.
- **Pre-deduction Ratio.** The **Input Pre-deduction Ratio** applies only to Token-priced tiers. The Group Ratio is applied last. See <a href="/en/docs/guide/feature-guide/system-settings/settings-billing#quota-settings" target="_blank" rel="noopener noreferrer">Quota Settings</a>.
- **Conditions during pre-deduction.** Branch conditions that reference `c` are always evaluated with `c = 0` during pre-deduction.
- **Negative pre-deduction.** The system rejects the request if the pre-deduction result is below 0.
- **Settlement.** After the upstream response arrives, the system evaluates the expression again using actual usage and refunds or charges the difference. If evaluation fails at settlement, the system settles at the pre-deducted amount.
- **Logs.** The usage log records the matched tier (`matched_tier`), billing unit (`billing_unit`), per-request price (`fixed_price`), image count (`image_count`), request rules and whether each matched (`request_rules`), and the full base64-encoded expression (`expr_b64`). Users can see these fields in their own log details, so keep expression content suitable for users to read.

### Task models

Models provided by task plugins are priced using the usage reported by the plugin. For editor steps, see [Set task model prices](#set-task-model-prices).

**Pricing rules**

- Task expressions use `u("field")` to read usage reported by the plugin, such as seconds or image count. The result is already in USD and requires no division by 1,000,000.
- `fixed()` is unavailable in task expressions.
- Task expressions cannot read chat request quantities such as Token counts or `image_count`. Attempting to save such an expression displays `task usage expressions cannot read chat request quantities …` in English.
- When a plugin also forwards regular requests for the same model, the model-level price applies to regular requests.
- In that case, tasks inherit the model-level price only if it is a legacy **Per Request (Deprecated)** price or an expression containing `u()`. Otherwise, set a separate price in that plugin's tab.
- If a separate price is required and missing, submitting a task displays “Model … has no task price for plugin …. Set a separate price for this plugin in model pricing.”
- For plugin usage fields, plugin-level price overrides, and validation on save, see <a href="/en/docs/plugins/billing" target="_blank" rel="noopener noreferrer">Usage and Billing</a>.

**Pricing Pending**

- If a task model cannot be billed, **Pricing Pending** appears next to its name in the model price list. The reason is one of “No price has been set,” “The price uses a usage field that the plugin no longer provides,” or “The plugin no longer provides this model.”
- For resolution steps, see <a href="/en/docs/guide/feature-guide/system-settings/settings-billing#pricing-pending-review" target="_blank" rel="noopener noreferrer">Billing & Payments Configuration</a>.

### Validation on save

When you save, the server validates each model's expression. If any expression fails validation, the server rejects the entire batch.

**Validation rules**

- Expressions must compile. `u()` is available only for task models.
- The server then evaluates seven fixed usage vectors, including an all-zero vector and one with a very large `len`. It tests each vector with two request contexts. One is an empty request. The other includes the `anthropic-beta: fast-mode-2026-02-01` header and a body with `service_tier: fast`.
- Every test result must be finite and non-negative.
- These tests leave branches triggered by other request parameters, request headers, or time conditions unchecked.
- For validation error messages, see [FAQ](#faq).

## Saving and applying changes

Editor changes remain in the draft until you click **Save Model Prices**. For the workflow, see [Save model prices](#save-model-prices). For how system settings are saved, see <a href="/en/docs/guide/feature-guide/system-settings/system-setting#save-methods" target="_blank" rel="noopener noreferrer">System Settings Overview</a>. Model prices are stored as system settings and take effect as follows.

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Where | When changes take effect |
| --- | --- |
| Node handling the save request | Uses the new prices for pre-deduction and settlement starting with the next request. |
| Other nodes | Use the new prices after system settings synchronize, typically within about 3 seconds and at most within one synchronization cycle, which defaults to 60 seconds.<br/>Until synchronization completes, they use the previous prices. See <a href="/en/docs/guide/feature-guide/system-settings/system-setting#scope-and-multi-instance-synchronization" target="_blank" rel="noopener noreferrer">Scope and Multi-Instance Synchronization</a>. |
| Requests with completed pre-deduction | Settle using the expression in effect at pre-deduction. |
| Asynchronous tasks already submitted | Continue using the expression in effect at submission. |
| Model Marketplace | The node handling the save request updates prices immediately. Other nodes update after system settings synchronize, typically within about 3 seconds. Users with the Model Marketplace already open see the new prices after refreshing the page. |

</div>

**Additional details**

- **Invalid drafts.** If the visual editor contains invalid fields, saving is disabled and the editor displays “Correct the invalid fields before saving or switching modes. The last valid expression has been retained.”
- **Batch saves.** When several models are submitted at once, a validation failure for any model rejects the entire batch and leaves existing prices in effect. See [Validation on save](#validation-on-save).
- **Version conflicts.** If someone changes the pricing after you open the page, the server rejects your save. Click **Reload Pricing**, then make your changes again.

## Important notes

- **Validation tests cover only some branches.** Branches triggered by other request parameters, request headers, or time conditions are outside the test set. Ensure each branch produces a non-negative result. See [Validation on save](#validation-on-save).
- **Restore Default Pricing clears custom prices.** Running this action in the model's **Pricing** tab removes its custom prices, including billing expressions, and restores the built-in defaults. Models without a default price become unpriced. See <a href="/en/docs/guide/feature-guide/admin/model#pricing" target="_blank" rel="noopener noreferrer">Model Management</a>.
- **Billing fields are visible to users.** The full expression and other billing fields appear in users' own log details. See [Pre-deduction, settlement, and logs](#pre-deduction-settlement-and-logs).
- **Request parameter surcharges require Channel forwarding.** Channels remove `service_tier` by default. See [Configure request rules](#configure-request-rules).

The Token Estimator excludes request rules and Group Ratios. Request simulation excludes Group Ratios. At settlement, the system recalculates the charge using actual usage and the settlement time, applies the Group Ratio, and adds any tool call surcharges separately.

**Possible causes**

- The condition uses `p`. Cache hits can reduce `p`, so use `len` for input length conditions.

</Accordion>

**Possible cause.** A misspelled or blank time zone in a time function silently defaults to UTC.
</Accordion>

`param()` reads only JSON request bodies.

**Resolution**

1. Use **Request Simulation** to check whether the rule is marked **Matched**.
2. Check the request rule entry in the usage log.
</Accordion>

**Possible causes**

- The expression has a syntax error or refers to a variable or function that does not exist.
- The expression uses a reserved name. In that case, the message also contains `identifier "_trace" is reserved for internal use`.

**Resolution**

1. Check spelling, parentheses, quotation marks, and commas.
2. Replace any reserved name with a different name.

**Possible causes**

- The amount in `fixed()` is something other than a non-negative numeric literal.
- The expression adds a `fixed()` tier to Token charges or otherwise uses an invalid structure.

**Resolution**

1. Use a numeric literal for the amount, as in `fixed(0.01)`.
2. Write each per-request tier as `tier(name, fixed(amount))`.

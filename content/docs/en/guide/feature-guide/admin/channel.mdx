## Common Operations

This section follows the order in which you typically work with channels. It covers creation and editing, the three specialized channel types (plugin, gateway, and advanced custom), and maintenance tasks such as testing connections, checking balances, updating models, duplicating channels, enabling, disabling, and deleting channels, managing tags and priorities, managing multiple keys, and repairing channel consistency.

### Create and Edit Channels

**Steps**

1. Click “Create Channel” in the upper-right corner of the page. To edit a channel, click the edit icon in its row or select “Edit” from the card's ⋯ menu.
2. Select a provider or plugin in the picker.
3. Turn on any quick options you need at the top of the drawer.
4. Complete the four tabs in order: “Connection and Models,” “Routing and Mapping,” “Request and Response,” and “Other Settings.”
5. Click “Create Channel” or “Update Channel.”

<Callout type="info" title="Tip">

- Use “Change Provider” below the drawer title to select a different type or plugin.
- A status indicator next to each tab shows “Incomplete,” “Error,” “Ready,” or “Configured.”
- If your account lacks the “Edit Sensitive Channel Settings” permission, the top of the drawer displays “Your account has view-only access to sensitive channel settings. You can still edit non-sensitive operational fields such as models, groups, priority, and weight.”
- When you save, the page validates the form first. The server then checks the channel type, credentials, plugin bindings, and advanced settings.

</Callout>

**Choose a channel type**

- **Standard provider or protocol**. Select a built-in channel and follow the guidance for its credentials and default URL.
- **Installed plugin**. Select “Plugin,” verify the plugin's models, upstream type, and default URL, then configure the credentials it requires.
- **New API or Sub2API upstream gateway**. Select “Gateway” to use the gateway adapter. The legacy Custom type (#8) cannot substitute for it.
- **Multiple inbound paths, protocols, or providers**. Select Advanced Custom. Define the inbound paths, upstream paths, authentication, and transformers first.

### Standalone Plugin Channels

- Channel Management - Plugin Channels

![Channel Management - Plugin Channels page](/assets/guide/feature-guide/create-channel-plugin-channel.png)

For plugins that provide a channel component, you can test the channel, fetch models, check for upstream model updates, and check the balance if the plugin provides it. The models declared by the plugin serve as initial values. Check the connection to verify that the upstream credentials work. The models, routes, and request types a plugin supports may vary by installed version.

On shared endpoints such as `/v1/images/generations`, `/v1/images/edits`, `/v1/responses`, and `/v1/videos`, standard and plugin channels that serve the same model are selected together based on Group, priority, and weight. When the system selects a standard channel, that channel forwards the request directly, bypassing the plugin.

**Prerequisites**

- The account must have the “Bind Task Plugins” permission for the “Plugins” category to appear in the selection dialog.
- The target plugin must be installed and enabled. See <a href="/en/docs/guide/feature-guide/admin/task-plugins#create-a-plugin-channel" target="_blank" rel="noopener noreferrer">Plugin Management</a>.

**Steps**

1. Select a registered plugin from the “Plugins” category.
2. Enter the credentials, Group, and other fields required by the plugin. The plugin provides the “Key Format” hint below “API Key”.
3. If the plugin declares settings, fill in the “Plugin Settings” section.
4. Click “Create Channel”. For plugins that require signing in to an upstream account, click “Save and Sign In”.
5. After saving, the sign-in window opens automatically. Follow the prompts to sign in.

<Callout type="info" title="Tip">

- When you select a plugin, its name fills the name field if the field is empty. The plugin’s declared models and default URL are also prefilled.
- If the plugin has a default URL, “Plugin Default: …” and “Use Default” appear below “API URL”. Otherwise, enter a URL.
- In “Plugin Settings”, unchanged fields retain their saved values, and blank fields use the plugin defaults. If validation fails, the message reads “Fix the highlighted fields before saving.”
- If you change the plugin while editing a channel, save the channel before signing in.
</Callout>

**Credentials**

For plugins that require signing in to an upstream account, “Connection and Models” displays a “Credentials” section in place of “API Key”.

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

</Callout>

### Gateway Channels: New API and Sub2API

- Channel Management - New API Gateway Channel

![Channel Management - New API Gateway Channel page](/assets/guide/feature-guide/create-channel-newapi-gateway-channel.png)

New API and Sub2API both append the request path to the gateway Base URL. The standard configuration leaves `/v1` out of the Base URL, so enter a Base URL without a trailing `/v1`. Both gateways can support OpenAI, Responses, Claude, Gemini, and other APIs. The available capabilities depend on the gateway deployment.

In New API, you can also use “Upstream Task Plugins” to bind task plugin extensions that support a New API upstream. The field description reads “This channel will provide the models from each selected plugin. The upstream New API gateway must have the same plugins installed.” These extensions run as part of the New API gateway channel (#60). [Standalone plugin channels](#standalone-plugin-channels) use a separate channel type.

<Callout type="info" title="Tip">

### How Pass-Through and Overrides Interact

- Channel Management – Confirm Request Body Pass-Through

![Channel Management – Confirm Request Body Pass-Through page](/assets/guide/feature-guide/create-channel-pass-through-request-body-description.png)

- Channel Management – Confirm Request Header Pass-Through

![Channel Management – Confirm Request Header Pass-Through page](/assets/guide/feature-guide/create-channel-pass-through-request-headers-description.png)

Before pass-through is enabled, a confirmation dialog lists the features that will become unavailable. Click “Confirm and Enable Pass-Through” to apply the setting.

**Execution Rules**

- Global or Channel-level request body pass-through bypasses the normal conversion pipeline. Model mapping, parameter overrides, and protocol conversion may no longer follow the standard processing path.
- When “Pass Through Request Body” is enabled for a Channel, instances configured for the “Before Format Conversion” and “Before Sending” stages on the sidebar’s “Request Processing” page are skipped. Instances added to this Channel for the “Before Reading the Request” stage are also skipped. “Final Check” and “Check Response” run as usual. See <a href="/en/docs/guide/feature-guide/admin/request-processing#important-notes" target="_blank" rel="noopener noreferrer">Request Processing</a>.
- Request header pass-through uses `*` or `re:`/`regex:` rules to copy client request headers. It excludes Authorization, `x-api-key`, `x-goog-api-key`, WebSocket handshake headers, and other security headers.
- Request header overrides are applied after pass-through, so explicit overrides take precedence. `{client_header:NAME}` must be the entire value. The header is omitted if the client did not send it.
- Select streaming mode in the client request. Rewriting `stream` in the JSON with a parameter override does not guarantee that the gateway, adapter, and upstream service will switch streaming modes together.

**Field Pass-Through Controls**

- All “Field Pass-Through Controls” toggles under “Request and Response” are off by default and are shown by Channel type. “Allow `service_tier` Pass-Through” applies to all types shown in this section.
- OpenAI-type Channels also offer “Block `store` Pass-Through,” “Allow `safety_identifier` Pass-Through,” “Allow `include` Usage Obfuscation Pass-Through,” and “Allow Inference Geography Pass-Through.”
- Claude-type Channels also offer “Allow `speed` Pass-Through.” Anthropic Channels additionally offer “Allow `inference_geo` Pass-Through” and “Allow Claude Beta Query Pass-Through.”

### Parameter Override System

- Channel Management – Parameter Overrides

![Channel Management – Parameter Overrides page](/assets/guide/feature-guide/create-channel-request-and-response-parameter-overrides-visual-editor.png)

Parameter overrides run after request conversion and before the request is sent upstream. They provide limited protocol conversion and do not automatically synchronize the client’s streaming state. The visual editor and JSON mode write to the same set of parameter override rules.

**Execution Order and Scope**

- Overrides run only when the request enters the corresponding relay processing path. Request body pass-through bypasses normal conversion and parts of the override pipeline.
- <a href="/en/docs/guide/feature-guide/admin/request-processing#global-parameter-override" target="_blank" rel="noopener noreferrer">Global Parameter Override</a> instances on the sidebar’s “Request Processing” page run before Channel-level parameter overrides. The Channel setting takes precedence for the same parameter. The global “Return Custom Error” operation always returns HTTP 400.
- Rules in the `operations` array run in array order. Each operation’s output becomes the input to the next operation.
- When both legacy top-level fields and the `operations` array are present, the legacy fields are applied first, followed by the operations.
- When a session rule matches, its parameter override template is merged with the Channel’s parameter overrides. See <a href="/en/docs/guide/feature-guide/system-settings/settings-request-policies#session-and-retry" target="_blank" rel="noopener noreferrer">Sessions and Retries</a>.
- Conditions default to “Match Any Condition (OR).” Select “Match All Conditions (AND)” (`logic: "AND"`) to require every condition to match.
- Conditions read the current request JSON and runtime context. If an earlier operation changes the model, a later condition may read the updated value. Context values such as `original_model` and `upstream_model` are not automatically written to the request JSON.
- “Return Custom Error” (`return_error`) ends the request early and returns a custom error. Supported status codes and error fields depend on what the backend can parse. The values an input field accepts may extend beyond what the backend supports.
- If a condition comparison fails, the request fails with `channel:param_override_invalid` and is handled as a Channel error. Examples include operands of different types in an “Exact Match” (`full`), a nonnumeric operand in a numeric comparison, or an invalid regular expression (`regex`).

**Visual Editor and JSON**

Under “Request and Response,” click “Visual Editor” to open the “Parameter Overrides” dialog. Under “Mode,” select “Visual” or “JSON Text.” Use Visual mode to edit rules individually and JSON mode to copy the complete rule set.

**Operation Quick Reference for Fields and Values**

| Exact Match (`full`), Prefix (`prefix`), Suffix (`suffix`), Contains (`contains`) | Match methods for strings or other comparable values. |
| Regular Expression (`regex`) | Matches the string representation of a field against a regular expression. The condition value must be a string. |
| Greater Than (`gt`), Greater Than or Equal To (`gte`), Less Than (`lt`), Less Than or Equal To (`lte`) | Both operands must be JSON numbers. Arbitrary strings cannot be used as numbers in these comparisons. |
| Invert Match (`invert`) | Inverts the match result. “Pass If Field Is Missing” (`pass_missing_key`) is evaluated first to determine whether a missing field passes. |
| Pass If Field Is Missing (`pass_missing_key`) | Allows the condition to pass if the path is missing. By default, the condition does not pass. |
| Match Any Condition (OR), Match All Conditions (AND) (`logic`) | “Match All Conditions (AND)” requires every condition to pass. The default is “Match Any Condition (OR).” |
| JSON Path | Supports paths such as `messages.0.content` and `messages.-1.content`. |
| Runtime Context | Supports matching on context values such as the original model, upstream model, user, and Group. These names are runtime context keys and should not be treated as fixed request body fields. |

</div>

<Callout type="warn" title="Caution">
Parameter overrides can change request semantics, request headers, and error handling. Avoid using them to switch `stream` or pass client keys to untrusted upstream services. Enable regex replacement, header synchronization, and custom errors with care.
</Callout>

## Saving and Applying Changes

Channels are stored in the database. With in-memory caching disabled, every node reads the database directly on each request, and the operations below take effect on each node’s next request. With in-memory caching enabled, including in deployments with Redis enabled, the node handling the request refreshes immediately. Other nodes reload the Channels within about 3 seconds, or within one sync cycle at the latest (60 seconds by default). Automatic disabling after request failures and automatic recovery after tests follow different timing. See “Automatic Changes and Background Tasks” below. The `SYNC_FREQUENCY` environment variable sets the sync interval in seconds and defaults to 60. New API reads all environment variables mentioned on this page at startup, so restart New API after changing them.

## Notes

- **Bulk operations affect all channels.** “Test All Channels,” “Update All Balances,” “Check All Upstream Updates,” “Apply All Upstream Updates,” “Delete All Disabled Channels,” and “Repair Channel Consistency” ignore the current list filters. Run these operations during off-peak hours.
- **Tests and balance updates may change channel status.** “Test All Channels” may automatically disable or re-enable channels. “Update All Balances” may automatically disable channels with insufficient balances. See “Automatic Changes and Background Tasks” under [Saving and Applying Changes](#saving-and-applying-changes).
- **Automatic syncing updates the channel’s model list directly.** When “Automatically Sync Upstream Models” is enabled, scheduled checks add newly discovered models to the channel’s model list, excluding ignored models. Existing models stay on the list.
- **“Apply All Upstream Updates” skips individual review.** It applies all pending model additions and removals for every channel that has been checked. To review changes individually, select them in “Preview Upstream Model Changes” and click “Confirm and Apply Selected Changes.”
- **Sensitive operations require the “Edit Sensitive Channel Settings” permission.** Admins without this permission cannot create, duplicate, or delete channels, or save changes to sensitive settings such as credentials, channel type, Base URL, proxy, header overrides, or parameter overrides. See [Permissions and Security Boundaries](#permissions-and-security-boundaries).
- **Deletion is irreversible, and duplication copies credentials.** New API cannot restore a deleted channel. A duplicate inherits the original channel’s credentials and therefore cannot serve as credential rotation. See [Enabling, Disabling, and Deleting Channels](#enable-disable-and-delete-channels) and [Duplicating a Channel](#duplicate-channels).

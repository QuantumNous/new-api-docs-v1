- Only Root users can access this page. In the sidebar, go to “Admin” → “System Information.”
- View each instance’s operational status, resource usage, and sync status, monitor system tasks, remove records for offline instances, and clean up task history.
- This page is for monitoring and cleanup only. System tasks are created automatically or triggered by actions in Channel Management or Operations Settings.

<Callout type="info" title="Note">

- Each instance is a New API process identified by `NODE_NAME`.
- Only Master instances run scheduled background tasks. Worker instances continue to report instance information and leave system tasks for Master instances to claim.
- A system task represents a batch of background maintenance, checks, or polling. User-submitted image, music, and video tasks are tracked separately. For example, `Async Task Polling` represents one background pass that checks the status of application tasks.

</Callout>

## Common Operations

This section covers checking instances and sync status, removing offline instance records, and filtering and cleaning up task history.

### View Instances and Sync Status

- System Information – Instance Monitoring

![System Information page showing instance monitoring](/assets/guide/feature-guide/system-information-instance-monitoring.png)

Each New API process attempts to report its instance information immediately after startup and then reports every 30 seconds.

**Steps**

1. In the “Instances” panel, check each instance’s status, role, and resource usage.
2. Hover over the status in the “Sync” column to view each sync item and any errors for that node.
3. If a yellow warning icon appears next to the instance name, click it to view the “Configure NODE_NAME” example.

<Callout type="info" title="Note">

- The sync items shown on hover vary by deployment. See [Node Sync](#node-sync).
- The “Sync” column shows `-` for offline instances and older nodes that do not report sync information.

</Callout>

### Remove Offline Instance Records

- System Information – Remove Offline Instances

![System Information page showing offline instance removal](/assets/guide/feature-guide/system-information-delete-instance.png)

Deleting an offline instance removes only its status record from the database. The instance’s runtime state and any requests it is handling are unaffected. If the instance is still running and resumes reporting, the system recreates the record automatically.

**Delete One Offline Instance Record**

1. Find an instance marked “Offline” in the instance list.
2. Confirm the instance has been taken offline or that you no longer need its old record.
3. Click the delete button at the end of the row.
4. Click “Delete” in the confirmation dialog.

**Delete All Offline Instance Records**

1. Review all offline instances in the current list and confirm you no longer need their records.
2. Click “Delete All Offline Instances” in the upper-right corner of the panel.
3. Click “Delete” in the confirmation dialog.

<Callout type="info" title="Note">

- “Delete All Offline Instances” appears only when the list contains offline records.
- Both confirmation dialogs are titled “Delete Offline Instance.” When deleting all offline records, the dialog asks “Delete … offline instance records? Online instances will be kept.”
- After bulk deletion, the success message shows the number of records actually deleted.

</Callout>

### Filter and Clean Up Task History

**Steps**

1. Use the “All Types” and “All Statuses” dropdowns below “Task History” to filter the list. The available status filters are “Succeeded” and “Failed.” Click “Reset” to clear the filters.
2. Click “Clean Up Task History” on the right.
3. Click “Delete” in the confirmation dialog.

<Callout type="warn" title="Caution">

- Cleanup applies to all historical tasks that match the current filters across all pages.
- The system always keeps active tasks and the latest record of each task type. It uses the latest record to determine when the next scheduled run is due.
- Cleanup is permanent. The success message shows the number of records actually removed.

</Callout>

### Node Sync

After settings, Channels, or other data are saved, nodes use sync tasks to load the changes. The “Sync” column in the instance table and the “... Sync” tasks both reflect this process.

**Sync Items**

- All nodes sync settings, permissions, plugins, login methods, and models.
- Only nodes with in-memory caching enabled and Master instances sync Channels. Set `MEMORY_CACHE_ENABLED=true` or enable Redis to enable in-memory caching.
- Nodes sync subscription plans only when Redis is disabled. The `REDIS_CONN_STRING` environment variable determines whether Redis is enabled.
- The “Sync” tooltip lists all sync items used by any node in the deployment. If a node skips an item, such as Channels on a Worker instance without in-memory caching, it reads that data directly from the database or shared cache, and the item shows “Synced.”

**Loading Rules**

- Each node checks for sync tasks every 3 seconds. When it detects a new change, it reloads the data and reports immediately. The “Sync” column updates ahead of the next 30-second instance report.
- If loading fails, the node shows “Update Failed,” records the error, and retries on the next check. The error clears automatically once loading succeeds.
- If the system fails to write a sync task or the cluster contains older nodes, settings, permissions, and the Channel cache reload at the regular sync interval as a fallback. `SYNC_FREQUENCY` controls the interval in seconds and defaults to 60. Fallback intervals vary for other sync items. See <a href="/en/docs/guide/feature-guide/system-settings/system-setting#scope-and-multi-instance-synchronization" target="_blank" rel="noopener noreferrer">Scope and Multi-Instance Sync</a>.

**How “... Sync” Tasks Complete**

- The Master instance checks about every 15 seconds. Once every online node that syncs the item has loaded the change, the task changes to “Succeeded” and progress reaches 100%.
- While the task is pending, “Progress” shows the percentage of nodes that have loaded the change, and “Details” shows the nodes that failed to load it and their errors.
- The check excludes nodes that have gone more than 90 seconds without reporting.
- If no Master instance is running, “... Sync” tasks remain “Pending.” Nodes continue to check every 3 seconds and apply the changes when they load them.

### Task Execution and Retention

Only Master instances execute system tasks. The system retains records according to the rules below.

**Execution Rules**

- The Master instance checks about every 15 seconds, claims pending tasks, and creates new tasks for scheduled runs that are due.
- A manual trigger immediately wakes the Master instance handling the request. If a Worker instance handles the request, a Master instance claims the task within about 15 seconds.
- The system creates a task only if there is no active task of the same type.
- The executing instance renews the 60-second task lock every 20 seconds. If the lock expires before renewal, the system marks the task “Failed” and shows `task lease expired` in “Details.”
- If no Master instance is running, tasks remain “Pending.” Only Master instances claim system tasks.

**Retention Rules**

- Manual cleanup always keeps active tasks and the latest record of each task type.
- Each day, the system automatically deletes completed tasks older than the configured “Completed Task Retention (Days),” which defaults to 30 days. It keeps the latest record of each type. See <a href="/en/docs/guide/feature-guide/system-settings/settings-operations#log-maintenance" target="_blank" rel="noopener noreferrer">Operations Settings</a>.

### System Task Status

The “Status” column in “Active Tasks” and “Task History” shows the following states.

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| --- | --- | --- |

**Additional note**

- **Instance records can be recreated.** Deleting a stale instance only removes its record from the database. If the instance is still running, its next heartbeat recreates the record.

## Important Notes

- **An instance can show as “Stale” while still running.** The status means that more than 90 seconds have passed without a heartbeat. A brief database outage or network interruption can also cause this status. Before deleting all stale records, confirm that the affected nodes are offline.
- **Only the Master instance runs system tasks.** Worker instances do not claim system tasks. If no Master instance is running, tasks remain “Pending.” See [Task Execution and Retention](#task-execution-and-retention).
- **Node names must be unique.** When multiple instances use the same `NODE_NAME`, they write to the same record and overwrite each other’s status.

“Stale” means the instance has gone more than 90 seconds without reporting a heartbeat.

**Possible causes**

- The instance process has stopped.
- The instance cannot write to the database, so its heartbeat fails.

**Resolution**

1. Check the instance process, its database connection, and its server logs.
2. Confirm that the instance is offline before deleting its record. See [Cleaning Up Stale Instance Records](#remove-offline-instance-records).
</Accordion>

<Accordion title="The instance list shows fewer instances than are deployed">
**Possible cause**

Multiple instances use the same `NODE_NAME` and write to the same record. If `NODE_NAME` is unset, the instance uses its hostname and displays a yellow warning icon next to the name.

**Resolution**

1. Set a unique `NODE_NAME` for each instance, then restart those instances.
</Accordion>

<Accordion title="Deleting a stale instance returns instance is not stale or no longer exists">
**Original message**

`instance is not stale or no longer exists` (English only)

**Possible causes**

- The instance resumed reporting after you opened the confirmation dialog.
- Another administrator already deleted the record.

**Resolution**

1. Click “Refresh” and check the instance status again.
2. If the instance is still running and you no longer need it, stop it first.
</Accordion>

<Accordion title="A system task stays “Pending”">
The Master instance checks for pending tasks to claim about every 15 seconds.

**Possible causes**

- No Master instance is currently running. Instances with `NODE_TYPE=slave` are Workers and do not claim system tasks. In this case, “… Sync” tasks also stay pending, and individual nodes still load the changes.
- A “… Sync” task stays “Pending” while an online node has yet to load the changes or has encountered an error loading them.

**Resolution**

1. Confirm that at least one Master instance is running. See [Task Execution and Retention](#task-execution-and-retention).
2. If a sync task is pending, check the tooltip in the instance table’s “Sync” column and the error under the task’s “Details.” Then check the affected node’s server logs. The system stops counting that node after more than 90 seconds without a heartbeat.
</Accordion>

<Accordion title="A system task shows as “Failed” with task lease expired in its details">
**Original message**

`task lease expired` (English only)

**Possible cause**

The instance running the task failed to renew its 60-second lease before it expired. This can happen if the process exits or the instance cannot write to the database.

**Resolution**

1. Use “Executing Instance” to identify the instance and check its server logs.
2. Scheduled tasks run again at their next scheduled time. Trigger manual tasks again yourself.
</Accordion>

<Accordion title="Records remain after historical task cleanup, or cleanup reports 0 deletions">
**Message**

“Deleted 0 historical system tasks”

The system always retains the latest record for each task type and all in-progress tasks. It uses these records to determine when scheduled tasks should run next. If only these records remain, cleanup reports 0 deletions.
</Accordion>

<Accordion title="The “Sync” column shows “Update Failed”">
The node failed to load a sync item. The changes have yet to take effect on that node.

**Possible cause**

An error occurred while the node was loading a sync item. The node may have failed to read from the database. Check the original error message in the tooltip for the specific cause.

**Resolution**

1. Hover over “Update Failed” to see which sync item failed and read the original error message.
2. Check the node’s server logs and database connection.
3. The node automatically retries every 3 seconds. Once it loads the item successfully, the status returns to “Synced.”
</Accordion>

</Accordions>

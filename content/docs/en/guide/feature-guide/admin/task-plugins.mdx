- Only Root can access this page. In the sidebar, go to “Admin” → “Plugins”.
- Upload plugins or install them from the Plugin Marketplace, manage their versions, and enable or disable them.
- Uploading a plugin or installing it from the marketplace does not automatically create a channel or a request processing instance.

<Callout type="info" title="Tip">

- Plugins are JavaScript scripts that run in the sandbox built into New API.
- A plugin can include up to three components. The task component connects platforms for asynchronous tasks such as image, video, and audio processing to a unified task API. The channel component forwards standard API requests like an advanced custom channel. The request processing component inspects or modifies requests before they go upstream. A single plugin can include multiple components.
- Task and channel components must be bound to a channel of type “Task Plugin”. Plugins can also be bound to New API channels as extensions. See [Create a Plugin Channel](#create-a-plugin-channel).
- To use a request processing component, add an instance on the <a href="/en/docs/guide/feature-guide/admin/request-processing" target="_blank" rel="noopener noreferrer">Request Processing</a> page in the sidebar. You can also add the instance to a specific channel.
- “Enable Plugins” in the upper-right corner is a global switch. Turning it off takes plugin tasks and plugin channels out of service. Request processing continues to run. See [Enable or Disable Plugins](#enable-or-disable-plugins).

</Callout>

## Common Operations

This section covers uploading and installing plugins, creating channels, viewing plugin details, enabling or disabling plugins, deleting versions, and managing marketplace sources.

### Upload a Plugin

- Plugin Management – Upload Plugin

![Upload Plugin dialog in Plugin Management](/assets/guide/feature-guide/plugins-upload-plugin.png)

- Plugin Management – Upload New Version

![Upload New Version dialog in Plugin Management](/assets/guide/feature-guide/plugins-upload-new-version.png)

**Upload a plugin**

1. On the “Installed” tab, click “Upload Plugin” in the upper-right corner.
2. Provide the source code. Drag and drop a `.js` file or click “Select File” to choose one. Alternatively, enter an address under “Import from URL” and click “Fetch”, or paste the code directly into “Plugin Source Code”.
3. Review the preview below “Plugin Source Code”. Check the applicable channels, upstream authentication method, default API address, additional domains the plugin can access, and supported models.
4. Optionally, select a “Plugin Icon” and enter “Notes”.
5. Click “Upload”.

**Upload a new version**

1. Click ⋯ at the end of the plugin row, or in the upper-right corner of the card in card view, and select “Upload New Version”.
2. Follow steps 2–4 above. Confirm that the `key` in the source code matches the plugin’s Key.
3. Click “Upload”.

<Callout type="warn" title="Caution">

- The “Third-Party Plugin Risks” notice at the top of the dialog reads “Plugins can read channel keys and modify content sent upstream. Review the code and changes before activation.” Review the source code before uploading.
- The server compiles the source code, validates the metadata, and checks for conflicts with the models, channel types, and routes of existing plugins. It saves the plugin only after all checks pass. If a check fails, the dialog shows “The gateway rejected this plugin” and the reason. If there is a conflict, the message names the conflicting plugin. See [Plugin Metadata](#plugin-metadata) and [Version, Enablement, and Conflict Rules](#version-enablement-and-conflict-rules).

</Callout>

### Install from the Plugin Marketplace

- Plugin Management – Official Plugins – Tasks

![Official task plugins in the Plugin Marketplace](/assets/guide/feature-guide/plugins-plugin-marketplace-task.png)

![Plugin Details tab in the Install Plugin dialog](/assets/guide/feature-guide/plugins-plugin-marketplace-install-plugin-details.png)

![Version Diff tab in the Install Plugin dialog](/assets/guide/feature-guide/plugins-plugin-marketplace-install-version-diff.png)

- Plugin Management – Install Plugin – Full Source Code

![Full Source Code tab in the Install Plugin dialog](/assets/guide/feature-guide/plugins-plugin-marketplace-install-full-source-code.png)

- Plugin Management – Install Plugin – Changelog

![Changelog tab in the Install Plugin dialog](/assets/guide/feature-guide/plugins-plugin-marketplace-install-changelog.png)

**Procedure**

1. Open the “Plugin Marketplace” tab.
2. Select “Official Plugins” or “Community Plugins”, then choose “Task”, “Channel”, or “Request Processing”.
3. Click “Install” on the plugin card. If you know the eight-digit plugin code, enter it in “Plugin Code” on the right, click “Find”, then click “Install” on the result card.
4. Use the version selector to choose the version to install.
5. Review the “Plugin Details”, “Version Diff”, “Full Source Code”, and “Changelog” tabs as available.
6. Click “Install and Enable”.

<Callout type="warn" title="Caution">

- Installation and upload both require compilation, metadata validation, and conflict checks. These checks are mandatory for both methods.
- If installation fails, the dialog shows “Plugin Installation Failed”, the reason, and “Resolve conflicts on the ‘Installed’ page before reinstalling.” For a conflict, delete or disable the conflicting plugin on the “Installed” tab, then retry the installation.
- The plugin’s marketplace source must still be in the source list. Otherwise, the dialog shows “This plugin’s marketplace source is missing from the source list”.
- “Integrity Check Failed” blocks installation. “No Integrity Hash” allows installation, but you cannot verify that the source code matches the version published by the source.
- The browser downloads both the index and the hash. The server recalculates the hash of the source code it receives but does not validate the marketplace index. A compromised browser can replace both the source code and the hash. The integrity check cannot detect that change.

</Callout>

### Create a Plugin Channel

- Plugin Management – Create Task Plugin Channel

![Create a task plugin channel in Plugin Management](/assets/guide/feature-guide/plugins-create-plugin-channel.png)

**Prerequisites**

- The target plugin must be enabled and its “Runtime Status” must be “Registered”. Built-in plugins are available without an upload. For other plugins, upload the plugin or install it from the marketplace first. The selection list excludes disabled plugins. For request-processing-only plugins, add an instance on the <a href="/en/docs/guide/feature-guide/admin/request-processing" target="_blank" rel="noopener noreferrer">Request Processing</a> page. These plugins do not appear in the “Plugins” category.
- Root can create plugin channels by default. For an Admin to see the “Plugins” category, Root must grant both channel operation permissions and the “Bind Task Plugins” permission in the administrator permission settings.
- Have the upstream service address and credentials ready.

**Procedure**

1. Open “Channels” in the sidebar and click “Create Channel”.
2. In the selection dialog, switch to the “Plugins” category.
3. Click the target plugin’s card.
4. Review the plugin models prefilled under “Models”. Add or remove models as needed.
5. Fill in “API Address” and “API Key”.
6. If the plugin declares settings, fill in “Plugin Settings” according to the plugin’s requirements.
7. Adjust the group, priority, and weight as needed.
8. Click “Create Channel”. For plugins that require an upstream account login, click “Save and Log In”, then complete the login in the “Credentials” section.

<Callout type="warn" title="Caution">

- For a channel with a task-only plugin, “Test Connection” displays a message that this channel type does not support testing. Channels whose plugins include a channel component support connection testing. The detailed test lists only the endpoints the plugin supports.
- Before deleting or disabling a plugin, switch its bound channels to another plugin. If you are disabling the plugin, you can also use the cascade option to disable its bound channels. Requests on channels still using an unavailable plugin will fail.

</Callout>

### Plugin Metadata

**Compilation and Validation**

- `apiVersion` must be `1`.
- `name` and `author.name` are required.
- `key` can contain only lowercase letters, digits, `-`, and `_`, and can be at most 30 characters long. It cannot match an existing gateway path segment such as `api`. If it does, the system displays `plugin meta key … is a reserved path segment` (English only).
- `version` must follow Semantic Versioning.
- `models` must be nonempty and contain no case-insensitive duplicates.
- `channelTypes` must contain unique positive integers and cannot include `60` (New API) or `61` (task plugins).
- `allowedHosts` must contain hostnames, optionally with ports. Schemes, paths, and credentials are prohibited.
- `fetchMode` must be `per_task` or `batch`.
- Uploads containing legacy fields such as `channelType`, `submitPaths`, or `actions` are rejected. Use `channelTypes` and `routes` instead.

**Metadata Fields**

Plugins declare the following fields in `meta` in their source code. For the full declaration rules for each component, see the <a href="/en/docs/plugins" target="_blank" rel="noopener noreferrer">plugin documentation</a>.

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_td_code]:wrap-anywhere [&_th]:whitespace-nowrap">

| Field | Type / Rules | Description |
| --- | --- | --- |
| `apiVersion` | Integer, currently must be `1` | The plugin API version. |
| `key` | String of at most 30 characters matching `^[a-z0-9][a-z0-9_-]*$` | The unique plugin identifier used for Channel binding and identification in the marketplace. |
| `name` | String or localized text, required | The plugin’s display name. Localized text must include `en`. The interface displays the name in the selected language. |
| `icon` | Optional | The plugin icon. |
| `description` | Localized text | The multilingual plugin description. |
| `version` | Semantic version string | The plugin version number. |
| `author` | `{ name, url }`, with `name` required | Author information. |
| `channelTypes` | Array of positive integers | IDs of the Channel types the plugin can bind to. Cannot include `60` or `61`. |
| `models` | Nonempty array of unique strings | Identifiers of the models the plugin supports. |
| `fetchMode` | `per_task` / `batch` | The fetch mode. Per-task mode requires `buildQueryRequest`. Batch mode requires `buildBatchQueryRequest` and `parseBatchResult`. |
| `routes` | Array | The plugin’s native route declarations, used to generate routes. |
| `protocols` | Array | The host protocols the plugin declares, such as `openai_responses`, `openai_video`, and `openai_image`. For `openai_responses`, `supports` specifies streaming, synchronous, and background modes. |
| `allowedHosts` | Array of hostnames | Upstream hosts the plugin can send requests to, optionally including ports. |
| `auth` | Object | The authentication method the plugin uses, such as OAuth2 JWT. |
| `usageSchema` | Object | Billing parameter declarations used by task model billing expressions. |
| `baseUrl` | String, optional | The default upstream URL. It prepopulates “API URL” when you create a task plugin Channel. |
| `relay` | Array, optional | Relay routes for the Channel component. When this array is nonempty, the plugin can relay standard API requests like an advanced custom Channel. |
| `channelConfig` | Object, optional | Channel-level setting declarations. The form for a Channel bound to this plugin shows “Plugin Settings.” |
| `configSchema` | Object, optional | Setting declarations for request processing instances. See <a href="/en/docs/guide/feature-guide/admin/request-processing#add-and-edit-instances" target="_blank" rel="noopener noreferrer">Request Processing</a>. |

</div>

<Callout type="info" title="Tip">

- `routes` and `protocols` determine how the plugin accepts requests. `usageSchema` determines how task results are billed. See the “Billing Parameters” tab in Plugin Details.
- Requests are routed to the plugin only if they match a model and Channel type declared by the plugin.
</Callout>

### Version, Enablement, and Conflict Rules

Multiple versions can be saved under the same Key, with only one active at a time. Plugins can be enabled or disabled both globally and individually.

**Version rules**

- The first version for a Key is activated automatically after upload or installation. If a version is already active, the new version is saved and remains inactive.
- If the same Key and version already exist with different source code, the upload is rejected with the English-only message `plugin key and version already exist with different source`. Version contents are immutable. Increment `version` to change the source code.
- The source code limit is 8 MiB. The plugin icon has a separate limit of 512 KiB.

**Enablement and deletion rules**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Action | Built-in plugins and their custom versions | Third-party plugins |
| --- | --- | --- |
| Disable | The built-in plugin for that Key also stops serving requests. The runtime status is “Disabled,” with no fallback to the built-in version. | The platform becomes unavailable. The runtime status is “Disabled (Platform Unavailable).” |
| Re-enable | The custom version and the built-in plugin resume service together. | The plugin resumes service. |
| Delete the current custom version | If other uploaded versions exist, the most recently uploaded one is activated and retains its own enabled status. Otherwise, the built-in plugin resumes service unless the Key has been disabled. | If other versions exist, the same rule applies. Otherwise, the platform becomes unavailable. |
| Turn off the global toggle | All plugin tasks and plugin channels stop running. Request processing continues as usual. | Same as for built-in plugins and their custom versions. |

</div>

**Conflict checks**

- Uploading, installing, enabling, activating a version, and deleting the current version all trigger checks for model, channel type, and route conflicts with existing plugins. Deleting the current version triggers the check because it activates another version or falls back to a built-in version. Conflicting operations are rejected, and the checks cannot be bypassed.

<Callout type="info" title="Note">

- Versions uploaded through the API can include `enabled` (enabled by default), `remark` (a note), and `sourceSha256`. If provided, `sourceSha256` must match the SHA-256 hash of the source code, ignoring case. A mismatch causes the upload to be rejected. Uploads through the UI and installations from the marketplace are always enabled. Marketplace installations provide `sourceSha256` automatically.
- If a custom version is disabled while the built-in plugin with the same name is still serving requests, the runtime status is “Disabled, Using Built-In Version.” Disabling a plugin in the UI never produces this status.

</Callout>

### Task Timeouts and Cleanup

When a plugin is disabled or the global toggle is turned off, in-flight tasks continue and are cleaned up by global polling when they time out.

**Cleanup rules**

- An in-flight task has its `platform` set to the plugin Key and has yet to succeed or fail.
- The global poller scans for timed-out tasks and marks them as failed once `TASK_TIMEOUT_MINUTES` has elapsed since submission. The default is 4,320 minutes (72 hours). Set it to 0 to disable time-based timeouts. Quota is refunded for non-legacy tasks.
- Cleanup runs only when `UPDATE_TASK` is enabled. When it is disabled, timed-out tasks are neither marked as failed nor refunded.
- `TASK_POLL_MAX_FAILURES` controls the maximum number of consecutive polling failures and defaults to 20.

<Callout type="info" title="Note">

Timeout cleanup uses a global poller shared by all plugins. When a plugin is disabled, its remaining tasks are still cleaned up under the same timeout and retry policy, so they do not fail immediately.

</Callout>

## Saving and Applying Changes

The server executes each action on this page as soon as it is submitted. There is no page-wide Save button. Changes take effect immediately on the node handling the request. Other nodes sync according to the two groups below. In a multi-instance deployment, the upper-right corner of the page shows whether each node has loaded the changes. See [Node Sync Status](#node-sync-status).

**Plugin versions**

The node handling the request updates its plugin registry immediately. Other nodes load the changes in about 3 seconds, with a maximum of 30 seconds.

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Action | How it is saved | When it takes effect |
| --- | --- | --- |
| Upload, or “Install and Enable” from the marketplace | The server compiles the plugin, validates its metadata, and checks for conflicts before saving it. | The first version for a Key is activated as soon as it is saved. If a version is already active, the message reads “Plugin saved, pending activation.” The current version stays active until you click “Activate Now” or activate the new version in “Version History.” |
| Activate or roll back a version | Use “Version History.” On success, the message reads “Plugin version activated.” | The version is compiled before activation. If compilation fails, the current version stays active. |
| Enable or disable a custom plugin | Use the toggle and confirm the change. If the plugin is still in use, follow the “Plugin Still in Use” flow. | Disabling removes the Key from routing. Re-enabling restores it. In-flight tasks continue. |
| Delete the current custom version | Confirm the action. On success, the message reads “Plugin version deleted.” | If other versions exist for the Key, the most recently uploaded one is activated. Otherwise, the gateway falls back to the built-in plugin. If no built-in plugin exists, the platform becomes unavailable. Conflicts are checked before fallback. If a conflict is found, deletion is rejected. |
| Pricing check after uploading, installing, activating, enabling, or deleting the current version | The result is returned with the operation. | If any task models cannot be billed, the message reads “Pricing needs attention for the following models:”. Address these models in the billing and payment settings. See [Upload a Plugin](#upload-a-plugin). |

</div>

**Global toggle, built-in plugins, and marketplace sources**

These changes are stored as system settings. They take effect immediately on the node handling the request. Other nodes pick them up through system settings sync in about 3 seconds, or within one sync cycle at most (60 seconds by default).

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Action | How it is saved | When it takes effect |
| --- | --- | --- |
| Global “Enable Plugins” toggle | Use the toggle. Before turning it off, confirm “Turn off plugin tasks and channels?” On success, the message reads “Plugin settings updated.” | Turning it off rejects new plugin tasks and plugin channel requests. Request processing and in-flight tasks continue. |
| Enable or disable a built-in plugin | Use the toggle and confirm the change. | When disabled, the built-in plugin for that Key stops serving requests without falling back to another version. Re-enabling restores service. |
| Change marketplace sources | Save the full list at once in the “Marketplace Sources” dialog. On success, the message reads “Marketplace sources updated.” | This affects only which sources are available to browse in the “Plugin Marketplace.” |

</div>

**Additional notes**

- **Enabling or disabling built-in and custom plugins with the same name together**. Each plugin syncs according to its group. Both changes take effect on other nodes in about 3 seconds, or within about 60 seconds under the default configuration.
- **Compilation failure**. If a node fails to compile a new version while loading it, that node continues to use the previously loaded version and shows “Compilation Failed” as its runtime status.
- **Plugin sandbox “Dry Run”**. The sandbox runs a temporary copy without saving it or affecting the current registry.
- **Plugin channels**. For details on saving and applying changes, see <a href="/en/docs/guide/feature-guide/admin/channel#saving-and-applying-changes" target="_blank" rel="noopener noreferrer">Channel Management</a>.

## Important Notes

**Installation and sources**

- **Uploading and installing plugins are administrator-level trust decisions.** Plugins can read channel credentials and construct upstream requests. Plugins from community and third-party sources are published by others. Review the source code before installing. See [Upload a Plugin](#upload-a-plugin) and [Official and Community Plugins](#official-and-community-plugins).
- **The Community source reports installation statistics.** When you install from the Community source, the server sends the plugin identifier, version number, and a randomly generated ID for this gateway to newapi.ai. See [Official and Community Plugins](#official-and-community-plugins).

**Enabling, disabling, and deleting plugins**

- **Disabling a plugin also disables the built-in plugin with the same Key.** If you disable a built-in plugin or a custom version with the same Key as a built-in plugin, the built-in plugin stops serving requests for that Key. No fallback occurs. See [Version, Enablement, and Conflict Rules](#version-enablement-and-conflict-rules).
- **In-flight tasks continue until timeout cleanup.** Turning off the global switch or disabling a plugin leaves in-flight tasks for timeout cleanup. Cleanup runs only when `UPDATE_TASK` is enabled. See [Task Timeouts and Cleanup](#task-timeouts-and-cleanup).
- **Update bound channels before deleting or disabling a plugin.** Requests on those channels will otherwise fail because the plugin is unavailable. See [Enable or Disable a Plugin](#enable-or-disable-plugins).
- **Another version takes over after deletion.** When you delete the current custom version, the most recently uploaded version for that Key becomes active if another version is available. See [Delete the Current Custom Version](#delete-the-current-custom-version).

**Versions and conflicts**

- **Bump the version when you change the source code.** The system rejects different source code submitted under an existing Key and version. See [Version, Enablement, and Conflict Rules](#version-enablement-and-conflict-rules).
- **Conflict checks are mandatory.** Uploading, installing, enabling, or activating a plugin, or deleting the current version, always triggers a conflict check. See [Version, Enablement, and Conflict Rules](#version-enablement-and-conflict-rules).

<Accordion title="The Plugin category is missing when creating a channel">

**Message**

When you copy or submit a task plugin channel, you may see `task plugin channels require the task_plugin.bind permission` (English only).

**Possible cause**

Your account lacks the “Bind Task Plugin” permission. The selection dialog hides the “Plugin” category from accounts without this permission.

**Resolution**

1. Ask Root to grant “Bind Task Plugin” under “Administrator Permissions” in <a href="/en/docs/guide/feature-guide/admin/user#administrator-permissions" target="_blank" rel="noopener noreferrer">User Management</a>.

</Accordion>

<Accordion title="A task plugin channel cannot be saved">

**Messages**

Examples include `task plugin "…" is not registered`, `task plugin key must not exceed 30 characters`, `base URL is required for task plugin channels`, and `channel cannot be empty` (English only). You may also see “Base URL is required for this channel type”.

**Possible causes**

- The bound plugin is unregistered.
- The Key of the plugin bound to the channel exceeds 30 characters.
- The “API Address” or “API Key” field is empty.

**Resolution**

1. Fix each issue indicated by the messages.
2. Confirm that the plugin's runtime status is “Registered”.

</Accordion>

<Accordion title="A request does not reach the expected plugin">

**Messages**

You may see `selected channel does not match the pinned task plugin`. If the plugin system or the plugin itself is disabled, the client receives HTTP 400 with `the task plugin system is disabled on this gateway` or `task plugin "…" is disabled on this gateway` (English only).

**Possible causes**

- The plugin Key bound to the channel differs from the Key pinned to the request.
- IDs for other channel types are missing from the plugin's `channelTypes`.
- The channel has a different type than “Task Plugin”, the bound Key is incorrect, the Group does not match, or the model is missing from the plugin's `models`.
- The global “Enable Plugins” switch or the plugin itself is off.

**Resolution**

1. Check the channel and plugin against each possible cause above.
2. Re-enable the plugin if it is disabled.

</Accordion>

<Accordion title="Plugin upload fails">

**Messages**

Examples include “Plugin source exceeds the 8 MiB limit.”, `plugin source sha256 mismatch`, and `plugin key and version already exist with different source` (English only for the two code-formatted messages).

**Possible causes**

- The source code exceeds 8 MiB.
- One or more of `apiVersion`, `key`, `version`, `name`, or `models` fail validation.
- The plugin has a model, channel type, or route conflict with an existing plugin.
- The same Key and version already exist with different source code.

**Resolution**

1. If there is a conflict, delete or disable the conflicting plugin on the “Installed” tab, then upload again.
2. After changing the source code, increment `version` before uploading again.

</Accordion>

<Accordion title="The plugin shows a compilation failure">

**Message**

Hover over the runtime status to see the error, such as `plugin … is missing required export "buildSubmitRequest"` (English only).

**Possible causes**

The source code contains errors, metadata is missing, or required exports such as `buildSubmitRequest`, `parseSubmitResponse`, or `parseTaskResult` are missing. `batch` mode also requires batch exports.

**Resolution**

1. Review the source code and error in the plugin details, then fix the issue.

</Accordion>

<Accordion title="The plugin shows as unregistered">

**Explanation**

This version is enabled, but the node handling the request has yet to load it into its registry. Other nodes load the new version within about 3 seconds. Each node also syncs with the database every 30 seconds.

**Resolution**

1. Refresh the list after a short wait.
2. If the plugin still shows as unregistered, check the server logs for task plugin sync errors.

</Accordion>

<Accordion title="Disabling a plugin shows “Plugin is still in use”">

**Explanation**

Enabled channels or in-flight tasks still use the plugin.

**Resolution**

1. In the confirmation dialog, click “Cascade Disable Channels”. If tasks are still in flight, click “Force Operation”. See [Enable or Disable a Plugin](#enable-or-disable-plugins).
2. If you need to keep these channels, switch them to another plugin first.

</Accordion>

<Accordion title="Disabling a custom version also stops the built-in plugin with the same Key">

**Explanation**

Disabling a custom version that shares a Key with a built-in plugin also disables the built-in plugin.

**Resolution**

1. Re-enable the plugin to restore the current custom version.
2. To use the built-in plugin, use “Delete Current Custom Version” to remove all custom versions for that Key. Once “Source” shows “Built-in”, turn on the “Enabled” switch for that row.

</Accordion>

<Accordion title="Task billing does not take effect">

**Possible causes**

- The plugin does not declare `usageSchema`.
- The request was not routed to this plugin.
- No task expression is configured for this task model in <a href="/en/docs/guide/feature-guide/admin/billing-expression#task-models" target="_blank" rel="noopener noreferrer">Billing Expressions</a>.

</Accordion>

<Accordion title="Marketplace installation fails">

**Messages**

You may see “Integrity check failed” or “Resolve the conflict on the Installed tab, then install again.”

**Possible causes**

- The index is unreachable.
- The source code hash differs from the hash in the index.
- There is a route conflict.
- A plugin from a community or third-party source uses the same identifier as a built-in plugin or lacks the required prefix of the author's GitHub username followed by an underscore.
- The plugin's source has been removed from the source list.

**Resolution**

1. Follow the instructions in the message and try installing again. If there is a conflict, resolve it on the “Installed” tab first.
2. If the identifier fails validation, contact the plugin author.

- The browser cannot reach the host, or the host blocks cross-origin requests.

**Explanation**

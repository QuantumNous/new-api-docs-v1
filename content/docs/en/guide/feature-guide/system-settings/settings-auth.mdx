### OAuth Integration

After registering this site with a built-in third-party sign-in provider, enter the credentials on the corresponding tab and enable the provider.

This section has six tabs, “GitHub,” “Discord,” “OIDC,” “Telegram,” “LinuxDO,” and “WeChat.” The page header has “Reset” and “Save Changes.” “Save Changes” saves edits across all tabs at once. Every tab except WeChat has a “Setup Guide” at the top that says “Before enabling sign-in, configure these values in your provider application” and lists callback URLs you can copy. When changes are pending, “Unsaved Changes” appears next to the title.

**Steps**

1. Create an application in the provider's dashboard and register its name, homepage, and the callback URL required by the provider.
2. Enter the credentials and endpoints on the corresponding tab, then click “Save Changes” in the page header.
3. Turn on the provider's switch and click “Save Changes” again.

<Callout type="info" title="Tip">

- The “Setup Guide” derives callback URLs from “Server Address,” using the format `/oauth/{provider}`. OIDC labels it “Redirect URL” and the other providers label it “Authorization Callback URL.” GitHub, Discord, and OIDC also display a “Homepage URL.”
- If the server address is unset, these URLs start with the placeholder “Site URL” and cannot be used as shown. Set the server address in <a href="/en/docs/guide/feature-guide/system-settings/settings-site#system-information" target="_blank" rel="noopener noreferrer">Site and Branding Settings</a> first.
- Discord and OIDC send their respective callback URLs derived from the server address during token exchange. GitHub currently omits `redirect_uri` from its token exchange.
- LinuxDO appends `/api/oauth/linuxdo` to the scheme and host of the incoming request. This URL may differ from the one shown in the interface.
- The callback URL, the public URL used by the browser, and the scheme seen by the server must agree. Copy the URL generated for this site and follow the provider's requirements and the actual forwarding path used by the reverse proxy.
- Administrators can manage users' linked accounts in <a href="/en/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">User Management</a>.
</Callout>

### Passkey Authentication

- Authentication – Passkey Authentication

![Authentication – Passkey Authentication page](/assets/guide/feature-guide/system-settings-authentication-passkey-authentication.png)

Passkeys use WebAuthn. Once enabled, users can register passkeys and sign in with them. “Primary Domain” and “Compatible Passkey Domains” are in the “Passkey Domains” group. Click “Why is this required?” in that group to open “How to Configure Passkey Domains.”

**Steps**

1. Enable “Enable Passkey” as needed and set the display name, user verification, and device type preference.
2. Enter the “Primary Domain” in the “Passkey Domains” group and keep old domains under “Compatible Passkey Domains.” Enter full addresses with ports under “Sites Allowed to Use Passkeys.”
3. Click “Save Changes” in the page header.
4. When the confirmation dialog appears, review the “Current Domain” and “New Domain.” If you are removing a compatible domain, also review the affected passkeys. Then click “Change Domain” or “Remove Domain.”

<Callout type="warn" title="Caution">

- “How to Configure Passkey Domains” shows the current site and the domain the system currently uses. The dialog shows “Use Current Site” if no domain is set, or “Keep Existing Domain” if one is already set.
- This button is available only when you access the site over HTTPS or through `http://localhost`, and the host is a domain name or `localhost`. Otherwise, the dialog displays “Configure passkeys using a domain over HTTPS. You can use localhost for local development.”
- If the primary domain does not match the current site or has not been set, the group displays a yellow warning. If the current site is missing from “Sites Allowed to Use Passkeys,” the interface displays “The current site is missing from the list. If users sign in here, add ….”
- Passkeys on removed domains will stop working. Before confirming, make sure affected users have another way to sign in.
- If “Enable Passkey” is turned off, users who have registered a passkey and have not enabled 2FA will be unable to sign in. After primary authentication succeeds, the system still requires passkey verification and displays “This verification method is currently unavailable.”
- To restore access, turn “Enable Passkey” back on or use “Reset Passkey” for affected users in <a href="/en/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">User Management</a>. Resetting a user's passkey deletes their passkey credentials and revokes their existing sessions.

**Login, linking, and deletion rules**

1. OAuth state is currently valid for about 10 minutes. State for account linking is also tied to the initiating user and session, preventing reuse across sessions.

## Login Verification and Security

This section describes the scope of authentication-related security checks. Most of these features affect login and account security and are configured outside this page.

- **Unified login verification**. If the user has enabled 2FA or Passkey authentication, successful primary authentication is followed by a unified verification challenge that is valid for about 5 minutes. The system issues a session only after the user completes the challenge. This mechanism strengthens login security. Signing in directly with a Passkey skips the additional challenge.
- **Single-use verification proofs**. Each proof is tied to a session and an action through an HMAC-based context hash, and the system consumes it once. If a callback, verification, or account linking flow fails, usually you need to restart the flow to obtain a fresh proof.
- **Scope of 2FA**. 2FA is a per-user security feature. Users enable and manage it on the <a href="/en/docs/guide/feature-guide/user/security#enable-two-step-verification" target="_blank" rel="noopener noreferrer">Security and Access</a> page. To reset a user’s 2FA, backup codes, and login sessions, administrators use “Reset 2FA” in <a href="/en/docs/guide/feature-guide/admin/user" target="_blank" rel="noopener noreferrer">User Management</a>.
- **Linking, unlinking, and deleting accounts**. Changes to account links and account deletion require re-verification to protect against session hijacking. Use 2FA or a Passkey if enabled. Otherwise, use a password or third-party login.

<Callout type="warn" title="Warning">

After enabling 2FA or Passkey authentication, users must complete the verification challenge, which lasts about 5 minutes, after primary authentication and before the system issues a session. Keep at least one verified alternative login method for Root and user accounts. If the verification proof or OAuth state has expired or been consumed, start a new login or account linking flow.

</Callout>

## Password Transmission Encryption

Password transmission encryption is controlled by the `PASSWORD_LOGIN_ENCRYPTION_ENABLED` environment variable, a boolean that defaults to `false`. This page has no corresponding setting. New API reads the variable only at startup. Restart New API after changing it.

When enabled, the front end uses RSA-OAEP to encrypt passwords before submitting them for password login or password verification during sensitive operations. Registration continues to submit the original password.

**How it works**

- At startup, the server reads the RSA private key from the database. If no key exists, the server generates a 2048-bit key and stores it in the database. Nodes connected to the same database share the key.
- The front end retrieves the enabled status and public key from the server, encrypts the password using an RSA-OAEP v1/v2 envelope, and submits it with the request.
- The server uses the private key to decrypt and verify the password.

<Callout type="warn" title="Warning">

- This is an instance-level environment variable. All nodes in a multi-instance deployment must use the same value.
- If the setting differs across nodes, some login requests will be rejected with the message “Invalid parameters”.
- The service fails to start if it cannot read or write the private key. If decryption fails, it displays “Incorrect username or password, or the user has been banned”.
- Account for HTTPS/HTTP transport through the reverse proxy. Disabling this setting sends the password in plaintext at the application layer.

</Callout>

Other nodes pick them up through system settings synchronization within about 3 seconds, or within one synchronization interval at the latest (60 seconds by default). **Additional notes**

- **Order of operations**. Before enabling GitHub, Discord, OIDC, LinuxDO, or WeChat login, or enabling email domain restriction, enter and save the corresponding credentials or settings. Then turn on the toggle and save again. The system rejects attempts to enable a feature before its required settings are saved. See [FAQ](#faq) for the messages.
- **No changes**. If OAuth integration or Passkey authentication settings are unchanged, the page displays “No changes to save”.
- **Unsaved changes**. If you leave the page with unsaved OAuth integration settings, the “Unsaved Changes” confirmation dialog appears.
- **Login and registration pages**. Login methods, registration options, and the Turnstile component are displayed based on site status cached in the browser. The server applies the new settings immediately, and pages that are already open show the changes after a refresh. The browser used to save Passkey settings, the OIDC display name, or custom OAuth settings updates automatically.

## Important Notes

**Login and callbacks**

- **Callback consistency**. The public URL used by the browser, the “Server Address”, the callback URL registered with the provider, and the Host/Proto values forwarded by the reverse proxy must all match.
- **Single-use verification proofs and state**. After a failure, start a new login or account linking flow.
- **Unified login verification**. Users with 2FA or Passkey authentication must complete the verification challenge after primary authentication. The challenge is valid for about 5 minutes.

**Credentials and domains**

- **Passkeys are bound to their domains**. After changing the domain or protocol, recheck the primary domain, compatible Passkey domains, sites allowed to use Passkeys, and the “Server Address”. Keep the old domain in the compatible domain list.
- **Turnstile**. Both the site key and secret key must be correct, Cloudflare must be reachable, and the Token must be valid. Turnstile uses a single global toggle. See [Bot Protection](#bot-protection) for the protected flows.
- **Telegram migration**. If you previously used the legacy Login Widget, register the `/oauth/telegram` callback URL under Login Widget in BotFather and obtain the Client ID and Client Secret. Existing account links continue to work. The `telegram` identifier (slug) remains reserved for the built-in provider.
- **Shared password encryption key**. The key is generated automatically at startup and stored in the database. All nodes must connect to the same database.

Disabling a provider leaves existing account links in place.

**Troubleshooting**

Disabling OAuth blocks new logins and account linking. Existing linked identities remain in place.

**Troubleshooting**

1. An administrator can reset the user’s Passkey in User Management and have the user register it again.

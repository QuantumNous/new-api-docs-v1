- Access to **System Settings** is restricted to Root.
- This page covers the rules for saving, applying, and verifying changes and handling sensitive settings across all settings areas. For details on individual fields, see the documentation for the corresponding area.

## Access and Permissions

Root can open System Settings from any of the following three locations. All three open **Site & Branding › System Information**.

1. **System Settings** at the bottom of the **Admin** group in the sidebar.
2. **System Settings** in the avatar menu in the upper-right corner.
3. The command palette, opened via **Search** in the top bar or by pressing ⌘/Ctrl+K. It lists the same pages as the sidebar.

When models have pending pricing changes, the count appears next to **System Settings** in the sidebar and next to **Billing & Payments** and its **Model Pricing** section in the left navigation.

Field-by-field saving submits each changed field separately and displays “Setting updated successfully” for each successful update. If a field fails to save, submission stops at that field and earlier changes remain saved. If there are no changes, some sections display “No changes to save,” while others give no notification.

<Callout type="info" title="Note">

- Messages such as “Setting updated successfully” and “Saved successfully” confirm only that the server accepted the save. Connectivity to external services such as OAuth, SMTP, payment gateways, webhooks, and Workers remains unverified.
</Callout>

### Scope and Multi-Instance Synchronization

1. Settings are stored as key-value pairs in the primary database. Once the node handling the save writes to the database, it immediately updates its in-memory values. The change takes effect without a restart.
2. After a save, other nodes reload settings from the database within about 3 seconds. Each save registers a sync task, and each node checks for new tasks about every 3 seconds and reloads settings when it finds changes. This also applies to settings with dedicated save methods, such as request policies, model prices, and passkey domains. The individual settings pages summarize this as “Syncs with system settings within about 3 seconds (within one sync cycle at most, 60 seconds by default).”
   - As a fallback, each node also reloads all settings every `SYNC_FREQUENCY` seconds (60 seconds by default). If the sync task could not be recorded, or if the cluster contains older nodes that have yet to be upgraded and do not check for sync tasks, those changes load on the next cycle.
   - `SYNC_FREQUENCY` is an environment variable measured in seconds. It is configured outside the interface and read only at startup. Changing it requires a restart.
   - Synchronization works with or without Redis, provided all nodes connect to the same primary database.
   - Nodes may read different values until they finish loading. Check the **Sync** column of the instance table to see which nodes have loaded the changes. If a node fails to load them, the column shows **Update Failed**, and the node retries on its next check. See <a href="/en/docs/guide/feature-guide/admin/system-info#node-sync" target="_blank" rel="noopener noreferrer">System Information</a>.
3. Master and Worker instances (`NODE_TYPE`) save and synchronize settings the same way. You can save changes on either type of node.

Adding, editing, or deleting a provider under **Authentication › Custom OAuth** also registers a sync task. Other nodes load the changes automatically within about 3 seconds without a restart. Custom OAuth relies on sync tasks alone, so older nodes that have yet to be upgraded must restart to load these changes.

The following changes require a restart to take effect.

1. Changes to **Maximum Cached Sessions** under **Request Policies › Sessions & Retries** require a restart. This setting only applies when Redis is disabled. See <a href="/en/docs/guide/feature-guide/system-settings/settings-request-policies#saving-and-applying-changes" target="_blank" rel="noopener noreferrer">Request Policies Configuration</a>.
2. Deployment environment variables are configured outside the interface and read only at startup. Changes require a restart. Examples include `SYNC_FREQUENCY`, `NODE_TYPE`, and global rate limit variables such as `GLOBAL_API_RATE_LIMIT`.
   - A few environment variables, including `CHANNEL_TEST_FREQUENCY` and `CHANNEL_TEST_ENABLED`, override values in the interface. See <a href="/en/docs/guide/feature-guide/system-settings/settings-request-policies#channel-health" target="_blank" rel="noopener noreferrer">Channel Health</a>.

### Frontend Display and Caching

1. The interface gets its sign-in methods, system name, logo, footer, top navigation, sidebar modules, quota display format, and console panels from the site status. The server returns the in-memory settings of the node handling each request. The browser caches the response for 5 minutes and fetches it again on page refresh. System announcements in the Notification Center use a separate cache with the same behavior.
2. After a save, the browser that submitted the changes automatically updates only certain display settings, such as the top navigation, sidebar modules, quota and currency display, server address, passkeys, and custom OAuth. Other settings, as well as pages that other users already have open, show the new values after a refresh.
3. The server processes requests using the saved settings independently of the browser cache. Open pages may still show old navigation entries or forms until refreshed.

## Sensitive Settings and Audit Logs

**Sensitive Settings**

- The settings read API omits entire entries whose keys end in `Token`, `Secret`, `Key`, `secret`, `api_key`, or `private_key`. These are primarily keys, tokens, and credentials. The corresponding fields always appear blank in the interface.
- Leaving these fields blank generally retains their saved values. The interface submits a value only when you enter a new one. Some fields display “Leave blank to keep the existing key,” “Leave blank to keep the existing credentials,” or “Leave blank unless you are rotating the key.” Under **Operations › Worker Proxy**, saving with **Worker URL** blank also clears **Worker Access Key**. Custom OAuth client secrets also appear blank, and leaving the field blank while editing retains the saved secret.
- The database stores setting values in plaintext. Protect the database and its backups to the same standard.

**Audit Logs**

- When fields are saved individually, the audit log records one entry per successful field update. The entry displays “Modify System Settings” followed by the configuration key and records only the key.
- Settings with dedicated save methods record different details. Request Policies records only the request method and path. Model Pricing records the names of the models whose prices changed. Passkey domain changes, including changes to **Server Address** under **System Information**, record the removed domains and the number of affected credentials. Custom OAuth records only the operation type: add, edit, or delete.
- Failed save requests also produce audit entries, with the configuration key omitted.
- In the sidebar, go to **General › Audit Log**. Only Root can see audit entries for Root actions. See <a href="/en/docs/guide/feature-guide/user/audit-log" target="_blank" rel="noopener noreferrer">Audit Log</a>.
- Audit logs omit previous values, so configuration recovery requires a separate record. Continue to use external secret management and maintain separate change records.

<Callout type="warn" title="Protect Your Secrets">
Keep sensitive values such as client secrets, SMTP tokens, and payment keys out of screenshots, support tickets, and general-purpose logs. The read API omits plaintext credentials. Browsers, proxies, database backups, and operations environments still require credential protection.
</Callout>

## Recording and Verifying Changes

System Settings has no configuration snapshots, version comparisons, or one-click rollback. Before making changes in production, record the original values and be prepared to restore them field by field. Record at least the following.

- The settings area, section, and fields being changed.
- The previous non-sensitive values and the versions of any sensitive credentials in your secret management system.
- The pages, APIs, roles, and external services you expect to be affected.
- The test steps, pass criteria, and conditions for restoring the previous settings.
- The time to allow for synchronization in multi-instance deployments and which changes require a restart.

After saving, verify the changes as follows.

1. Check the notifications. When saving field by field, each modified field should produce a “Setting updated successfully” notification. If a save fails, the failed field and all subsequent fields remain unsaved.
2. Refresh the page and check the non-sensitive fields. Sensitive fields always appear blank, so a refresh cannot verify their values. In a multi-instance deployment, wait for the other nodes to load important changes before refreshing to verify them.
3. Test the affected workflows directly, such as signing in, sending email, running sandbox payments, testing callbacks, and making model requests.
4. In a multi-instance deployment, confirm that each node has loaded the changes in the **Sync** column of the instance table, then verify the changes on other nodes. See <a href="/en/docs/guide/feature-guide/admin/system-info#node-sync" target="_blank" rel="noopener noreferrer">System Information</a>.
5. Verify changes involving authentication, payments, billing, request policies, SSRF, or outbound callbacks on a test instance or during a maintenance window first.

## Important Notes

- **Field-by-field saves are not rolled back.** When saving multiple fields, earlier changes remain saved if a later field fails. Submission stops at the failed field. See [Save Methods](#save-methods).
- **Synchronization takes time across nodes, and some changes require a restart.** Other nodes sync with system settings within about 3 seconds (within one sync cycle at most, 60 seconds by default). Changes to **Maximum Cached Sessions** and environment variables require a restart. See [Scope and Multi-Instance Synchronization](#scope-and-multi-instance-synchronization).
- **Refresh the page to see display changes.** The browser caches site status. After a save, other users see the new values when they refresh the page, if they have not already appeared. See [Frontend Display and Caching](#frontend-display-and-caching).
- **Environment variables can override values in the interface.** If `CHANNEL_TEST_FREQUENCY` or `CHANNEL_TEST_ENABLED` overrides a setting, the environment value may remain in effect after you change the setting in the interface.
- **Key fields appear blank.** Leave them blank to retain the saved values. Saving with **Worker URL** blank also clears **Worker Access Key**. See [Sensitive Settings and Audit Logs](#sensitive-settings-and-audit-logs).
- **Keep your own record of previous values.** Audit logs omit previous values, and System Settings has no version history to restore from. Record the original values before making changes. See [Recording and Verifying Changes](#recording-and-verifying-changes).

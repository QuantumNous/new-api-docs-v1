## Request Policy Configuration Overview

The request policy determines which channel a request tries first, whether to retry after a failure, and when to automatically disable or recover a channel. Switch between the two sections under **Request Policy** in the left navigation. **Session and Retry** opens by default.

The screenshot shows **Session Cache Settings** expanded. It is collapsed by default. **Cache Entries** in the footer shows `0 / 0` because the screenshot was taken in an environment that uses Redis.

**Configure session persistence**

1. In **Session Defaults**, confirm that **Enable Session Persistence** is on. New rules default to **Inherit Global Default** for **Session Persistence**, so choose a global mode that enables persistence. Save any changes here in step 3.
2. Click **Add Rule** → **Blank Rule**, enter a **Name**, a **Model Regex**, and at least one **Key Source**, then click **Save** in the dialog. See **Add or Edit a Rule** below for field descriptions. The new rule appears at the end of the table.
   - Rules are matched in list order. Make sure your conditions do not overlap with earlier rules, which would match the request first. See **Rule Matching** below. To reorder rules, use JSON mode.
   - The **Codex CLI** and **Claude CLI** templates match the two built-in rules listed below. Use the templates to restore the built-in rules if you deleted them.
3. Click **Save Changes** in the page header. The “Saved successfully” message confirms submission. For validation errors, see [Saving and Applying Changes](#saving-and-applying-changes).

<Callout type="info" title="Tip">

- For a rule added using the steps above, a binding is written only when a request meets all the rule’s conditions, uses a Key value with no existing binding, and succeeds with an HTTP status code below 400. Requests pinned to a channel bypass session rules.
- The **Cache Entries** column and footer count stay the same as requests come in. Click **Refresh Statistics** in the footer to update them. Saving changes to session rules also refreshes the counts automatically.
- To check whether subsequent requests used the binding, see “Does the ✦ next to the channel ID mean the session binding is active?” in the [FAQ](#frequently-asked-questions).

</Callout>

**Session Defaults**

The card subtitle is “Rules can inherit or override these settings.” Turning off **Enable Session Persistence** grays out both binding switches. You can still change the **Session Persistence** radio selection, but it only takes effect when the main switch is on. Expand **Session Cache Settings**, which is collapsed by default, to see the two cache fields.

**Session Persistence Modes**

| Mode | Behavior When a Rule Matches |
| --- | --- |
| No Persistence | The rule still matches and its parameter override template still applies. Channel selection proceeds normally, with no session bindings read or written. |
| Prefer Original Channel, Allow Switching on Failure | The first attempt prefers the channel already bound to the session. If that attempt fails, the normal retry process can switch to another channel. |
| Require Original Channel | If there is no binding yet, the request selects a channel normally and creates a binding on success. Once a rule matches, any failure ends the request without a retry, even if the session has no channel binding yet. If a binding exists and its channel is unavailable, the request immediately returns HTTP 503 with the error `strict_session_binding_unavailable`. |

**Session Rules**

The card subtitle is “Define how sessions are identified and which channels they use.” The rule count appears next to the title. Session rules define how to identify requests from the same session and how to keep using that session’s channel after a match. The system selects the channel normally before binding it to the session.

Each session binding occupies one cache entry. **Cache Entries** is the number of bindings currently stored. Clearing the cache removes those bindings, so subsequent requests select channels again.

**Rule Matching**

1. Rules are checked in list order. The first rule that meets both conditions below applies, even if the session has no binding yet. Later rules are skipped.
   1. The model, path, and User-Agent conditions all match.
   2. A nonempty Key is found and passes Value Regex validation.
2. With multiple Key sources, only the first nonempty value is used. If that value fails Value Regex validation, the entire rule is skipped, including any remaining Key sources in that rule.
3. A rule with an empty model regex matches no requests, even if it displays as **All Models** in the table. The dialog requires at least one line, so a rule like this can only be entered in JSON mode.
4. If a session persistence mode has never been set for a rule, as with the two built-in rules and rules carried over from older versions, the legacy `skip_retry_on_failure` field determines the displayed mode. A value of `true` displays **Require Original Channel**. Otherwise, it displays **Prefer Original Channel, Allow Switching on Failure**. Both show **Rule Override** as the source. The dialog preselects the same mode and writes it explicitly when you save.
5. **Cancel** in the dialog discards the current edit. **Save** only updates the draft, as described in the **Session Rules** caution above.
6. On submission, the backend compiles the model, path, and Value Regex patterns for all rules. Any invalid pattern causes the entire save to fail with an error of the form `rule "<规则名>": error parsing regexp: …`.

**Retry Budget Settings**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | Definition | Requirements and Limits | Default |
| --- | --- | --- | --- |
| Maximum Retry Count | Excludes the initial attempt and is counted per group. See item 2 under **Retry Rules** below. The default of `0` disables retries after a failure. | Integer from `0–99`. The backend only requires a value of at least `0`. | `0` |
| Auto-Retry Status Codes | Always excludes 2xx, 504, and 524. The placeholder reads “e.g., 401, 403, 429, 500-599”. Adjacent ranges are merged on save. See [Saving and Applying Changes](#saving-and-applying-changes). | Comma-separated status codes or inclusive ranges within `100–599`. Invalid input displays “Invalid status code rule”. Leave empty to disable status-code-based retries. | `100-199,300-399,401-407,409-499,500-503,505-523,525-599` |

</div>

**Retry Rules**

1. The total number of attempts is 1 plus **Maximum Retry Count**. Each retry selects a channel again and moves down one channel priority level. Once the lowest level is reached, retries stay at that level and may select the same channel again. If the initial attempt used a session-bound channel, the first retry starts at the highest priority.
2. If the API key’s group is `auto` and **Cross-Group Retry** is on, each group has its own retry budget. When the current group’s budget runs out, the request moves to the next group and starts at its highest priority.
3. After each failure, the following conditions are checked in order. The first match stops retries.
   1. The request matches a **Require Original Channel** rule.
   2. The request is pinned to a channel.
   3. The error is marked as non-retryable.
   4. The retry budget is exhausted.
   5. The status code is 2xx, 504, or 524, or the upstream response body cannot be parsed.
   6. The status code is absent from **Auto-Retry Status Codes**.
4. Two exceptions apply.
   - For channel errors, whose error codes start with `channel:`, only conditions 1 and 2 are checked before retrying. Examples include a channel with no available keys, an invalid key, an invalid parameter override configuration, and a model mapping error. **Maximum Retry Count** still limits the total number of attempts.
   - If the status code falls outside `100–599`, the request retries after passing checks 1–4 and skips checks 5 and 6.
5. Asynchronous task submissions, such as video generation, use built-in rules and ignore **Auto-Retry Status Codes**. They retry on 429, 307, and all 5xx status codes except 504 and 524. They skip retries on 2xx, 400, 408, 504, and 524. For all other status codes, local errors end the request and upstream errors trigger a retry, including upstream 401, 403, and 404 responses. **Maximum Retry Count**, channel pinning, and **Require Original Channel** also apply.

**When automatic disabling is triggered**

<div className="[&_table]:min-w-[36rem] [&_td:first-child]:whitespace-nowrap [&_th]:whitespace-nowrap">

| Scenario | Criteria | Notes |
| --- | --- | --- |
| Live request failure | Channel errors, “Auto-Disable Status Codes,” and “Failure Keywords” | Request duration is ignored. Errors marked as non-retryable do not trigger disabling unless they are channel errors. |
| Scheduled test or “Test All Channels” | The same criteria as above, plus “Health Check Duration Threshold (seconds)” | “Check Only Automatically Disabled Channels” mode leaves channel disabling inactive. |
| Single-channel test | — | Leaves channel status unchanged. |

1. Automatic disabling requires both the global “Disable on Failure” toggle and the channel’s “Auto-Disable on Error” toggle to be on.
2. For a multi-key channel, the system disables only the key that encountered the error. It marks the entire channel as automatically disabled once all keys are disabled.

**Automatic recovery and notifications**

1. To recover automatically, a channel must be in the automatically disabled state, “Re-enable on Success” must be on, and the channel must pass a scheduled test or “Test All Channels.” If the global “Disable on Failure” toggle is on, the test duration must also be at or below the “Health Check Duration Threshold (seconds).” Recovery is limited to automatically disabled channels tested through a scheduled or batch test.
2. Automatic disabling and recovery both send notifications. Enabled administrators with the Admin or Root role receive them if they turn on “Channel Notifications.” If the toggle has never been set, only Root receives notifications by default. Each administrator can toggle “Channel Notifications” in their <a href="/en/docs/guide/feature-guide/user/personal-setting#configure-notification-and-behavior-preferences" target="_blank" rel="noopener noreferrer">Profile</a>.
3. For each administrator, notifications for the same channel and status are limited to 2 within 10 minutes by default. The `NOTIFY_LIMIT_COUNT` environment variable controls the count (default `2`), and `NOTIFICATION_LIMIT_DURATION_MINUTE` controls the window in minutes (default `10`, with values of 0 or less treated as 10). These limits are configured through environment variables only.

**Runtime requirements**

1. Periodic tests run only on the Master instance. Nodes with `NODE_TYPE=slave` skip them. Tests are queued at the configured interval, and a new round starts only after the previous one finishes.
2. Environment variables override the settings on this page. Setting `CHANNEL_TEST_FREQUENCY` to a positive integer forces periodic testing on, sets the interval to that number of minutes, and locks the mode to “Proactively Check All Channels.” Setting `CHANNEL_TEST_ENABLED` to a Boolean value forces the “Periodic Channel Testing” toggle to that value. `CHANNEL_TEST_ENABLED` is applied after `CHANNEL_TEST_FREQUENCY`, so `false` turns periodic testing off even when a frequency is set.
3. All three periodic test settings on the page remain editable and can be saved when these variables are set. Runtime behavior follows the environment overrides. New API reads both variables only at startup, so restart it after changing either one.

## Request Decision Records

Request Policy records routing and retry decisions for each request to help with troubleshooting.

- To find the record, open an entry in <a href="/en/docs/guide/feature-guide/user/log#request-policy-decisions" target="_blank" rel="noopener noreferrer">Usage Logs</a> and go to “Details” → “Request Policy Decisions.” Only Admin and Root can see it, and it appears only when “All” is selected in the upper-right corner of the page.
- The record shows the selected channel, the matched session rule, the reason for failure, the decision to retry or stop and the source of that decision, the elapsed time, the group, the status code, and how channel health was handled, step by step.
- Decision records for successful requests are written to usage logs. This requires “Log Quota Usage” to be enabled in <a href="/en/docs/guide/feature-guide/system-settings/settings-operations#log-maintenance" target="_blank" rel="noopener noreferrer">Operations Settings</a>. It is on by default.
- Decision records for failed attempts are written to error logs only when `ERROR_LOG_ENABLED=true` is set. The default is `false`. Configure it through the environment and restart New API after changing it. If the request ultimately fails, the failed-attempt entries are the only records written.
- Requests that match “Must Use Original Channel” and return HTTP 503 immediately because the bound channel is unavailable leave no decision record.

## Saving and Applying Changes

For instructions on saving changes, see <a href="/en/docs/guide/feature-guide/system-settings/system-setting#save-methods" target="_blank" rel="noopener noreferrer">System Settings Overview</a>. For information about when changes take effect and how they synchronize across instances, see <a href="/en/docs/guide/feature-guide/system-settings/system-setting#scope-and-multi-instance-synchronization" target="_blank" rel="noopener noreferrer">Scope and Multi-Instance Synchronization</a>. Unless otherwise specified, the node handling the save request starts using the new values immediately. Other nodes usually pick them up through system settings synchronization within about 3 seconds and within one synchronization cycle at the latest (60 seconds by default). The `SYNC_FREQUENCY` environment variable sets the cycle in seconds. New API reads all environment variables mentioned on this page at startup, so restart it after changing any of them. The tables below show when each setting is read.

**Retries and session affinity**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | How to Save | When It Takes Effect |
| --- | --- | --- |
| Max Retries, Auto-Retry Status Codes | Click “Save Changes” at the top of the page. All three cards are saved together. | The new values are read after each request failure when deciding whether to retry. |
| Session affinity toggle, mode, and session rules | Click “Save Changes” at the top of the page. | Applies the next time a request is evaluated against the rules. Existing session bindings survive the save and remain until they expire or are cleared. |
| Default Session TTL (seconds) | Click “Save Changes” at the top of the page. | Applies to newly created bindings. |
| Max Cached Sessions | Click “Save Changes” at the top of the page. | Restart the service to change the in-memory cache capacity. This setting applies only to the in-memory cache. |
| Clear All Caches, Clear Cache for a Single Rule | Runs immediately after confirmation without using the save button. | Removes the corresponding session bindings immediately after confirmation. In multi-instance deployments without Redis, this clears only the cache on the node handling the request. |

</div>

**Channel testing and automatic disabling**

<div className="[&_table]:min-w-[36rem] [&_th]:whitespace-nowrap">

| Setting | How to Save | When It Takes Effect |
| --- | --- | --- |
| Periodic Channel Testing | Click “Save Changes” at the top of the page to save the settings together. | The Master instance checks about every 15 seconds. Once enabled, a test starts at the next check if the time since the previous test finished exceeds the interval. Tests already in progress continue. |
| Test Interval (minutes) | Click “Save Changes” at the top of the page to save the settings together. | The new interval is used starting with the next check. |
| Channel Test Mode, Channel Test Concurrency | Click “Save Changes” at the top of the page. | The new values are read when the next test round starts. Tests already in progress keep their original settings. |
| Disable on Failure, Auto-Disable Status Codes, Failure Keywords | Click “Save Changes” at the top of the page. | The new values are read the next time a request fails or a channel test result is evaluated. |
| Health Check Duration Threshold (seconds), Re-enable on Success | Click “Save Changes” at the top of the page. | The new values are read during the next scheduled or batch channel test. |

</div>

**Additional notes**

- **Saving settings together.** The page submits only the settings that changed in the section. The backend merges the submitted values into the full request policy, validates it as a whole, and saves the changes in a single transaction. On success, the page displays “Saved successfully.” A single invalid setting prevents all changes in that submission from being saved. Settings areas such as “Security and Limits” save each setting individually.
- **No changes.** If nothing has changed, the page displays “No changes to save.”
- **Validation messages.** The frontend validates most fields and blocks submission if a value is invalid. If backend validation fails, a toast displays the original English error from the backend. This most often happens when editing rule regular expressions or making changes in JSON mode. “Sessions and Retries” also displays the error in red below the card. If that section has unsaved changes and contains an invalid value, the footer displays “Fix invalid settings before saving.”
- **Merging ranges.** When you save changes to “Auto-Retry Status Codes” or “Auto-Disable Status Codes,” the frontend merges adjacent ranges before submitting them. For example, `409-499,500-503` becomes `409-503` and covers the same status codes.
- **Concurrent edits and unsaved changes.** Request Policy saves are last-write-wins, with no version conflict detection. Leaving the page discards unsaved changes without prompting.

## Important Notes

- **Failed requests that match built-in CLI rules are not retried.** The two built-in rules and rules generated from templates default to “Must Use Original Channel.” See [Sessions and Retries](#session-and-retry).
- **Each retry runs channel selection again.** Once the available priority levels are exhausted, the same channel may be selected again. “Max Retries” defaults to `0`, which disables retries. See [Sessions and Retries](#session-and-retry).
- **“Test All Channels” can disable or recover channels.** It tests all channels except manually disabled ones and applies the automatic disable and recovery rules in [Channel Health](#channel-health).
- **Environment variables override periodic test settings.** If `CHANNEL_TEST_FREQUENCY` or `CHANNEL_TEST_ENABLED` is set, the periodic test settings on the page may have no effect. See [Channel Health](#channel-health).
- **Decision records for failed attempts require an environment variable.** These records are written only when `ERROR_LOG_ENABLED=true` is set. See [Request Decision Records](#request-decision-records).

<Accordion title="Retries do not take effect">

**Troubleshooting**

Check the following in order.

1. Whether “Max Retries” is still set to its default of `0`.
2. Whether the failure status code appears in “Auto-Retry Status Codes.”
3. Whether the request matched a rule set to “Must Use Original Channel,” including either of the two built-in CLI rules.
4. Whether the request was pinned to a specific channel.
5. Whether the status code is one that never triggers a retry, such as 2xx, 504, or 524.
6. Whether only one channel is available or the lowest priority level contains just one channel. A retry can still occur and select the same channel again, making it look as though the request was never retried.

</Accordion>

<Accordion title="Failed requests that match built-in CLI rules are not retried">

**Explanation**

The two built-in CLI rules match `/v1/responses` requests for `gpt-*` models when the body includes `prompt_cache_key`, and `/v1/messages` requests for `claude-*` models when the body includes `metadata.user_id`, respectively.

**Possible cause**

Both rules default to “Must Use Original Channel.” A request that matches either rule is never retried, even if a channel binding has yet to be created.

**Troubleshooting**

1. Change “Session Affinity” for both rules to “Prefer Original Channel, Allow Switching on Failure,” or select “Inherit Global Default” and verify that the global mode permits switching or disables affinity.
2. Click “Save” in the dialog.
3. Click “Save Changes” at the top of the page.

</Accordion>

<Accordion title="A channel was automatically disabled">

**Explanation**

The duration threshold is checked only during scheduled tests and “Test All Channels.”

**Possible cause**

The global “Disable on Failure” setting, the channel’s “Auto-Disable on Error” setting, “Auto-Disable Status Codes,” or “Failure Keywords” may be configured differently than expected.

</Accordion>

<Accordion title="A channel did not recover automatically">

**Explanation**

Automatic recovery applies only to automatically disabled channels and requires a scheduled or batch test.

**Possible cause**

The global “Disable on Failure” toggle is on, and the test took longer than the “Health Check Duration Threshold (seconds).”

**Troubleshooting**

1. Turn on “Re-enable on Success.”
2. Verify that the channel passed a scheduled test or a run of “Test All Channels.”

</Accordion>

<Accordion title="The periodic test interval differs from the value on the page">

**Explanation**

Nodes with `NODE_TYPE=slave` skip periodic tests.

**Possible cause**

The deployment environment has `CHANNEL_TEST_FREQUENCY` or `CHANNEL_TEST_ENABLED` set. These variables override the values on the page.

</Accordion>

<Accordion title="The Clear Cache button is unavailable or Cache Entries shows Not Applicable">

**Possible causes**

- “Include Rule Name” is off for the rule.
- The cache statistics could not be retrieved.
- The rule has yet to be saved using “Save Changes” at the top of the page.

</Accordion>

<Accordion title="Cache Entries stays at 0">

**Explanation**

A capacity of `0` is expected when Redis is in use.

**Troubleshooting**

If the number of entries in use stays at 0, check the following in order.

1. Whether you clicked “Refresh Statistics” after sending the request. Cache statistics update only when refreshed.
2. Whether you submitted the rule using “Save Changes” at the top of the page. “Save” in the dialog updates only the draft.
3. Whether “Enable Session Affinity” is on and whether the rule’s effective mode is “No Affinity.”
4. Whether the request meets all the rule’s conditions, including extracting a non-empty key and matching the value against the regular expression.
5. Whether an earlier rule in the list matched the request first. You can see the rule that actually matched in the “Matched Session Rule” step under “Request Policy Decisions.”
6. Whether the request failed. Only successful requests write bindings.
7. Whether the request was pinned to a specific channel. Pinned requests bypass session rules.

</Accordion>

<Accordion title="An English error appears when saving">

**Explanation**

The message comes directly from backend validation. The backend rejected the entire submission.

**Troubleshooting**

1. Correct the invalid settings and save again.

</Accordion>

<Accordion title="Decision records for failed requests are missing from Usage Logs">

**Troubleshooting**

1. Set the `ERROR_LOG_ENABLED=true` environment variable.

</Accordion>

<Accordion title="Does the ✦ next to the channel ID mean a session binding took effect?">

**Explanation**

The amber ✦ at the upper-right corner of the channel ID in Usage Logs indicates that the request was associated with a session rule. Hover over it to see the rule name and group. Use the checks below to verify whether the binding took effect.

- For rules without a parameter override template, ✦ appears only when the first attempt uses an existing binding. The first request for a new key has no ✦. It can appear from the second request onward.
- For rules with a parameter override template, including both built-in rules, ✦ appears whenever the rule matches, even on the first request and in “No Affinity” mode.

**Troubleshooting**

1. Click “Refresh Statistics” at the bottom of the card and check whether the “Cache Entries” count increased for that rule.
2. Send another request with the same key and compare the channel IDs for the two entries in Usage Logs.

</Accordion>
